## 문제 정의

이벤트 목록에 인기순 정렬을 도입하려면 "인기"를 어떤 신호로 측정할지 결정해야 한다. 가장 직관적인 신호는 페이지뷰다. GA4 같은 analytics warehouse에는 page_view 이벤트 로그가 쌓여 있고, SQL 한 줄로 이벤트별 조회수를 집계할 수 있다.

문제는 데이터 소유권이다. analytics warehouse는 다음 두 가지를 보장하지 않는다.

- **비즈니스 적격성**: 현재 판매 중인지, 노출 허용 상태인지, 사전예약 대상인지는 analytics warehouse가 알지 못한다. 집계 기간 중 비활성화된 이벤트도 조회수 상위에 오를 수 있다.
- **실시간 일관성**: analytics warehouse의 집계는 배치로 처리되므로 애플리케이션 DB의 현재 상태와 동기화되어 있지 않다.

이 두 가지를 analytics warehouse 쪽에서 해결하려 하면 파이프라인이 복잡해지고 결합도가 높아진다. 대신, analytics warehouse의 역할을 "조회수 기반 후보 선출"로 제한하고 나머지 판단은 애플리케이션 DB에서 수행하는 방향이 더 단순하고 유지보수하기 쉽다.

## 설계 원칙과 접근 방식

### 1. analytics warehouse는 신호 생성기, 애플리케이션 DB는 판단자

파이프라인을 두 단계로 명확히 분리한다.

```
[analytics warehouse]
  └─ page_view 집계 → 이벤트별 조회수 순위 후보 리스트 생성

[애플리케이션 DB]
  └─ 후보 리스트 수신
  └─ 비즈니스 적격성 재검증 (판매 상태, 노출 여부 등)
  └─ 적격 이벤트만 대상으로 최종 순위 재계산
  └─ 랭킹 캐시에 저장
```

analytics warehouse SQL은 조회수 기준으로 후보를 선출하는 역할만 한다. 실제로 노출할 순위는 애플리케이션 DB가 자체 상태를 기준으로 다시 계산한다.

### 2. SQL은 코드 저장소에서 관리

analytics warehouse 쿼리를 코드에 인라인으로 넣으면 변경 이력을 추적하기 어렵다. `.sql` 파일로 분리해서 코드 저장소에 함께 관리하면 리뷰와 diff가 가능하고, 쿼리 변경이 다른 코드 변경과 같은 맥락에서 검토된다.

### 3. 조회수 값은 내부 정렬에만 사용, 캐시나 API에 노출하지 않는다

정확한 조회수(viewCount)는 비즈니스적으로 민감할 수 있다. 이 값을 랭킹 캐시에 저장하거나 frontend API를 통해 외부에 내려보내면 두 가지 문제가 생긴다.

- 수치가 경쟁사나 외부에 노출될 위험
- 캐시와 실제 집계값이 불일치하는 시점이 발생했을 때 디버깅 복잡도 증가

해결책은 단순하다. 조회수는 후보 선출과 내부 정렬에만 사용하고, 캐시와 API 응답에는 **순위 인덱스(rank)** 만 저장한다.

## 트레이드오프

### 후보 크기와 랭킹 정확도

analytics warehouse에서 상위 N개 후보만 뽑아오면 애플리케이션 DB 재검증 단계에서 일부 후보가 탈락했을 때 최종 랭킹 결과가 N개에 못 미칠 수 있다. 후보 크기를 충분히 크게 잡으면 이 문제를 완화할 수 있지만, 너무 크면 재검증 비용이 늘어난다. 실제 탈락률을 측정해서 후보 크기를 조정하는 것이 현실적인 접근이다.

### 집계 기간 설정

analytics warehouse 집계 기간이 너무 짧으면 최근에 등록된 이벤트가 불리해지고, 너무 길면 오래된 인기가 현재 순위에 과도하게 반영된다. 서비스 특성에 맞는 기간을 실험적으로 찾아야 하며, 기간 설정은 `.sql` 파일에서 파라미터로 분리해 두는 것이 변경 추적에 유리하다.

### 랭킹 캐시 갱신 주기

랭킹 캐시를 얼마나 자주 갱신할지는 analytics warehouse 집계 지연과 비즈니스 요구 사이에서 결정해야 한다. 실시간에 가까운 순위가 필요하다면 캐시 갱신 비용이 올라간다. 대부분의 이벤트 랭킹은 수 시간 단위의 배치 갱신으로 충분하다.

## 검증 방법

### 단위 테스트: 인제스트 로직 분리

analytics warehouse 쿼리 실행과 애플리케이션 DB 적격성 검증을 별도 함수로 분리하면 각각을 독립적으로 테스트할 수 있다. 특히 애플리케이션 DB 재검증 로직은 픽스처 데이터만으로 단위 테스트가 가능하다.

```python
# 예시: 적격성 필터 로직을 순수 함수로 분리
def filter_eligible_events(candidates, db_session):
    eligible_ids = {
        e.id for e in db_session.query(Event)
        .filter(Event.id.in_(candidates), Event.is_active == True)
    }
    return [c for c in candidates if c["event_id"] in eligible_ids]
```

이 함수는 analytics warehouse 연결 없이 DB 픽스처만으로 테스트할 수 있다.

### 정적 검증 파이프라인

코드 변경이 파이프라인 전체를 깨지 않는지 확인하는 최소한의 검증 체계를 구성한다.

- `py_compile` 혹은 syntax check: 구문 오류 조기 감지
- import 체크: 의존성 누락 사전 감지
- format 체크: 코드 스타일 일관성
- `.sql` 파일 diff: 쿼리 변경 의도 명시적 검토

환경 의존성이 높은 통합 테스트(실제 analytics warehouse 연결, 운영 환경 시크릿 필요)는 CI 파이프라인에서 분리하거나 로컬 환경에서는 스킵할 수 있도록 조건부 처리한다.

### 구 캐시 필드 방어적 무시

랭킹 캐시 스키마가 변경될 때, 구 필드를 그대로 읽으면 오래된 값이 의도치 않게 노출될 수 있다. 캐시를 읽는 쪽에서 신규 스키마 기준으로만 필드를 참조하고, 구 필드는 명시적으로 무시하는 방어 코드를 추가한다. 이는 캐시 마이그레이션 중단 없이 점진적 배포를 가능하게 한다.

## 배운 것

**analytics warehouse는 신호 생산자이지 진실의 원천이 아니다.** 비즈니스 로직이 analytics 데이터에 직접 의존하기 시작하면 두 시스템 간 불일치가 버그로 이어진다. 랭킹 파이프라인을 설계할 때 "이 판단은 어느 시스템이 해야 하는가"를 명확히 정의하면 데이터 소유권이 분산되지 않는다.

**조회수 같은 민감한 집계값은 순위 계산 과정에서만 소비하고 저장하거나 외부에 내보내지 않는다.** 순위 인덱스만 캐시하면 민감도 문제와 캐시 불일치 문제를 동시에 피할 수 있다.

**SQL도 코드다.** analytics 쿼리를 코드 저장소에서 관리하면 파이프라인 변경 이력이 명확해지고, 쿼리 수정이 리뷰 프로세스 안에 들어온다.
