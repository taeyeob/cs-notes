## 문제 정의

범용 `Category` 또는 `Tag` 모델에는 보통 `description`이나 `additional_info` 같은 JSON 필드가 있다. 새 기능이 필요할 때 이 필드에 키 하나를 추가하면 마이그레이션도 없고 빠르게 동작한다. "도시별 이벤트"처럼 지역 기반 필터링을 추가할 때도 같은 유혹이 생긴다.

그러나 아래 두 문장은 다른 사실이다.

- "이 이벤트에 '도쿄'라는 태그가 붙어 있다."
- "이 이벤트의 지역 source of truth는 도쿄다."

첫 번째는 분류 속성이고, 두 번째는 도메인 식별자다. 이 둘을 같은 테이블에 섞으면 의미의 경계가 사라진다.

## JSON 필드 재활용의 위험

태그 체계에 지역 정보를 끼워 넣으면 처음에는 잘 동작한다. 문제는 운영이 시작된 이후에 드러난다.

운영자가 "도쿄" 태그 이름을 "Tokyo (일본)"으로 수정하거나, 태그를 다른 카테고리로 재분류하면 지역 필터 API가 의도치 않게 깨진다. 태그는 표시용 레이블이므로 바뀔 수 있는데, 지역 API는 이 태그가 고정된 식별자처럼 동작하기를 기대하는 것이다.

기능 요구가 늘어날수록 JSON 필드는 빠르게 불어난다.

```python
# 처음엔 단순해 보인다
tag.additional_info = {"region_code": "JP-13"}

# 조금 지나면 이렇게 된다
tag.additional_info = {
    "region_code": "JP-13",
    "country": "JP",
    "latitude": 35.6895,
    "longitude": 139.6917,
    "aliases": ["Tokyo", "東京"],
    "sort_order": 1,
    "is_active": True,
}
```

이 시점에서 JSON 필드는 사실상 `Location` 모델이다. 타입 안전성도 없고, 외래 키 참조도 없으며, 인덱스도 모델 필드나 FK 제약만큼 자연스럽게 걸리지 않는 채로.

중간 절충안으로 `CategoryType.REGION` 같은 타입을 두는 방법도 있다. 하지만 지역이 독립적인 도메인으로 성장할 가능성이 높다면, 타입 분기는 범용 모델에 책임을 계속 추가하는 임시방편이 된다.

## 추천 설계: Location 모델 분리

`Location`을 독립 모델로 만들면 구조가 명확해진다.

```python
class Location(models.Model):
    code = models.CharField(max_length=20, unique=True)  # 예: "JP-TOKYO"
    type = models.CharField(
        max_length=20,
        choices=[("COUNTRY", "국가"), ("CITY", "도시"), ("REGION", "지역")]
    )
    name_ko = models.CharField(max_length=100)
    name_en = models.CharField(max_length=100)
    parent = models.ForeignKey(
        "self", null=True, blank=True, on_delete=models.SET_NULL
    )
    latitude = models.FloatField(null=True, blank=True)
    longitude = models.FloatField(null=True, blank=True)
    aliases = models.JSONField(default=list)
    is_active = models.BooleanField(default=True)
    sort_order = models.IntegerField(default=0)
```

이벤트와 `Location`의 관계는 단일 FK보다 M2M + through table이 유연하다. 하나의 이벤트가 복수 도시에 걸칠 수 있고, 국가와 도시를 동시에 태깅할 수 있으며, 데이터 출처를 추적할 수 있기 때문이다.

```python
class EventLocation(models.Model):
    event = models.ForeignKey(Event, on_delete=models.CASCADE)
    location = models.ForeignKey(Location, on_delete=models.CASCADE)
    source = models.CharField(
        max_length=20,
        choices=[("MANUAL", "수동"), ("MIGRATED", "마이그레이션"), ("AUTO", "자동추론")],
        default="MANUAL",
    )

    class Meta:
        unique_together = [("event", "location")]
```

`source` 필드는 나중에 "어떤 경로로 이 관계가 생겼는가"를 추적할 때 유용하다. 자동 추론된 값을 운영자가 덮어쓴 경우를 구분하거나, 마이그레이션 결과를 감사할 때 활용할 수 있다.

## 기존 데이터 마이그레이션 접근

기존 태그를 `Location`으로 옮길 때, 기존 태그는 source of truth가 아니라 backfill 추론의 입력으로만 취급한다.

문자열 자동 판별보다 명시 매핑을 권장한다.

```python
TAG_TO_LOCATION_CODE = {
    "도쿄": "JP-TOKYO",
    "tokyo": "JP-TOKYO",
    "오사카": "JP-OSAKA",
    # ...
}

def migrate_event_locations(event):
    for tag in event.tags.all():
        code = TAG_TO_LOCATION_CODE.get(tag.name.strip().lower())
        if code:
            location = Location.objects.get(code=code)
            EventLocation.objects.get_or_create(
                event=event,
                location=location,
                defaults={"source": "MIGRATED"},
            )
```

backfill이 끝난 후 새 API와 관리 화면의 계약은 `Location` 기준으로 고정한다. 태그 변경이 지역 API 결과에 영향을 미치는 경로를 차단하는 것이 목표다.

## 트레이드오프

모델을 분리하면 작업량이 늘어난다. 마이그레이션 스크립트, Admin 화면, API 엔드포인트를 새로 만들어야 한다. 기존 코드에서 태그 기반으로 작동하던 필터 쿼리도 수정이 필요하다.

그러나 얻는 것도 명확하다.

- API 계약이 `Location.code` 기준으로 고정되므로, 운영자가 표시명을 바꿔도 API가 흔들리지 않는다.
- 지도 연동, 지역별 통계, 다국어 이름, 계층 구조(국가 > 도시 > 구역) 같은 요구가 생겨도 모델이 준비되어 있다.
- 데이터 소유권이 명확해진다. 지역 정보의 정답은 `Location` 테이블 한 곳에 있다.

## 검증 체크리스트

이 패턴을 적용하거나 리뷰할 때 확인할 항목이다.

- source of truth가 한 곳인가? `Location` 말고 다른 테이블에도 지역 식별자 역할을 하는 필드가 남아 있지 않은가.
- 기존 태그 이름 변경이 지역 API 결과를 깨지 않는가? 태그와 `Location`이 완전히 분리된 이후에도 의존 관계가 남아 있지 않은지 확인한다.
- 마이그레이션 매핑에 누락이 없는가? 매핑되지 않은 태그, 중복 매핑, 비활성 `Location`으로의 연결 등을 검증한다.
- 새 이벤트 생성/수정 경로에서 `Location` 관계가 빠지지 않는가? 태그는 연결하면서 `EventLocation`은 누락되는 경우가 없는지 확인한다.

## 배운 것

빠른 JSON 확장은 MVP 단계에서 유용하다. 그러나 어떤 값이 API 계약의 기준이 되고, 다른 도메인의 식별자로 쓰이기 시작하는 순간, 그것은 더 이상 메타데이터가 아니다. 그 시점에서 모델로 승격하는 것이 나중에 감당해야 할 기술 부채를 줄이는 가장 직접적인 방법이다.
