## 문제 정의

레거시 코드베이스에는 처음 설계할 때 의미가 불분명했던 필드 이름이 남아 있다. 시간이 지나 도메인 이해가 깊어지면 더 명확한 이름으로 바꾸고 싶어지는데, 이미 클라이언트가 기존 이름으로 요청을 보내고 있다면 한 번에 교체하기 어렵다.

예를 들어 `lastOrderClosingDate`라는 필드가 있다고 하자. 팀 내에서는 이 필드가 실제로 "유통사 선주문 마감일"을 뜻한다는 걸 모두 알게 됐고, `distributorPreOrderDeadline`이라는 이름이 훨씬 명확하다는 결론을 냈다. DB와 내부 로직은 새 이름으로 바꿨고, API 응답도 새 이름으로 내려보내기로 했다. 문제는 프론트엔드가 아직 `lastOrderClosingDate`로 요청을 보내고 있다는 것이다.

이런 상황에서 자주 나타나는 실수를 정리한다.

## 경계에서만 호환성을 둔다

`@JsonAlias` 같은 역직렬화 별칭 어노테이션은 JSON 요청을 파싱하는 시점에만 동작한다. 즉 **입력 DTO에만 붙여야 한다**.

```java
public class OrderCreateRequest {
    @JsonAlias("lastOrderClosingDate")
    private LocalDate distributorPreOrderDeadline;
}
```

응답 DTO나 내부 서비스 모델에 레거시 이름을 남기면 안 된다. 그렇게 하면 DB 컬럼, 내부 도메인 객체, API 응답 필드까지 이름이 섞여 어느 것이 현재 표준인지 알 수 없게 된다.

원칙은 단순하다: **호환성은 시스템 경계의 입력 지점에서만 처리하고, 그 안쪽은 새 이름으로 통일한다.**

## 입력 경로를 빠뜨리지 않는다

REST API 엔드포인트만 수정하고 나면 호환성 작업이 끝난 것처럼 느껴진다. 하지만 실제 시스템에는 입력 경로가 여러 개인 경우가 많다.

- JSON 본문으로 단건 생성/수정하는 엔드포인트
- 여러 건을 배열로 받아 일괄 처리하는 엔드포인트 (배열 요소도 같은 DTO를 쓴다면 자동으로 처리되지만, 별도 DTO를 쓴다면 별도로 확인해야 한다)
- Excel이나 CSV를 업로드해서 파싱하는 임포트 경로

Excel 임포트처럼 코드에서 직접 컬럼 헤더를 매핑하는 경우, `@JsonAlias`는 전혀 효과가 없다. JSON 파서를 거치지 않기 때문이다. 헤더 이름을 코드에서 직접 비교한다면 그 비교 로직에서 레거시 헤더도 처리해야 하는지 별도로 판단해야 한다.

입력 경로를 점검할 때 물어볼 것:

- 이 필드를 받는 엔드포인트가 하나인가, 여럿인가
- 각 엔드포인트가 같은 DTO를 쓰는가, 다른 DTO를 쓰는가
- JSON이 아닌 파일 업로드 경로가 있는가

## null / 누락 / clear 정책

별칭을 추가하고 나면 "구 이름과 새 이름이 동시에 들어오면 어떻게 되는가"라는 문제가 생긴다. 대부분의 `@JsonAlias` 구현은 이를 명시적으로 정의하지 않는다. 먼저 파싱된 값이 남거나, 나중 값이 덮어쓰거나, 파서 구현에 따라 달라질 수 있다.

```json
// 요청 본문에 두 이름이 모두 들어온 경우
{
  "distributorPreOrderDeadline": "2026-07-01",
  "lastOrderClosingDate": "2026-08-01"
}
```

어느 값이 적용되는지 보장하는 명세가 없다면, 이를 명시적으로 테스트하거나 정책을 문서화해야 한다. "현재 라이브러리 버전에서 우연히 잘 된다"는 건 정책이 아니다.

업데이트 요청에서는 또 다른 함정이 있다. PUT/PATCH 요청에서 클라이언트가 필드를 **누락**하면 어떻게 처리할지가 명확하지 않은 경우가 많다.

```java
public class OrderUpdateRequest {
    @JsonAlias("lastOrderClosingDate")
    private LocalDate distributorPreOrderDeadline; // null이면 "지우겠다"인가, "건드리지 않겠다"인가?
}
```

필드가 null이라는 건 "이 값을 null로 바꿔라"는 의도일 수도 있고, "이 요청에서 이 필드는 변경하지 않는다"는 의도일 수도 있다. PATCH 시맨틱을 명확히 정의하지 않으면, 프론트엔드 마이그레이션 중 구 이름을 보내던 클라이언트가 새 이름을 생략한 채 요청을 보낼 때 DB 값이 의도치 않게 null로 덮어 써질 수 있다.

## 검증 체크리스트

필드 리네임 작업을 리뷰할 때 확인할 항목이다.

- 레거시 별칭이 **입력 DTO에만** 붙어 있는가 (응답 DTO, 내부 모델에는 없는가)
- JSON 엔드포인트 외에 파일 임포트 등 별도 입력 경로가 있다면, 거기서도 레거시 이름을 처리하는가
- 구 이름과 새 이름이 동시에 요청에 포함될 때 어느 값이 적용되는지 테스트가 있는가
- 업데이트 요청에서 필드 누락과 `null` 전송을 구별하고 있는가
- API 응답과 DB 컬럼에는 레거시 이름이 남아 있지 않은가

## 배운 것

필드 이름을 바꾸는 작업은 작아 보이지만, 입력 경로와 null 시맨틱을 꼼꼼히 따지지 않으면 조용한 버그가 생긴다. 데이터가 의도치 않게 지워지거나, 레거시 이름이 내부 로직 깊숙이 남아 나중에 더 복잡한 마이그레이션을 불러온다.

핵심 원칙은 두 가지다. 첫째, 호환성은 경계에서만, 내부는 새 이름으로 통일한다. 둘째, 별칭이 충돌할 때의 정책을 명시적으로 정의하고 테스트로 고정한다. 이 두 가지를 지키면 이름이 바뀌는 과도기에도 데이터가 안전하게 흐른다.
