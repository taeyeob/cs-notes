## 문제 정의

결제 흐름에는 최종 상태로 수렴하기 전 중간 상태가 존재한다. 예를 들어 결제 시작 후 외부 결제사(이하 PG) 응답을 기다리는 상태(`READY`), 취소 요청 후 PG 취소 처리를 기다리는 상태(`CANCEL_REQUESTED`) 같은 것들이다. 정상 흐름에서는 이 중간 상태가 몇 초 안에 최종 상태로 전환된다.

문제는 이 상태가 예상보다 오래 지속될 때다. PG 콜백이 유실되거나, 취소 task가 큐에서 처리되지 못하거나, 네트워크 장애로 상태 전환이 멈추면 중간 상태에 고착된다. 이 상태를 **장기 정체**라고 부른다.

장기 정체를 탐지하고 운영 알림을 보내는 책임이 어디에 있어야 하는지 처음부터 명확하게 설계하지 않으면, 주문 서버와 결제 서버가 각자 탐지 로직을 중복 구현하거나, 반대로 아무도 탐지하지 않는 공백이 생긴다.

## 위험한 설계

**주문 서버가 결제 상태를 직접 polling한다**

주문 서버가 결제 상태 변화를 직접 확인하기 위해 결제 서버에 주기적으로 조회 API를 호출하는 방식이다. 결제 상태가 한동안 바뀌지 않으면 주문 서버에서 운영 알림을 발송한다.

이 구조의 문제는 결제 상태의 원장이 결제 서버에 있다는 점이다. 주문 서버는 현재 상태가 왜 그 상태인지, 외부 PG 상태와 일치하는지 알 수 없다. "N분째 `CANCEL_REQUESTED`다"는 사실은 주문 서버도 관찰할 수 있지만, 그것이 정말 정체인지 아니면 처리 중인지는 결제 서버만 판단할 수 있다.

**양쪽이 중복으로 탐지한다**

결제 서버도, 주문 서버도 각자 정체 탐지 로직을 갖고 있는 경우다. 임계값이나 알림 조건이 서로 달라서 같은 건에 대해 알림이 두 번 오거나, 한쪽에서 해소된 뒤에도 다른 쪽에서 뒤늦게 알림을 보내는 상황이 생긴다. 운영팀 입장에서는 어느 알림이 최신 정보인지 판단하기 어렵다.

**아무도 탐지하지 않는다**

"결제 서버가 콜백을 받으면 알아서 상태가 바뀌겠지"라는 암묵적인 가정 하에 능동적인 탐지 로직이 없는 경우다. 콜백이 유실되거나 task가 큐에서 사라지면, 장기 정체가 조용히 누적된다. 고객 서비스나 정산 단계에서야 불일치가 드러난다.

## 책임 경계

결제 상태의 원장을 가진 서버가 정체 탐지 책임도 가진다.

```
결제 서버
  ├─ 결제 상태 원장 보유
  ├─ 외부 PG 상태와 직접 대조 가능
  ├─ 지연 task를 통해 정체 여부 판단
  └─ 정체 확정 시 운영 알림 발송

주문 서버
  ├─ 결제 서버 콜백 결과만 반영
  ├─ 직접 결제 상태를 polling하지 않음
  └─ 콜백 처리 과정에서 드러난 이상 케이스에 운영 알림 발송
```

주문 서버가 운영 알림을 보내는 경우는 결제 내부 정체 탐지가 아니라, 콜백 결과를 반영하는 과정에서 드러나는 이상 케이스다. 예를 들어 성공 콜백인데 처리 가능한 주문이 없거나, 취소 실패 확정 콜백을 수신한 경우 등이 해당된다. 콜백 미수신을 감시하는 타임아웃 알림이 별도로 있다면 그것도 이 범주에 속한다. 결제 내부 상태의 정체 여부를 판단하는 것은 결제 서버의 역할이다. 콜백 이상 처리 패턴에 대한 상세한 내용은 별도 글([외부 결제 콜백 ACK 계약과 내부 이상 상태 가시성을 분리하는 법](./payment-callback-ack-observability))을 참고한다.

## 구현 패턴

### 상태 전환 시점에 정체 탐지 task를 예약한다

중간 상태로 진입할 때 지연 task를 함께 예약한다. task가 실행되는 시점에도 아직 중간 상태라면 정체로 판단한다.

```python
# 의사코드
def start_payment(payment_id):
    db.update("UPDATE payment SET status = 'READY' WHERE id = ?", payment_id)
    # 상태 전환과 동시에 정체 탐지 task 예약
    schedule_stuck_check(payment_id, delay=STUCK_THRESHOLD)  # 예: 1시간

def request_cancel(payment_id):
    db.update(
        "UPDATE payment SET status = 'CANCEL_REQUESTED' WHERE id = ? AND status = 'PAID'",
        payment_id
    )
    schedule_stuck_check(payment_id, delay=STUCK_THRESHOLD)
```

임계값(`STUCK_THRESHOLD`)은 정상 처리 시간과 PG 처리 지연 허용 범위를 고려해 시스템마다 조정한다.

### 정체 판단 전에 PG 상태와 대조한다

단순히 "N분째 중간 상태"라는 사실만으로 정체를 확정하지 않는다. 결제 서버는 PG 상태를 직접 조회할 수 있으므로, task 실행 시점에 PG 실제 상태와 대조해 판단한다.

```python
# 의사코드
def check_stuck_payment(payment_id):
    payment = db.get("SELECT * FROM payment WHERE id = ?", payment_id)

    # 이미 최종 상태라면 정체 아님 (정상 처리 완료)
    if payment.status not in INTERMEDIATE_STATES:
        return

    pg_status = pg_client.retrieve(payment.pg_transaction_id)

    if payment.status == "READY" and pg_judge.is_paid(pg_status):
        # 내부는 READY인데 PG는 이미 완료 — 콜백 유실 가능성
        alert_ops("결제 정체: READY 상태이나 PG 완료 확인됨", payment_id)
        # 보정 가능 여부에 따라 자동 완료 전환 또는 수동 판단 알림
        attempt_complete_recovery(payment_id, pg_status)

    elif payment.status == "CANCEL_REQUESTED":
        cancel_result = pg_judge.get_cancel_result(pg_status)

        if cancel_result == "CANCELED":
            # PG에서 이미 취소됨 — 내부 상태 반영
            mark_canceled(payment_id)
        elif cancel_result == "FAILED":
            # PG 취소 실패 확정
            mark_cancel_failed(payment_id, reason="pg_confirmed_fail")
        else:
            # PG도 미결 상태 — 정체로 판단하고 알림
            alert_ops("결제 정체: CANCEL_REQUESTED 장기 미결", payment_id)

    else:
        # 그 외 중간 상태 — 단순 정체 알림
        alert_ops(f"결제 정체: {payment.status} 장기 유지", payment_id)
```

### 주문 서버는 콜백 결과만 반영한다

주문 서버는 결제 서버가 보내는 콜백이 도착할 때만 주문 상태를 갱신한다. 결제 상태가 어떻게 전환됐는지는 주문 서버의 관심사가 아니다. 콜백 페이로드에 담긴 최종 결과(`PAID`, `CANCELED`, `CANCEL_FAILED` 등)를 받아서 주문 상태에 반영하는 것이 전부다.

```python
# 의사코드 (주문 서버)
def handle_payment_callback(payload):
    payment_result = payload["payment_result"]  # PAID | CANCELED | CANCEL_FAILED
    order = find_order_by_payment_id(payload["payment_id"])

    if payment_result == "PAID":
        complete_order(order)
    elif payment_result == "CANCELED":
        cancel_order(order)
    elif payment_result == "CANCEL_FAILED":
        # 취소 실패 확정 — 현재 상태를 보존하고 운영 알림 발송
        # 주문 상태를 즉시 변경하지 않음; 보정 여부는 운영 판단 또는 별도 보정 작업에 위임
        alert_ops("취소 실패 확정 수신", sanitize(payload))

    return success_response()
```

`CANCEL_FAILED`처럼 실패 확정 상태를 콜백으로 수신하는 경우, 주문 서버는 주문 상태를 즉시 성공/취소로 추측 변경하지 않고 현재 상태를 보존한 채 운영 알림을 발송한다. 주문 상태 보정이 필요하다면 이 알림을 트리거로 별도 보정 작업이나 운영 판단 절차를 거친다. 이 알림은 결제 서버의 정체 탐지 알림과 별개의 채널 역할을 한다 — 결제 서버는 "취소가 오래 걸린다"를 알리고, 주문 서버는 "취소가 실패로 확정됐다"를 알린다.

### 멱등성 보장

정체 탐지 task가 큐에서 중복 실행될 수 있으므로, task 실행 시 현재 상태를 재확인한다. 이미 최종 상태로 전환됐다면 중복 알림 없이 종료한다. 알림 발송에도 `payment_id` 기준 dedup을 적용해 동일 건에 대한 알림이 짧은 시간 내에 중복으로 발송되지 않도록 한다.

## 검증 방법

| 시나리오                                 | 탐지 주체 | 기대 동작                                          |
| ---------------------------------------- | --------- | -------------------------------------------------- |
| READY 상태 장기 유지, PG도 미결          | 결제 서버 | 정체 알림 발송                                     |
| READY 상태 장기 유지, PG는 완료          | 결제 서버 | 콜백 유실 알림 + 보정 시도                         |
| CANCEL_REQUESTED 장기 유지, PG 취소 완료 | 결제 서버 | 내부 상태 CANCELED 전환                            |
| CANCEL_REQUESTED 장기 유지, PG 취소 실패 | 결제 서버 | CANCEL_FAILED 전환 + 알림                          |
| CANCEL_FAILED 콜백 수신                  | 주문 서버 | 현재 주문 상태 보존 + 운영 알림 (보정은 별도 판단) |
| 주문 서버 콜백 미수신 (결제 서버 장애)   | 주문 서버 | 콜백 이상 알림 (타임아웃 기준)                     |

핵심 검증 항목은 다음과 같다.

- 중간 상태가 임계값 이전에 최종 상태로 전환되면 정체 task가 실행되더라도 알림을 발송하지 않는가
- PG 상태 대조 결과에 따라 알림 발송, 보정, 실패 확정 분기가 올바르게 실행되는가
- 정체 task가 중복 실행됐을 때 알림이 중복 발송되지 않는가
- 주문 서버가 결제 서버 콜백 없이 결제 상태를 직접 조회하는 경로가 존재하지 않는가

## 배운 것

정체 탐지 책임이 불명확하면 두 가지 방향으로 문제가 생긴다. 주문 서버가 직접 결제 상태를 polling하기 시작하면 결제 서버의 내부 판단 맥락 없이 단순 시간 기준으로만 정체를 판단하게 되고, 이 판단은 종종 틀린다. 반대로 어느 쪽도 탐지하지 않으면 정체가 조용히 누적되다가 정산이나 고객 서비스에서야 드러난다.

원칙은 명확하다. 상태 원장을 소유한 서버가 그 상태의 정체를 탐지한다. 결제 서버는 PG 상태와 직접 대조할 수 있는 유일한 주체이므로, 정체 여부 판단도 결제 서버에 위치해야 한다. 주문 서버는 결제 서버가 최종 판단한 결과를 콜백으로 받아 반영하는 역할에 머문다.

구현 측면에서는 두 가지가 중요하다. 첫째, 정체 탐지를 단순 시간 기준이 아니라 PG 상태 대조로 확인한다. "N분째 중간 상태"와 "N분째 중간 상태인데 PG도 같은 상태"는 다른 의미다. 둘째, 정체 탐지 task와 콜백 처리는 멱등하게 설계한다. 어느 쪽이 먼저 도착하더라도 최종 상태가 같아야 하고, 중복 실행에도 알림이 중복 발송되지 않아야 한다.
