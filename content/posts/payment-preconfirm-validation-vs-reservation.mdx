## 문제 정의

주문 시스템에서 수량 제한이 있는 상품을 판매할 때, 결제 승인 직전에 현재까지 판매된 수량을 집계해 한도를 초과하지 않는지 확인하는 검증 단계를 둔다. 이 검증은 직관적으로 필요하고 실제로 유용하다.

문제는 이 검증이 단일 요청에서는 올바르게 동작하더라도, 두 요청이 동시에 들어오면 둘 다 검증을 통과해 제한을 초과하는 상황이 발생할 수 있다는 것이다.

나아가 검증 로직을 어느 서비스가 소유해야 하는지, 현재 진행 중인 주문을 집계에 어떻게 포함해야 하는지, 동기 confirm형 결제와 비동기/자동매입형 결제에서 각각 어느 시점에 제어해야 하는지도 함께 설계해야 한다.

## 경쟁 시나리오: TOCTOU

**TOCTOU(Time-Of-Check Time-Of-Use)** 경쟁은 검증 시점과 실행 시점 사이에 상태가 바뀌는 패턴이다. 수량 제한 검증에서는 다음과 같이 발생한다.

```
시각   요청 A (수량 1)               요청 B (수량 1)      잔여 한도: 1
─────────────────────────────────────────────────────────────────
t1     현재 판매량 조회 → 잔여 1
t2                                   현재 판매량 조회 → 잔여 1
t3     검증 통과 → 결제 승인 요청
t4                                   검증 통과 → 결제 승인 요청
t5     승인 완료 → 주문 확정
t6                                   승인 완료 → 주문 확정  ← 한도 초과
```

t1과 t2에서 두 요청 모두 잔여가 1이라고 읽는다. 검증을 각자 통과하고, 결국 두 주문이 모두 확정된다. 검증 로직 자체는 틀리지 않았지만, 읽은 값과 실제 쓰기 사이 시간 간격이 문제다.

단일 서버, 단일 DB에서도 동시 요청이 같은 스냅샷을 읽으면 이 경쟁은 발생한다. 트래픽이 많을수록, 결제 승인 응답 시간이 길수록 경쟁 창이 넓어진다.

## 검증 로직 소유권: 정책 데이터가 있는 서비스

수량 제한 정책(최대 수량, 1인당 구매 제한, 기간 등)이 어느 서비스에 있는지에 따라 검증 판정 책임도 달라진다. 주문 서비스가 결제 서버에 단순히 "결제를 승인해 달라"고 요청하는 구조에서, 정책과 현재 판매량 데이터를 가진 쪽이 주문 서비스라면 판정도 주문 서비스가 한다. 결제 서버는 정책을 모르므로 한도 초과 여부를 올바르게 판단할 수 없다.

반대로 수량 원장이 별도 재고 서비스에 있다면, 재고 서비스가 판정을 소유하고 주문/결제 서비스는 재고 서비스의 응답에 따라 진행 여부를 결정한다.

판정을 정책 데이터가 없는 서비스에 두면, 두 서비스의 데이터를 교차 조회해 판단하는 복잡한 경로가 생기고 이 경로 자체가 경쟁 조건에 노출된다.

## 현재 주문 집계의 이중 합산 문제

검증 시점에 현재 진행 중인 주문(CREATED, PENDING 등)을 집계에 포함할 때 이중 합산이 발생하는 패턴이 있다.

### 방식 A: 현재 주문을 포함해 집계하고 총합과 제한 비교

현재 요청 중인 주문도 이미 PENDING 상태로 DB에 존재한다고 가정하면, 모든 PENDING/CREATED 주문을 집계에 포함하고 그 합계를 제한과 비교한다.

```sql
-- 방식 A
SELECT SUM(quantity)
FROM orders
WHERE product_id = ? AND status IN ('CREATED', 'PENDING', 'PAID')
```

```
집계 합계 > limit   →  거절
집계 합계 <= limit  →  통과
```

이 방식에서 현재 주문은 집계에 이미 포함되어 있으므로 추가로 더하면 안 된다.

### 방식 B: 현재 주문을 제외해 집계하고 요청 수량을 더해 비교

현재 요청 중인 주문은 아직 DB에 없거나, 집계 대상에서 의도적으로 제외한다. 그 대신 요청 수량을 별도로 더해서 예상 합계를 계산한다.

```sql
-- 방식 B: 현재 주문(order_id = ?)을 제외
SELECT SUM(quantity)
FROM orders
WHERE product_id = ? AND status IN ('CREATED', 'PENDING', 'PAID')
  AND id != ?  -- 현재 주문 제외
```

```
(집계 합계 + 요청 수량) > limit  →  거절
(집계 합계 + 요청 수량) <= limit →  통과
```

### 이중 합산이 발생하는 경우

두 방식을 섞으면 이중 합산이 발생한다. 현재 주문이 집계에 포함된 상태(방식 A의 SQL)에서 요청 수량을 추가로 더하면(방식 B의 비교 로직), 현재 주문 수량이 두 번 계산된다.

```
잘못된 예시:
집계 = SUM(CREATED + PENDING + PAID)  ← 현재 주문 포함
비교 = (집계 + 요청 수량) > limit    ← 현재 주문을 또 더함
→ 현재 주문 수량이 두 번 반영됨
```

어느 방식을 쓰든 일관되게 적용해야 한다. 집계 SQL과 비교 로직을 동시에 수정할 때 이 일관성이 깨지기 쉽다.

## Validation과 Reservation/Claim의 차이

### Validation의 한계

앞서 본 TOCTOU 경쟁에서 알 수 있듯, 검증(validation)은 검증 시점의 스냅샷을 기준으로 판단한다. 검증 통과와 실제 승인 사이에 상태가 바뀌어도 이를 막지 못한다.

CREATED/PENDING 주문을 점유 프록시로 활용하는 아이디어는 자연스럽지만, 상태를 생성하는 것만으로는 충분하지 않다. capacity check와 해당 상태 생성 사이에도 경쟁 창이 존재하기 때문이다. 이 구간을 닫으려면 모든 경쟁 요청이 공통으로 잠글 수 있는 안정된 행(product, capacity, counter 등)을 먼저 잠근 뒤, 같은 트랜잭션 안에서 현재 점유량을 계산하고 PENDING 레코드를 생성하거나 카운터를 조건부 갱신하는 방식으로 check+write를 직렬화해야 한다.

PostgreSQL 등 일반 관계형 DB에서 aggregate 쿼리에 `FOR UPDATE`를 직접 붙이는 것은 지원되지 않거나 의도한 잠금 범위와 다르게 동작할 수 있다. 올바른 패턴은 안정된 공통 행을 먼저 잠근 뒤 같은 트랜잭션 안에서 집계하는 것이다.

```sql
-- 안정된 공통 행을 먼저 잠근 뒤 집계하는 올바른 패턴
BEGIN;
-- 모든 경쟁 요청이 같은 행을 잠금 → 직렬화 지점
SELECT id FROM product_capacity WHERE product_id = ? FOR UPDATE;
-- 같은 트랜잭션 안에서 현재 점유량 계산
SELECT SUM(quantity)
FROM orders
WHERE product_id = ? AND status IN ('CREATED', 'PENDING', 'PAID');
-- 한도 초과 여부 판정 후 조건 충족 시 PENDING 레코드 생성 또는 카운터 갱신
INSERT INTO orders (...) VALUES (...);
COMMIT;
```

이 방식도 두 트랜잭션이 같은 product_capacity 행을 잠그려 하면 하나가 대기하므로 처리량에 영향을 준다. 트래픽이 높은 경우 카운터 테이블에 조건부 UPDATE를 사용하는 방식(업데이트 성공 여부로 claim 판정)을 고려한다.

### 재고가 외부 원장에 있을 때: Reservation/Claim

실제 재고 숫자가 별도 재고 서비스나 원장에 관리된다면, 주문 서비스의 상태 집계만으로는 강한 보장이 어렵다. 이 경우 재고 원장에 **멱등한 reservation/claim** 이 있어야 한다.

재고 원장이 별도 서비스라면, `inventory.claim(...)` API 자체가 원장 내부 트랜잭션에서 capacity check와 claim 영속화를 원자적으로 수행하고, 커밋된 결과만 호출자에게 응답한다. 호출자는 별도 DB lock을 보유하지 않는다. 같은 DB를 공유하는 경우에만 앞 절의 공통 행 lock 트랜잭션 패턴을 사용할 수 있다.

올바른 호출자 흐름은 claim API 성공 응답(원장 내부 commit 완료) → PG confirm(호출자 DB lock 없음) → 멱등 finalize/release API 호출이다. 외부 PG 호출은 원장 상태 전이 경계 밖에서 수행하므로 DB 행 잠금이 지속되지 않는다. finalize/release도 멱등하게 설계하고, 호출 실패 시 같은 키로 재시도할 수 있는 durable 상태나 outbox가 필요하다.

```
# Reservation/Claim 흐름 (saga형 의사코드)
def handle_payment_preconfirm(order_id, product_id, quantity):
    # 단계 1: claim API — 원장 내부 트랜잭션에서 capacity check + 영속화 후 커밋 결과만 응답
    result = inventory.claim(
        product_id=product_id,
        quantity=quantity,
        idempotency_key=order_id
    )
    if result.status == "FAILED":
        raise InsufficientStockError()
    # claim commit 완료 (원장 내부). 호출자 DB lock 없음

    # 단계 2: 호출자 DB lock 없이 PG confirm 호출
    try:
        payment_result = payment_gateway.confirm(order_id)
    except PaymentGatewayTimeout:
        # timeout: 결과 불명확 → 즉시 release 금지
        # 같은 idempotency key로 PG 상태 조회/재시도 후 판정
        raise PaymentResultUncertainError()

    # 단계 3: 멱등 finalize 또는 release API 호출
    # 호출 실패 시 같은 key로 재시도 가능한 durable 상태 또는 outbox 필요
    if payment_result.failed:
        inventory.release_claim(order_id)
        raise PaymentFailedError()
    inventory.finalize_claim(order_id)
```

**timeout 불확실 결과 처리:** confirm 호출 중 timeout이 발생하면 결과를 알 수 없는 상태다. 이때 곧바로 claim을 release하면 PG에서 이미 승인이 완료된 경우 재고를 돌려준 채 결제는 성공한 모순 상태가 생긴다. 같은 idempotency key로 PG 상태를 조회하거나 재시도해서 성공/실패가 확정됐을 때만 finalize 또는 release를 결정한다.

claim은 재고 원장에 원자적으로 수량을 점유하므로, 두 요청이 동시에 claim을 시도하면 재고 원장이 직렬화해서 하나만 성공시킨다. 이것이 validation과의 핵심 차이다. validation은 읽기 기준 판단이고, claim은 쓰기 기준 직렬화다.

claim 재시도를 안전하게 하려면 멱등 키(order_id 등)를 사용해 같은 order에 대한 중복 claim이 추가 차감 없이 같은 결과를 반환하도록 설계한다.

## 결제 유형별 제어 지점

수량 제한 검증의 위치와 claim 시점은 결제 유형에 따라 다르다.

### 동기 confirm형 PG

동기 confirm형은 서버에서 PG confirm API를 직접 호출해 즉시 응답을 받는 구조다. 제어 흐름이 서버 내에 있으므로, claim 성공 이후 confirm 호출이라는 순서를 명확하게 지킬 수 있다.

```
[클라이언트] → [주문 서버: claim 시도]
                        ↓ 성공
               [주문 서버: PG confirm 호출]
                        ↓ 성공
               [주문 서버: 주문 확정, claim finalize]
                        ↓ 실패
               [주문 서버: claim 해제]
```

confirm 응답이 동기적으로 돌아오므로, claim commit → PG confirm 호출 → finalize 또는 release라는 애플리케이션 흐름의 순서를 명확하게 지킬 수 있다. 단, 각 단계(claim, finalize, release)는 재고 원장 내부의 독립된 멱등 상태 전이이며, 외부 PG 호출은 원장 상태 전이 경계 밖에서 수행한다.

### 비동기/자동매입형 PG

비동기/자동매입형은 클라이언트가 PG 결제창으로 이동하고, 사용자 결제 완료 후 PG가 웹훅 또는 콜백으로 결과를 전달하는 구조다. 결제 승인 자체는 PG 내부에서 발생하므로, 서버가 개입할 수 있는 시점이 제한된다.

**결제창 진입 전에 claim을 만드는 경우:**

```
[클라이언트: 결제창 진입 요청]
        ↓
[주문 서버: claim 시도]
        ↓ 성공
[주문 서버: 결제창 URL 반환]
        ↓
[클라이언트 → PG 결제창]
        ↓ 완료 (웹훅)
[주문 서버: claim finalize]
        ↓ 실패/취소 (웹훅 또는 타임아웃)
[주문 서버: claim 해제]
```

결제창 진입 전에 claim을 만들면 수량 제어 지점이 생기지만, 사용자가 결제창에서 이탈하거나 결제를 취소하는 경우 claim을 해제하는 TTL 또는 명시적 해제 정책이 필요하다. claim이 해제되지 않으면 점유된 수량이 계속 잠기므로 판매 기회를 잃는다.

단, TTL 단순 시간 만료만으로 claim을 release해서는 안 된다. TTL이 만료되더라도 외부 승인 결과가 불명확한 동안에는 claim을 유지해야 한다. 안전한 만료 조건은 TTL 만료 전 PG 세션이 취소 또는 만료되어 이후 승인이 불가능함을 확인했거나, 결제 세션 최대 수명보다 TTL을 길게 설정하고 PG 상태 조회·갱신을 연동한 경우다. 승인 결과가 불명확한 상태에서 claim을 해제하면, 이후 PG 승인이 확정될 때 재고 없이 결제가 완료되는 상태가 발생한다.

**결제창 진입 전 제어 지점이 없는 경우:**

PG 연동 구조 또는 레거시 설계로 결제창 진입 전에 claim을 만들 수 있는 시점이 없다면, 수량 검증을 결제 완료 이벤트 수신 후에 할 수밖에 없다. 이 경우 이미 PG 승인이 완료된 결제를 검증하는 것이므로, 한도를 초과한 것을 발견하더라도 **보상 취소(compensation cancel)** 를 통해 되돌려야 한다. 이것은 사전 차단이 아니라 사후 보정이다.

```
[PG 완료 이벤트 수신]
        ↓
[주문 서버: 수량 검증]
        ↓ 초과 감지
[주문 서버: PG 취소 요청 → 보상 취소]
```

보상 취소는 이미 결제를 완료한 고객에게 환불을 발생시키므로, 고객 경험과 운영 비용 측면에서 사전 차단보다 훨씬 비싸다. 보상 취소가 가능한 구조를 갖추는 것은 최후의 안전망으로서 의미가 있지만, 이것을 주된 수량 제어 수단으로 삼는 것은 설계 선택이 아니라 강제된 제약에 가깝다. 보상 취소 설계에 대한 세부 내용은 [외부 결제 취소에서 멱등성과 PG 상태 조회 보정을 함께 설계하는 법](./payment-cancel-compensation-idempotency)을 참고한다.

## Fail-Closed와 일시 장애 구분

수량 검증 또는 claim 호출이 실패하는 경우 두 가지 원인을 구분해야 한다.

**한도 초과(정책적 거절):** claim이 재고 부족을 이유로 실패했다면 결제를 진행하지 않는다. 이것은 정상적인 비즈니스 거절이며 재시도해도 결과가 바뀌지 않는다.

**인프라 timeout(일시 오류):** 재고 서비스가 응답하지 않거나 네트워크 오류로 claim 결과를 알 수 없는 경우다. 이때는 아직 승인하지 않은 상태이므로, 같은 멱등 키를 사용해 제한적으로 재시도할 수 있다. 강한 수량 보장을 목표로 한다면 재시도를 모두 소진한 뒤에도 결과를 알 수 없는 경우 fail-open(결제 통과)으로 승인하지 않는다.

```
# fail-closed 예시 (의사코드)
def claim_stock(product_id, quantity, idempotency_key):
    try:
        return inventory_service.claim(product_id, quantity, idempotency_key)
    except InventoryServiceUnavailable:
        # 인프라 오류: 아직 승인하지 않은 상태
        # 같은 멱등 키로 제한적 재시도 후 소진 → fail-closed, 결제 차단
        raise PaymentBlockedDueToInventoryError()
    except InsufficientStock:
        # 정책적 거절 (재시도 불필요)
        raise InsufficientStockError()
```

fail-closed를 선택하면 인프라 장애 시 판매가 멈춘다. fail-open(장애 시 통과)을 선택하면 판매는 이어지지만 재고 초과 위험이 생긴다. fail-open은 초과 판매를 감수하는 별도 정책을 명시적으로 결정했을 때만 선택 가능하며, 그것은 강한 수량 보장을 포기하는 선택이다. 상품 유형(한정 수량인지, 무한 공급인지)과 보상 취소 처리 능력에 따라 정책을 명시적으로 결정하고 코드에 표현해야 한다. 암묵적인 fail-open은 설계 선택이 아니라 버그로 이어진다.

## 동시성 검증 테스트 매트릭스

검증 로직과 claim 흐름이 올바르게 동작하는지는 단위 테스트만으로는 부족하다. 동시 요청 시나리오를 명시적으로 작성해야 한다.

| 시나리오                        | 입력                                                 | 기대 결과                                                                  |
| ------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------------- |
| 순차 요청, 한도 내              | 요청 A(수량 1) → 요청 B(수량 1), 한도 3              | 둘 다 통과                                                                 |
| 순차 요청, 한도 초과            | 요청 A(수량 2) → 요청 B(수량 2), 한도 3              | A 통과, B 거절                                                             |
| 동시 요청, 정확히 한도          | 요청 A(수량 1), 요청 B(수량 1) 동시, 한도 1          | 정확히 하나만 통과                                                         |
| 동시 요청, 합산 초과            | 요청 A(수량 2), 요청 B(수량 2) 동시, 한도 3          | 정확히 하나만 통과                                                         |
| claim 후 결제 실패              | claim 성공 → confirm 실패                            | claim 해제, 수량 복원                                                      |
| claim 중복 (같은 order_id)      | 동일 order_id로 claim 두 번                          | 두 번째는 멱등 응답, 추가 차감 없음                                        |
| 재고 서비스 장애                | claim 호출 중 timeout                                | 승인 보류, 같은 멱등 키로 재시도, 소진 시 차단                             |
| 이중 합산 회귀                  | 방식 A/B 중 하나 선택 후 집계 SQL과 비교 로직 일관성 | 현재 주문 수량이 한 번만 계산됨                                            |
| claim TTL 만료와 늦은 승인 경합 | TTL 만료 직전/직후 PG 승인 완료                      | claim 유지 또는 갱신, 늦은 승인이 가능한 동안 release 금지, 보상 경로 필요 |

동시 요청 테스트는 실제로 두 스레드나 두 프로세스를 동시에 실행하거나, claim 함수 내부에 인위적인 지연을 삽입해서 TOCTOU 창을 만들어 검증한다.

## 트레이드오프

**검증만 두는 경우:** 구현이 단순하다. 트래픽이 낮거나 한도 초과가 드문 상품이라면 충분할 수 있다. 그러나 동시 요청이 많아지면 TOCTOU 경쟁이 현실화된다. 사후 보상 취소 체계가 갖춰져 있다면 허용 가능한 선택이다.

**DB 행 잠금으로 검증 직렬화:** 재고 원장이 별도 시스템에 없고 주문 DB가 단일 원장인 경우 적용 가능하다. 처리량 상한이 생기므로 트래픽이 높은 시간대에 병목이 될 수 있다.

**재고 서비스에 claim 위임:** 재고 원장 분리가 명확하고 강한 일관성 보장이 필요한 경우 적합하다. 재고 서비스가 추가 의존성이 되고, 해당 서비스 장애가 결제 흐름에 전파된다. 서비스 간 트랜잭션이 없으므로 claim과 결제 승인 사이 실패 복구(해제) 로직이 별도로 필요하다.

**비동기/자동매입형에서 사전 claim:** TTL 기반 해제 정책 설계가 추가로 필요하다. claim이 걸린 채 만료되지 않으면 재고가 잠겨 판매 기회를 잃는다. TTL이 너무 짧으면 결제창에서 오래 머무는 사용자의 claim이 만료된다.

## 배운 것

수량 제한 검증을 처음 설계할 때 가장 흔한 실수는 "단일 요청에서 올바르게 동작한다"는 사실을 "동시 요청에서도 올바르게 동작한다"와 동일시하는 것이다. 검증 로직 자체의 정확성과 동시 요청 간 격리는 별개의 문제다.

설계 교훈을 정리하면 다음과 같다.

1. **TOCTOU는 검증 로직이 틀린 게 아니다.** 검증 통과와 상태 반영 사이의 간격이 문제다. 이 간격을 없애려면 읽기-검증-쓰기를 원자적으로 묶거나, 별도 claim 단계를 둬야 한다.

2. **정책 데이터가 있는 서비스가 판정을 소유한다.** 정책이 없는 서비스가 판정을 시도하면 필연적으로 교차 조회와 추가 경쟁 조건이 생긴다.

3. **집계 방식(A 또는 B)을 하나만 일관되게 적용한다.** SQL과 비교 로직을 별도로 수정할 때 이중 합산이 끼어드는 경우가 많다. 변경 시 반드시 함께 검토한다.

4. **결제 유형이 제어 지점을 결정한다.** 동기 confirm형은 claim → confirm 순서를 서버 흐름 안에서 보장할 수 있다. 비동기/자동매입형은 결제창 진입 전이 유일한 서버 제어 지점이며, 그마저 없으면 보상 취소가 유일한 경로다.

5. **보상 취소는 최후의 안전망이다.** 사후 보상이 가능한 체계를 갖추는 것은 중요하지만, 이것을 주된 수량 제어 수단으로 설계하면 고객 경험과 운영 비용 모두 커진다.

6. **장애와 정책적 거절을 코드에서 명확히 분리한다.** 둘 다 claim 실패로 보이지만 재시도 여부와 fail 동작이 다르다. 암묵적으로 한쪽을 다른 쪽처럼 처리하면 예상치 못한 결과가 생긴다.

7. **비동기 claim의 TTL은 PG 세션 생존 여부를 확인한 뒤 만료한다.** TTL 단순 시간 만료만으로 claim을 release하면, TTL 만료 직후 PG 승인이 확정될 때 재고 없이 결제가 완료되는 경합이 생긴다. 늦은 승인이 가능한 동안에는 claim을 유지·갱신하거나, PG 세션이 취소·만료됐음을 확인한 뒤에만 release한다. 이 확인이 불가능하면 결제 세션 최대 수명보다 TTL을 충분히 길게 설정하고 상태 조회·갱신을 연동해야 한다.
