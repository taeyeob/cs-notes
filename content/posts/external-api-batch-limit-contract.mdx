## 문제 정의

아이템 그룹에 새 항목 120개를 한 번에 연결하는 작업이 있다고 하자. 작업을 실행했을 때 완료 메시지가 표시됐고, 오류 로그도 없었다. 그런데 실제로 연결된 항목 수를 세어보면 100개뿐이다.

원인은 내부 코드가 외부 아이템 조회 API를 호출할 때 한 요청에서 최대 100개만 반환된다는 제약을 처리하지 않았기 때문이다. 120개 ID를 요청해도 API는 100개만 돌려줬고, 코드는 그 100개만 연결했다. 나머지 20개는 오류 없이 조용히 누락됐다.

이것이 문제의 핵심이다. 외부 API의 페이지 제한(page size)은 API 제공자의 인프라·과금 제약이다. 이 제한이 내부 비즈니스 로직의 상한이 되어서는 안 된다. 하지만 조회 결과를 검증하지 않으면 그 제한이 내부 도메인 불변식으로 흡수된다.

## 실패 메커니즘

요청부터 저장까지 흐름을 단계별로 추적하면 어디서 문제가 생기는지 드러난다.

```
1. 운영자가 아이템 ID 120개를 그룹에 연결 요청
2. 내부 코드: items = external_api.lookup(ids=120_ids, size=100)
3. 외부 API 응답: 최대 100개만 반환 (나머지 20개는 응답에 없음)
4. 내부 코드: 반환된 100개에 대해서만 연결 생성
5. 결과: 20개 아이템 누락, 오류 없음
```

응답 코드는 200이고, 반환된 목록 자체도 올바른 데이터다. "일부가 빠진 올바른 응답"이 문제다. 요청한 수와 반환된 수를 비교하지 않는 한 이 차이는 코드에서 보이지 않는다.

### 왜 테스트에서 발견되지 않았는가

테스트를 최근에 추가한 아이템 1개 또는 소수로만 작성하면 이 버그를 재현하기 어렵다.

최근 생성된 아이템은 API 응답에서 상위(최신 순 정렬)에 포함될 가능성이 높다. 1개를 요청할 때 그 항목이 첫 100개 안에 들어오면 테스트는 통과한다. 100개 제한을 초과하는 배치를 테스트하지 않으면 버그가 보이지 않는 것이다.

실패를 재현하려면 기존에 그룹과 연결된 적 없는 아이템을 PAGE_SIZE를 초과하는 개수로 요청해야 한다. 최근 아이템이 아니라 오래된 아이템을 포함한 배치, 또는 충분히 많은 수의 아이템이 픽스처에 있어야 한다.

## 위험한 구현 패턴

```python
def link_items_to_group(group_id, item_ids):
    # 위험: API 응답 개수가 요청 개수와 같다고 암묵적으로 가정한다
    items = external_api.lookup_items(ids=item_ids, size=100)
    for item in items:
        create_link(group_id, item.id)
    return len(items)
```

문제가 세 곳에 있다.

- 요청한 ID 수와 반환된 아이템 수를 비교하지 않는다.
- 반환되지 않은 ID가 "존재하지 않는 항목"인지 "페이지 제한으로 잘린 항목"인지 구분하지 않는다.
- `len(items)`를 성공 건수로 반환해 호출자가 전체 처리가 완료됐다고 오해할 수 있다.

## 올바른 설계: 청크 분할·전체 집계·반환 ID 대조

세 단계로 나눈다.

**1단계 — 청크 분할**: 요청 ID를 API의 최대 허용 개수 단위로 나눈다.  
**2단계 — 전체 집계**: 각 청크에서 반환된 아이템을 하나의 집합으로 합산한다.  
**3단계 — 반환 ID 대조**: 요청한 ID 집합과 집계된 ID 집합을 비교해 누락 항목을 확인한다.

### ID 기반 필터링 API

외부 API가 ID 목록을 받아 해당 항목만 반환하는 경우.

```python
PAGE_SIZE = 100

def lookup_all_items(item_ids):
    """
    외부 API를 청크 단위로 호출해 모든 아이템을 조회한다.
    반환값: (found: dict[id -> item], missing_ids: set)
    """
    requested = set(item_ids)
    found = {}

    chunks = [
        item_ids[i : i + PAGE_SIZE]
        for i in range(0, len(item_ids), PAGE_SIZE)
    ]

    for chunk in chunks:
        result = external_api.lookup_items(ids=chunk, size=PAGE_SIZE)
        for item in result:
            found[item.id] = item

    missing_ids = requested - set(found.keys())
    return found, missing_ids


def link_items_to_group(group_id, item_ids):
    found, missing_ids = lookup_all_items(item_ids)

    if missing_ids:
        raise ValueError(
            f"외부 API에서 {len(missing_ids)}개 아이템을 찾을 수 없습니다: {missing_ids}"
        )

    for item in found.values():
        create_link(group_id, item.id)

    return len(found)
```

### 커서 페이지네이션 API

외부 API가 ID 필터링을 지원하지 않고 전체 목록을 페이지 단위로 순차 반환하는 경우, 목표 ID가 모두 발견되거나 다음 페이지가 없을 때까지 순회한다.

```python
def lookup_all_items_cursor(target_ids):
    """
    커서 페이지네이션 API에서 목표 ID가 모두 발견될 때까지 순회한다.
    """
    target = set(target_ids)
    found = {}
    cursor = None

    while True:
        result = external_api.list_items(size=PAGE_SIZE, cursor=cursor)
        for item in result.items:
            if item.id in target:
                found[item.id] = item

        if not result.has_next or len(found) == len(target):
            break
        cursor = result.next_cursor

    missing_ids = target - set(found.keys())
    return found, missing_ids
```

커서 방식은 목표 ID가 뒤쪽 페이지에 있을 경우 API를 많이 호출하게 된다. 총 호출 횟수 상한을 사전에 추정하고 필요 시 타임아웃을 별도로 설정한다.

## 테스트 전략

```python
import pytest

def test_link_exactly_page_size_items(group):
    """경계값: PAGE_SIZE개 요청 시 전부 연결된다."""
    item_ids = create_items(count=100)
    result = link_items_to_group(group.id, item_ids)
    assert result == 100
    assert count_links(group.id) == 100


def test_link_page_size_plus_one(group):
    """경계값: PAGE_SIZE + 1개 요청 시 전부 연결된다."""
    item_ids = create_items(count=101)
    result = link_items_to_group(group.id, item_ids)
    assert result == 101
    assert count_links(group.id) == 101


def test_link_over_page_size_items(group):
    """핵심: PAGE_SIZE를 크게 초과해도 전부 연결된다."""
    item_ids = create_items(count=120)
    result = link_items_to_group(group.id, item_ids)
    assert result == 120
    assert count_links(group.id) == 120


def test_missing_ids_are_reported(group, mocker):
    """누락 ID는 예외로 명시적으로 전달되며 조용히 무시되지 않는다."""
    # 외부 API가 특정 ID를 반환하지 않는 동작을 모의 (페이지 제한이 아닌 실제 누락)
    MISSING_ID = 42
    mocker.patch(
        "myapp.external_api.lookup_items",
        side_effect=lambda ids, size: [make_item(id=i) for i in ids if i != MISSING_ID],
    )
    item_ids = list(range(120))
    with pytest.raises(ValueError, match="1개 아이템을 찾을 수 없습니다"):
        link_items_to_group(group.id, item_ids)
```

**테스트 픽스처 대표성**

단일 테스트에서 최근 아이템 1개만 대상으로 하면 그 항목이 API 응답의 상위 100개 안에 포함될 가능성이 높아 실패를 재현하지 못한다. 다음 기준으로 픽스처를 구성한다.

- PAGE_SIZE(100개), PAGE_SIZE+1(101개), 그 이상(120개) 세 케이스를 각각 독립 테스트로 작성한다.
- 누락 ID 보고 테스트에서는 특정 ID를 반환하지 않는 방식으로 모의해, 페이지 제한이 아닌 실제 누락 케이스를 재현한다.
- 회귀 테스트는 고정 픽스처로 두어 API 응답 정렬 순서 변경에 영향받지 않도록 한다.

## 트레이드오프

| 항목          | 단일 호출 (청크 없음)         | 청크 분할 + 전체 집계      |
| ------------- | ----------------------------- | -------------------------- |
| API 호출 횟수 | 1회                           | ⌈N / PAGE_SIZE⌉ 회         |
| 지연 시간     | 짧음                          | 청크 수에 비례해 증가      |
| 정확성        | 페이지 제한 초과 시 누락 발생 | N개 전체 조회 보장         |
| 누락 감지     | 없음 (silent failure)         | 반환 ID 대조로 명시적 탐지 |
| 구현 복잡도   | 낮음                          | 청크·집계·대조 로직 추가   |

**부분 실패 처리**

여러 청크 중 일부가 실패하면 성공한 청크만 반영할지, 전체를 롤백할지 결정해야 한다. 아이템 연결은 원자적으로 처리하는 것이 안전하다. 한 청크라도 오류가 발생하면 전체 작업을 취소하고 재시도 가능한 상태로 남기는 방식을 기본으로 선택한다.

**레이트 리밋과 백오프**

청크를 연속으로 요청하면 레이트 리밋에 걸릴 수 있다. 청크 단위 호출에 지수 백오프와 최대 재시도 횟수를 설정한다.

```python
import time

def lookup_with_backoff(chunk, max_retries=3):
    for attempt in range(max_retries):
        try:
            return external_api.lookup_items(ids=chunk, size=PAGE_SIZE)
        except RateLimitError:
            if attempt == max_retries - 1:
                raise
            time.sleep(2 ** attempt)
```

**API 지원 방식에 따른 선택**

외부 API가 ID 기반 필터링을 지원하면 청크 분할 방식이 단순하고 예측 가능하다. 커서 페이지네이션만 지원하면 전체 목록을 순회해야 하므로 호출 횟수가 늘어난다. 어느 방식이든 "요청한 수 == 반환된 수"를 가정하지 않는다는 원칙은 동일하다.

## PR 설명에 사용자 가시적 현상을 명시한다

코드 변경 사유가 "size 파라미터 수정"이나 "청크 처리 추가"로만 기술되면, 리뷰어나 추후 유지보수자가 이 변경이 왜 중요한지 파악하기 어렵다.

PR 설명에는 사용자가 경험한 현상을 명시한다.

```
Before: 아이템 120개를 그룹에 연결 요청 → 100개만 연결됨 (20개 누락, 오류 없음)
After:  아이템 120개를 그룹에 연결 요청 → 120개 모두 연결됨
```

이렇게 명시해야 "왜 이 경계값 테스트가 있는가"가 코드 리뷰 시점에 자명해지고, 회귀 방지 테스트가 추가된 이유도 남는다.

## 배운 것

외부 API의 페이지 제한은 외부 제약이다. 코드가 이 제한을 처리하지 않으면 그것이 내부 도메인 불변식이 된다. "100개 이하만 연결 가능"이라는 규칙이 생기는 것이다. 이 규칙은 코드 어디에도 명시되지 않고, 오류 메시지로도 나타나지 않는다.

설계 원칙 세 가지를 정리한다.

**요청 ID와 반환 ID를 항상 대조한다.** 반환 수가 요청 수보다 적을 때 "일부 항목이 존재하지 않는 정상 케이스"와 "페이지 제한으로 잘린 비정상 케이스"를 코드에서 구분해야 한다. 구분할 수 없다면 차이가 생겼다는 사실만이라도 예외나 경고로 명시한다.

**청크 단위 조회를 기본 추상화로 둔다.** 호출자가 아이템 수를 신경 쓰지 않아도 전체 결과를 받을 수 있도록 조회 레이어에서 청크 분할과 집계를 처리한다. `size=100` 같은 API 제약이 비즈니스 로직 레이어까지 올라오면 그 순간 외부 제약이 내부 계약이 된다.

**테스트는 PAGE_SIZE 이상의 배치 크기를 반드시 포함한다.** 최근 아이템 1개로만 테스트하면 첫 100개 안에 들어가 실패를 재현하지 못한다. `PAGE_SIZE`, `PAGE_SIZE+1`, 그 이상 세 케이스를 독립 테스트로 고정한다. 이 테스트들이 PAGE_SIZE가 변경되거나 API 스펙이 바뀔 때 가장 먼저 실패 신호를 보낸다.
