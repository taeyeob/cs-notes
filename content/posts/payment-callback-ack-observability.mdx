## 문제 정의

PG(결제대행사)에서 결제 성공 콜백이 수신됐다. 그런데 내부 DB를 조회해 보면 해당 `payment_request_id`에 매핑되는 처리 가능한 주문이 없다.

정확히는 세 가지 경우로 나뉜다.

1. **정상 경로**: 주문이 존재하고 대기(PENDING) 상태다 — 결제 완료로 전환하고 200 응답을 반환한다.
2. **중복 콜백**: 주문이 이미 완료(PAYMENT_COMPLETED) 상태다 — 멱등 처리로 조용히 200을 반환하고 알림은 보내지 않는다.
3. **이상 상태**: 주문이 없거나 취소·실패 등 종단(terminal) 상태다 — 200을 반환해야 하지만 내부적으로는 알림을 발송해야 한다.

이 세 가지 중 세 번째 경우를 어떻게 처리하느냐가 이 글의 핵심이다.

## 실패 모드

**500을 반환하면 PG가 계속 재전송한다**

콜백 수신 측이 4xx/5xx를 반환하면 대부분의 PG는 자체 재전송 정책에 따라 동일 콜백을 반복 전송한다. 내부 이상 상태를 외부 제공자에게 전파하면 재전송이 누적되고, 정작 정상 콜백 처리를 방해할 수 있다. 또한 재전송이 멈추기 전까지 PG 측 트랜잭션도 미결 상태로 남는다.

**200을 반환하고 조용히 삼키면 이상 상태를 놓친다**

반대 극단도 문제다. 처리 가능한 주문이 없다는 사실을 로그에만 남기고 알림 없이 200을 반환하면, 결제 금액은 PG 측에서 확정됐지만 내부에서 주문이 완료로 전환되지 않은 불일치가 조용히 쌓인다. 이런 불일치는 정산 또는 고객 서비스 단계에서야 발견되는 경우가 많다.

## 콜백 상태 분류와 처리 경로

수신한 콜백을 처리하기 전에 내부 주문 상태를 먼저 확인한다.

```
callback 수신
    │
    ├─ 주문 존재 & PENDING 상태
    │       → 결제 완료 전환 + 200 반환      [정상 경로]
    │
    ├─ 주문 존재 & PAYMENT_COMPLETED 상태
    │       → 아무것도 하지 않음 + 200 반환  [중복 콜백, 알림 없음]
    │
    ├─ 주문 존재 & 취소/실패 등 terminal 상태
    │       → ops 알림 발송 + 200 반환       [이상 상태, 데이터 변경 없음]
    │
    └─ 주문 없음 (payment_request_id 미매핑)
            → ops 알림 발송 + 200 반환       [이상 상태, 데이터 변경 없음]
```

중복 콜백(`PAYMENT_COMPLETED`)은 정상적인 멱등 재전송이므로 알림 대상이 아니다. 나머지 이상 상태는 내부 운영팀이 인지해야 하므로 알림을 보낸다. 어느 경우든 외부 제공자에게는 항상 200(성공)을 반환한다.

## 설계 접근: 알림 전용 경로

이상 상태 분기에서 핵심 제약은 두 가지다.

**1. 데이터를 변경하지 않는다**

이상 상태를 감지한 시점에서 기존 주문이나 결제 레코드를 수정하는 것은 부작용이 크다. 상태를 추측해서 덮어쓰면 정산 오류나 감사 로그 오염으로 이어진다. 알림 전용 경로는 읽기와 알림 발송만 수행한다.

```python
def handle_payment_callback(payload):
    payment_request_id = payload["payment_request_id"]
    status = payload["status"]

    order = find_order_by_payment_request_id(payment_request_id)

    if order is None:
        alert_ops("결제 콜백: 매핑된 주문 없음", sanitize(payload))
        return success_response()

    if order.status == "PAYMENT_COMPLETED":
        # 중복 콜백 — 알림 없이 통과
        return success_response()

    if order.status in TERMINAL_STATES:  # e.g. CANCELED, PAYMENT_FAILED
        alert_ops("결제 콜백: 종단 상태 주문에 성공 콜백 수신", sanitize(payload))
        return success_response()

    # 정상 경로: PENDING 상태 주문 완료 전환
    complete_order(order, payload)
    return success_response()
```

**2. 페이로드를 정제한다**

알림에 원본 페이로드를 그대로 담으면 고객 식별 정보나 카드 정보 같은 민감 데이터가 알림 채널에 노출된다. 운영팀이 상황을 파악하는 데 필요한 최소한의 필드만 포함한다.

```python
ALLOWED_ALERT_FIELDS = {"payment_request_id", "status", "pg_provider", "amount"}

def sanitize(payload):
    return {k: v for k, v in payload.items() if k in ALLOWED_ALERT_FIELDS}
```

## 트레이드오프

**"왜 데이터를 수정하지 않는가"**

이상 상태에서 주문을 강제로 완료 처리하면 단기적으로 불일치가 해소된 것처럼 보인다. 그러나 원인을 파악하기 전에 상태를 덮어쓰면 — 예컨대 이미 취소된 주문을 완료로 전환하면 — 환불 처리나 재고 원복 로직과 충돌한다. 이상 상태의 원인 조사는 알림을 받은 운영팀이 맥락을 보고 판단하는 것이 맞다.

**"알림이 너무 많아지지 않는가"**

중복 콜백(`PAYMENT_COMPLETED`)을 알림 대상에서 제외하면 정상적인 PG 재전송 노이즈는 걸러진다. 남는 알림은 실제로 조사가 필요한 케이스다. 운영 환경에서 알림 빈도가 높다면 `payment_request_id` 기준으로 일정 시간 내 중복 알림을 억제하는 dedup 레이어를 추가할 수 있다.

**"success_response()를 반환하는 게 맞는가"**

ACK 계약은 "콜백을 수신했다"는 사실을 확인하는 것이지, 내부 처리 결과를 전달하는 게 아니다. 내부 이상 상태는 내부 가시성 경로(알림, 로그)로 처리한다. 두 채널을 혼용하면 PG 재전송 폭주 위험이 생긴다.

## 검증: 테스트 매트릭스

브랜치별로 명시적인 테스트를 작성한다.

| 시나리오                     | 내부 주문 상태    | 기대 응답 | 알림 발송 | 데이터 변경                        |
| ---------------------------- | ----------------- | --------- | --------- | ---------------------------------- |
| 정상 결제 완료               | PENDING           | 200       | 없음      | 주문 상태 PAYMENT_COMPLETED로 전환 |
| 중복 콜백                    | PAYMENT_COMPLETED | 200       | 없음      | 없음                               |
| 취소된 주문에 성공 콜백      | CANCELED          | 200       | 있음      | 없음                               |
| 실패 처리된 주문에 성공 콜백 | PAYMENT_FAILED    | 200       | 있음      | 없음                               |
| 매핑 주문 없음               | —                 | 200       | 있음      | 없음                               |

```python
def test_duplicate_callback_does_not_alert(mock_alert):
    order = make_order(status="PAYMENT_COMPLETED")
    response = handle_payment_callback(make_payload(order.payment_request_id))
    assert response.status == 200
    mock_alert.assert_not_called()

def test_canceled_order_alerts_without_mutation(mock_alert):
    order = make_order(status="CANCELED")
    response = handle_payment_callback(make_payload(order.payment_request_id))
    assert response.status == 200
    mock_alert.assert_called_once()
    order.refresh_from_db()
    assert order.status == "CANCELED"  # 상태 변경 없음

def test_no_order_alerts(mock_alert):
    response = handle_payment_callback(make_payload("unknown-id-000"))
    assert response.status == 200
    mock_alert.assert_called_once()

def test_pending_order_completes_normally(mock_alert):
    order = make_order(status="PENDING")
    response = handle_payment_callback(make_payload(order.payment_request_id))
    assert response.status == 200
    mock_alert.assert_not_called()
    order.refresh_from_db()
    assert order.status == "PAYMENT_COMPLETED"
```

테스트에서 `mock_alert.assert_not_called()`와 `assert_called_once()`를 둘 다 명시하는 이유는, "알림이 안 울려야 하는 분기"를 회귀로부터 보호하기 위해서다. 알림 누락만큼 알림 과발송도 운영에 영향을 준다.

## 배운 것

외부 제공자 콜백의 ACK 계약과 내부 이상 상태 가시성은 서로 다른 채널의 문제다. 500 응답으로 내부 상태를 외부에 전파하면 재전송이 폭주하고, 200으로 조용히 삼키면 불일치가 쌓인다.

최소한의 원칙은 세 가지다. 첫째, 외부 제공자에게는 항상 ACK(200)를 반환한다. 둘째, 이상 상태는 알림으로만 가시화하고 데이터는 건드리지 않는다. 셋째, 중복 콜백(이미 완료된 주문)과 진짜 이상 상태를 코드에서 명시적으로 구분한다.

이 분류가 코드에 명확히 드러나 있어야 알림 발송 여부를 테스트로 고정할 수 있고, 리뷰어도 각 분기의 의도를 빠르게 파악할 수 있다.
