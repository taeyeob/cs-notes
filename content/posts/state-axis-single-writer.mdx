## 문제 정의

하나의 명령이 여러 상태 축(state axis)을 동시에 갱신하는 코드는 처음에는 자연스러워 보인다. 노출 예약 명령이 공개 여부 외에 판매 상태와 lifecycle 상태까지 직접 고정값으로 박는 식이다. 그런데 이 패턴이 반복되면 세 가지 문제가 드러난다.

첫째, **소유권이 흐려진다.** `sale_status`를 바꿀 수 있는 명령이 여러 개가 되면, 어디서 어떤 이유로 바뀌었는지 추적하기 어려워진다.

둘째, **수동 override가 덮어써진다.** 운영자가 "품절" 또는 "판매 중지"를 수동으로 설정했는데, 다른 명령이 실행될 때 고정값으로 덮어쓰면 운영자의 의도가 사라진다.

셋째, **책임 밖 축이 함께 오염된다.** 공고 상태(`announcement_status`)처럼 전혀 다른 소유자를 가진 축이 명령 안에서 같이 갱신되면, 그 축의 진짜 writer가 누구인지 알 수 없게 된다.

이 글은 상태를 갱신하는 시점과 트랜잭션 경계가 아니라, **어느 명령이 어느 축을 소유하는가**와 **소유하지 않은 축을 어떻게 보존하는가**에 집중한다.

## 단일 writer 정의

이 글에서 **단일 writer**란 특정 상태 축의 모든 쓰기 규칙을 소유하는 단일 정책 경계(policy boundary)—하나의 컴포넌트, 클래스, 또는 모듈—를 뜻한다. literal single function이 아니라, 자동 파생과 수동 override를 포함한 해당 축의 모든 갱신이 반드시 이 정책 경계의 공개 API를 통과해야 한다는 계약이다. 다른 명령이 해당 필드를 직접 대입하면 이 계약이 깨진다.

이 글의 single writer는 데이터베이스 primary writer와 다른 개념으로, 어떤 replica가 쓰기를 처리하는가가 아니라 **어떤 도메인 로직이 특정 상태 필드의 유일한 쓰기 정책을 소유하는가**를 뜻한다.

## 상태 축과 소유권 구조

아래는 이벤트 도메인의 상태 축 예시다. 각 축마다 원천, 소유 경계, 갱신 방식이 다르다.

| 상태 축               | 가능한 값                                                | 원천                                     | 갱신 방식                 | 소유 경계           |
| --------------------- | -------------------------------------------------------- | ---------------------------------------- | ------------------------- | ------------------- |
| `visibility_status`   | `HIDDEN` / `DISPLAY_RESERVED` / `VISIBLE`                | 운영자·예약 스케줄                       | 직접 할당                 | visibility 명령     |
| `sale_status`         | `WAITING` / `ON_SALE` / `ENDED` / `SOLD_OUT` / `STOPPED` | 판매 기간 + 수동 override                | 기간 파생 + override 보존 | `SaleStatusWriter`  |
| `lifecycle_status`    | `RESERVED` / `ACTIVE` / `PAUSED` / `CLOSED`              | `visibility_status` + `sale_status` 파생 | 파생 전용 sync            | lifecycle sync 함수 |
| `announcement_status` | `DRAFT` / `PUBLISHED` / `ARCHIVED`                       | 운영자 조작                              | 직접 할당                 | 공고 명령           |

`visibility_status`는 운영자 또는 예약 스케줄이 직접 전환하므로 visibility 명령이 단독 소유한다. `sale_status`는 기간에서 자동 파생되지만 수동 override도 존재하며, 두 경로 모두 `SaleStatusWriter` 정책 경계를 통과한다. `lifecycle_status`는 `visibility_status`와 `sale_status`를 source로 하는 파생 축으로, lifecycle sync 함수만 갱신한다. `announcement_status`는 완전히 독립된 축이다. visibility 명령과 sale 명령은 이 축에 절대 개입하지 않는다.

## 실패 모드

### 다른 명령이 소유권 경계를 넘는다

아래 코드는 노출 예약 명령 안에서 `sale_status`와 `lifecycle_status`를 직접 고정값으로 할당한다.

```python
# 위험: reserve_visibility가 sale_status와 lifecycle_status를 직접 박는다
def reserve_visibility(event_id, reserved_at):
    event = Event.objects.get(id=event_id)
    event.visibility_status = "DISPLAY_RESERVED"
    event.visibility_reserved_at = reserved_at

    # 소유권 침범: 수동 STOPPED/SOLD_OUT도 WAITING으로 덮어씀
    event.sale_status = "WAITING"        # ← SaleStatusWriter를 우회
    # 실제 기간이나 visibility+sale 조합을 무시하고 직접 할당
    event.lifecycle_status = "RESERVED"  # ← lifecycle sync 함수를 우회

    event.save()
```

이 코드는 두 가지 실패를 동시에 만든다. 하나는 소유권 침범이고, 다른 하나는 수동 override 덮어쓰기다. 운영자가 "판매 중지(`STOPPED`)" 상태를 수동으로 설정했더라도, 노출 예약 명령이 실행되면 `WAITING`으로 바뀐다. `lifecycle_status`도 실제 visibility+sale 조합과 무관하게 고정값이 박힌다.

### sync-all 함수가 책임 밖 축을 포함한다

여러 상태를 한꺼번에 갱신하는 함수를 만들면 또 다른 문제가 생긴다.

```python
# 위험: sync-all이 announcement_status까지 건드린다
def sync_all_statuses(event, now):
    SaleStatusWriter.sync_from_period(event, now=now)
    sync_lifecycle_status(event)
    event.announcement_status = derive_announcement_status(event)  # ← 공고 축 오염
    event.save()
```

판매 상태 sync를 호출하러 들어갔다가 공고 상태까지 함께 바뀐다. 새 상태 축이 추가될 때마다 이 함수를 수정해야 하고, 어떤 명령이 어떤 축을 건드리는지 추적하기 어려워진다.

## 설계 접근

### SaleStatusWriter: 단일 정책 경계

`sale_status` 축의 모든 쓰기 규칙은 `SaleStatusWriter` 하나가 소유한다. 자동 파생(`sync_from_period`)과 수동 override(`apply_manual_override`) 모두 이 클래스의 공개 메서드를 통과한다. 다른 명령이 `event.sale_status`를 직접 대입하면 이 계약이 깨진다.

```python
MANUAL_OVERRIDE_STATUSES = {"SOLD_OUT", "STOPPED"}


class SaleStatusWriter:
    """sale_status 축의 모든 쓰기 규칙을 소유하는 단일 정책 경계."""

    @classmethod
    def sync_from_period(cls, event, now) -> None:
        """기간 기반 자동 파생. 수동 override 상태는 덮어쓰지 않는다."""
        event.sale_status = cls._derive(
            sale_start=event.sale_start,
            sale_end=event.sale_end,
            current_status=event.sale_status,
            now=now,
        )

    @classmethod
    def apply_manual_override(cls, event, status: str) -> None:
        """운영자 수동 override. SOLD_OUT, STOPPED만 허용."""
        if status not in MANUAL_OVERRIDE_STATUSES:
            raise ValueError(f"수동 override 대상이 아닌 상태: {status}")
        event.sale_status = status

    @classmethod
    def _derive(cls, sale_start, sale_end, current_status, now) -> str:
        # 1순위: 수동 override는 자동 파생으로 덮어쓰지 않는다
        if current_status in MANUAL_OVERRIDE_STATUSES:
            return current_status

        # 2순위: 원천 데이터(기간)가 없으면 현재 상태를 보존한다
        if sale_start is None and sale_end is None:
            return current_status if current_status is not None else "WAITING"

        # 3순위: 기간에서 파생
        if sale_start is not None and now < sale_start:
            return "WAITING"
        if sale_end is None or now <= sale_end:
            return "ON_SALE"
        return "ENDED"
```

수동 override를 설정할 때도 `SaleStatusWriter.apply_manual_override`를 사용하므로, "writer가 둘"이 되는 모순이 없다.

```python
# 운영자 수동 품절 처리
def mark_sold_out(event_id):
    event = Event.objects.get(id=event_id)
    SaleStatusWriter.apply_manual_override(event, "SOLD_OUT")
    event.save(update_fields=["sale_status"])
```

### lifecycle_status: visibility + sale 파생

`lifecycle_status`는 `visibility_status`와 `sale_status` 조합에서 계산된다. 이벤트 기간이나 다른 원천 데이터를 직접 참조하지 않는다.

```python
KNOWN_VISIBILITY_STATUSES = {"HIDDEN", "DISPLAY_RESERVED", "VISIBLE"}
KNOWN_SALE_STATUSES = {"WAITING", "ON_SALE", "ENDED", "SOLD_OUT", "STOPPED"}


def derive_lifecycle_status(visibility_status: str, sale_status: str) -> str:
    # 조건 순서는 제품 계약이다:
    # DISPLAY_RESERVED는 composite lifecycle에서 RESERVED를 우선 표현하되
    # sale 축의 수동 STOPPED/SOLD_OUT 값 자체는 보존된다.
    # 예약이 아닌 경우 수동 sale override(STOPPED/SOLD_OUT)가 PAUSED를 만든다.
    if visibility_status not in KNOWN_VISIBILITY_STATUSES:
        raise ValueError(f"알 수 없는 visibility_status: {visibility_status!r}")
    if sale_status not in KNOWN_SALE_STATUSES:
        raise ValueError(f"알 수 없는 sale_status: {sale_status!r}")
    # 1. visibility_status가 DISPLAY_RESERVED이면 RESERVED
    if visibility_status == "DISPLAY_RESERVED":
        return "RESERVED"
    # 2. sale_status가 STOPPED 또는 SOLD_OUT이면 PAUSED
    if sale_status in {"STOPPED", "SOLD_OUT"}:
        return "PAUSED"
    # 3. sale_status가 ENDED이거나 visibility_status가 HIDDEN이면 CLOSED
    if sale_status == "ENDED" or visibility_status == "HIDDEN":
        return "CLOSED"
    return "ACTIVE"


def sync_lifecycle_status(event) -> None:
    """lifecycle_status 축의 단일 writer. visibility_status와 sale_status를 source로 한다."""
    event.lifecycle_status = derive_lifecycle_status(
        visibility_status=event.visibility_status,
        sale_status=event.sale_status,
    )
```

조건 순서는 의도된 제품 계약이다. `DISPLAY_RESERVED`는 composite lifecycle에서 예약 단계를 우선 표현하되, 해당 이벤트의 `sale_status` 값 자체(`STOPPED`, `SOLD_OUT` 등)는 그대로 보존된다. 예약 상태가 아닌 경우 수동 sale override(`STOPPED`/`SOLD_OUT`)가 `PAUSED`를 만들고, 이 우선순위가 `HIDDEN`보다 앞선다. `KNOWN_VISIBILITY_STATUSES`와 `KNOWN_SALE_STATUSES`에 없는 enum 값이 전달되면 조용히 `ACTIVE`로 흘러가지 않고 즉시 `ValueError`를 발생시켜 fail-closed로 동작한다.

### 안전한 reserve_visibility 명령

visibility 명령은 `visibility_status`만 직접 할당한다. sale 상태는 `SaleStatusWriter` 정책 경계를 통해, lifecycle은 전용 sync 함수를 통해 갱신한다. `announcement_status`는 호출·저장 대상에서 제외한다.

```python
def reserve_visibility(event_id, reserved_at, now):
    event = Event.objects.get(id=event_id)

    # visibility 축: 이 명령이 소유 → 직접 할당
    event.visibility_status = "DISPLAY_RESERVED"
    event.visibility_reserved_at = reserved_at

    # sale 축: SaleStatusWriter 정책 경계를 통해 갱신 (수동 override 보존)
    SaleStatusWriter.sync_from_period(event, now=now)

    # lifecycle 축: visibility + sale source 기반 전용 sync 함수
    sync_lifecycle_status(event)

    # announcement_status: 이 명령의 소유 밖 → 호출/저장 대상에서 제외
    event.save(update_fields=[
        "visibility_status", "visibility_reserved_at", "sale_status", "lifecycle_status"
    ])
```

### 자동 파생 상태와 수동 override 우선순위

우선순위는 세 단계다.

1. 수동 override(`SOLD_OUT`, `STOPPED`) → 현재 상태 그대로 반환
2. 원천 데이터(기간) 없음 → 현재 상태 보존. 현재 상태도 없으면 명시적 fallback(`WAITING`)
3. 기간 있음 → 주입된 `now` 기준으로 `WAITING` / `ON_SALE` / `ENDED` 파생

"원천 데이터 없음"과 "알 수 없는 enum"은 다른 정책을 적용한다. **원천 데이터(기간) 없음**은 `sale_start`와 `sale_end` 모두 `None`인 경우로, 이 이벤트에 판매 기간이 아직 설정되지 않은 것이므로 현재 `sale_status`를 보존하거나 명시적 fallback(`WAITING`)으로 내린다. 이 케이스는 정상 운영 흐름이다. 반면 **알 수 없는 enum**은 `KNOWN_VISIBILITY_STATUSES`나 `KNOWN_SALE_STATUSES`에 정의되지 않은 값이 전달된 경우로, 계약 밖의 입력이므로 `ValueError`를 발생시켜 fail-closed로 처리한다. 둘 다 "값이 없거나 이상하다"는 점은 같지만, 전자는 fallback 정책으로 흡수하고 후자는 명시적 오류로 거절한다.

"기간이 없으면 현재 상태를 유지한다"는 규칙은 부분 업데이트 명령에서 중요하다. 기간 없이 `visibility_status`만 바꾸는 명령이 실행될 때, 판매 상태를 초기화하거나 fallback으로 내려버리면 의도치 않은 상태 손실이 생긴다.

`_derive`가 `now`를 인자로 받으므로 테스트에서 임의의 시각을 주입해 결정론적으로 검증할 수 있다. `datetime.utcnow()` 직접 호출은 피한다.

### 명령이 소유하지 않은 축은 update_fields에서도 제외한다

`save(update_fields=[...])` 없이 전체 `save()`를 호출하면, ORM 객체에 로드된 구버전 필드값이 다른 경로에서 바뀐 값을 덮어쓸 수 있다. `update_fields`에 소유 축만 명시하면 이 문제가 사라진다.

## 트레이드오프

### 단일 sync-all 함수 vs 축별 writer

**단일 sync-all 함수**는 "상태를 갱신해야 할 때 함수 하나만 호출하면 된다"는 단순함을 제공한다. 호출자가 어느 축을 갱신해야 할지 알 필요가 없다.

그러나 sync-all 함수가 커질수록 결합이 높아진다. 판매 상태를 sync하려고 들어갔는데 공고 상태까지 갱신된다. 새 상태 축이 추가될 때마다 이 함수를 수정해야 하고, 어떤 명령이 어떤 축을 건드리는지 추적하기 어려워진다. 오직 `lifecycle_status`만 갱신하고 싶은 명령도 sync-all을 호출해야 하므로, sync-all이 건드리는 다른 축의 파생 로직 버그가 엉뚱한 명령 실행 시에 드러난다.

**축별 writer**는 축마다 책임이 명확하다. 명령은 자신이 소유하는 축의 writer만 호출하고, 나머지는 건드리지 않는다는 계약이 코드에 드러난다. 함수 수가 늘어나는 복잡도가 생기지만, 각 writer는 단독으로 테스트할 수 있고 호출 지점에서 의도가 명확하게 표현된다. 상태 축이 4개 이상이 되면 sync-all 방식보다 축별 writer가 유지보수 측면에서 낫다.

### 수동 override 보존과 자동 파생의 경계

수동 override 상태 집합이 커지면 파생 함수에 조건이 늘어난다. `MANUAL_OVERRIDE_STATUSES`가 명확히 정의되어 있지 않으면 "이 상태는 자동으로 덮어써도 되는가"를 판단하기 어려워진다. 새 수동 상태가 추가될 때 파생 함수의 우선순위 로직도 함께 검토하는 관례를 세우는 것이 좋다.

## 검증 방법

테스트는 "파생이 맞는가"와 "다른 축이 바뀌지 않는가"를 분리해서 확인한다. `now`를 인자로 주입하므로 `datetime.utcnow()` 없이 결정론적으로 검증한다.

```python
from datetime import datetime, timedelta, timezone

NOW = datetime(2026, 8, 26, 12, 0, 0, tzinfo=timezone.utc)

# --- 자동 파생 상태 ---


def test_판매_기간_시작_전에는_waiting():
    future = NOW + timedelta(days=1)
    status = SaleStatusWriter._derive(
        sale_start=future, sale_end=None, current_status=None, now=NOW
    )
    assert status == "WAITING"


def test_판매_기간_중에는_on_sale():
    past = NOW - timedelta(hours=1)
    future = NOW + timedelta(hours=1)
    status = SaleStatusWriter._derive(
        sale_start=past, sale_end=future, current_status=None, now=NOW
    )
    assert status == "ON_SALE"


def test_판매_기간_종료_후에는_ended():
    past_start = NOW - timedelta(days=2)
    past_end = NOW - timedelta(days=1)
    status = SaleStatusWriter._derive(
        sale_start=past_start, sale_end=past_end, current_status="ON_SALE", now=NOW
    )
    assert status == "ENDED"


# --- 수동 override 보존 ---


def test_sold_out은_기간_파생으로_덮어쓰지_않는다():
```

| 케이스                                     | 검증 포인트                                                                                                                     |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| 판매 전/중/후 자동 파생                    | `sale_start`, `sale_end` 기준으로 `WAITING` / `ON_SALE` / `ENDED`가 맞게 도출되는가                                             |
| 수동 `SOLD_OUT` / `STOPPED` unit 보존      | 기간이 있어도 override 상태가 덮어써지지 않는가                                                                                 |
| 원천 데이터(기간) 없음                     | 현재 상태가 보존되는가 (fallback이 아니라 현재값 유지)                                                                          |
| 원천도 현재 상태도 없는 fallback           | 명시된 fallback(`WAITING`)이 반환되는가                                                                                         |
| lifecycle 기본 조합 계산                   | lifecycle이 직접 할당되지 않고 visibility+sale 정상 조합에서 올바르게 파생되는가                                                |
| lifecycle 충돌 우선순위 고정               | `DISPLAY_RESERVED`+`STOPPED`/`ENDED`→`RESERVED`, `HIDDEN`+`STOPPED`→`PAUSED` 로 조건 순서가 고정되는가                          |
| unknown enum 거절                          | `KNOWN_VISIBILITY_STATUSES`/`KNOWN_SALE_STATUSES` 밖의 값이 `ValueError`를 발생시키는가                                         |
| 명령 통합: 책임 밖 축 불변                 | `announcement_status`가 노출 예약 명령 실행 후에도 바뀌지 않는가                                                                |
| 명령 통합: 수동 override + 책임 밖 축 보존 | `STOPPED`(수동 override) + 판매 기간 중 이벤트에 `reserve_visibility` 실행 후 visibility·sale·lifecycle·공고 축이 모두 올바른가 |

"파생이 맞는가" 테스트와 "다른 축이 바뀌지 않는가" 테스트는 분리해야 한다. 두 성질은 독립적이고, 하나만 확인하면 나머지가 깨진 채로 통과될 수 있다.

## 배운 점

**명령이 건드리지 않는 상태 축을 명시적으로 결정하는 것이 소유권 설계의 핵심이다.** "이 명령이 어떤 축을 갱신하는가"보다 "이 명령이 어떤 축을 건드리지 않는가"를 먼저 생각하는 편이 경계를 더 선명하게 그린다.

설계 원칙을 요약하면 이렇다.

1. 각 상태 축마다 단일 writer(정책 경계)를 정한다. 두 개 이상의 명령이 같은 축을 직접 할당하면 소유권이 없는 것과 같다.
2. `sale_status`처럼 자동 파생과 수동 override가 공존하는 축은 하나의 정책 컴포넌트(`SaleStatusWriter`)에 두 경로를 모두 집약한다. 두 경로가 모두 같은 정책 경계를 통과하면 단일 writer다.
3. 파생 전용 축(`lifecycle_status`)은 source 축(visibility+sale)에서만 계산하고, 직접 할당을 허용하지 않는다.
4. 수동 override 상태는 자동 파생으로 덮어쓰지 않는다. override 상태 집합을 상수로 명시하고 파생 함수에서 먼저 확인한다.
5. 원천 데이터가 없으면 현재 상태를 보존한다. 원천도 현재 상태도 없을 때는 명시적 fallback을 선택한다. 묵시적으로 초기화하지 않는다.
6. 명령이 소유하지 않는 축은 `update_fields`에서도 제외한다. ORM 객체 수준에서 필드를 수정하지 않더라도 전체 `save()`는 의도치 않게 덮어쓸 수 있다.
7. sync-all 함수보다 축별 writer를 선호한다. 함수 수가 늘어도 각 명령이 책임지는 범위가 코드에서 보인다.

가장 발견하기 어려운 버그는 "명령이 건드리지 않는 축의 값이 조용히 바뀐다"처럼 변경 책임이 명확하지 않아서 생긴다. `update_fields` 명시와 축별 소유권 테스트가 이 버그를 조기에 잡는 가장 직접적인 방법이다.
