## 문제 정의

백엔드 서비스를 유지보수하다 보면 "이 API, 아무도 안 쓰는 것 같은데?"라는 생각이 드는 엔드포인트를 만나게 된다. 기능 개편 이후 남겨진 어드민 API, 클라이언트 버전이 올라가면서 deprecated된 v1 엔드포인트, 내부 테스트용으로 만들었다가 잊힌 utility route 같은 것들이다.

이런 API를 정리하고 싶을 때 빠지기 쉬운 함정이 있다. 코드 검색으로 "이 함수를 호출하는 곳이 없으니 지워도 되겠다"고 결론 내리는 것이다. 그런데 실제로 삭제해보면 런타임에서야 드러나는 참조, 삭제를 빠뜨린 라우트 등록, 다른 저장소에서 들어오는 외부 호출 같은 것들이 등장한다.

미사용 API를 안전하게 지우는 일은 "없다고 생각했음"을 증명하는 과정이다. 이 글은 그 증명을 체계화하는 절차를 다룬다.

## 왜 "안 쓰는 것 같음"만으로 부족한가

### grep은 코드 내부 참조만 본다

로컬 저장소에서 함수명이나 URL 패턴을 grep해서 결과가 없으면 충분해 보인다. 하지만 다음 케이스는 grep으로 잡히지 않는다.

- **다른 저장소에서의 호출**: 클라이언트 앱, 관리 도구, 스크립트가 별도 저장소에 있고 해당 엔드포인트를 직접 호출하고 있을 수 있다.
- **하드코딩된 URL 문자열**: 클라이언트 측에서 함수 레퍼런스가 아닌 URL 문자열로 호출하는 경우, 서버 측 코드 검색으로는 나타나지 않는다.
- **동적 라우팅**: ViewSet의 router 등록이나 URL conf에 동적으로 포함된 경우, 명시적 URL 선언 없이 패턴 매칭으로 처리된다.
- **외부 자동화 및 운영 스크립트**: 배치 잡이나 cron, 내부 관리 도구에서 주기적으로 호출하는 경우 코드 리뷰로 파악하기 어렵다.

### 라우트를 남기면 삭제가 아니다

구현 함수(view, handler)를 지웠더라도 URL 라우팅 설정에 해당 경로가 남아 있으면 요청이 들어왔을 때 500이나 AttributeError가 발생한다. 반대로 라우팅을 지웠더라도 구현 함수를 남기면 코드베이스에 dead code가 남아 이후 혼란의 원인이 된다.

삭제가 완료되려면 라우트 등록과 구현이 모두 제거되어야 한다.

### 삭제 직후 검증이 없으면 놓친 항목을 모른다

엔드포인트를 여러 개 지우고 배포했을 때 "전부 지운 것이 맞는가?"를 후속 확인 없이 넘기면, 빠진 항목은 나중에 운영 오류나 클라이언트 문의로 드러난다.

## 인벤토리를 먼저 만든다

삭제를 시작하기 전에 정리 대상의 전체 목록을 만든다. 인벤토리가 있어야 삭제가 완료됐을 때 "모두 처리됐음"을 확인할 수 있다.

### 인벤토리에 담을 항목

각 API 엔드포인트에 대해 다음 정보를 모은다.

- **식별자**: URL 패턴, ViewSet 이름, 핸들러 함수명
- **위험도**: 삭제 판단의 난이도를 HIGH / MEDIUM / LOW로 분류한다. 외부 클라이언트 참조 여부, 운영 로그 확인 가능 여부, 라우트 공유 여부 등을 기준으로 삼는다.
- **삭제 근거**: 마지막 호출 확인 기간, 참조 저장소 스캔 결과, 운영 로그 확인 결과

```
# 인벤토리 예시

| 엔드포인트              | 위험도 | 삭제 근거                         | 처리 상태 |
|-------------------------|--------|-----------------------------------|-----------|
| GET /api/v1/resource/   | HIGH   | 클라이언트 저장소 스캔 필요       | 대기      |
| POST /admin/batch-op/   | MEDIUM | 내부 도구 참조 여부 확인 필요     | 대기      |
| GET /api/v1/health-old/ | LOW    | 운영 로그 90일 내 호출 없음 확인  | 삭제 완료 |
```

### 위험도 게이트로 삭제 순서를 통제한다

LOW(내부 코드에만 참조, 로그 확인 완료) → MEDIUM(내부 도구 참조 가능) → HIGH(외부 클라이언트 참조 가능성) 순으로 처리한다. 높은 위험도는 더 많은 근거를 확보한 뒤 삭제한다. 인벤토리에 위험도와 처리 상태를 기록해두면, 중간에 작업을 멈추거나 재개할 때 어디까지 진행됐는지 즉시 파악할 수 있다.

## 삭제는 라우트와 구현을 같이 지운다

엔드포인트 하나를 삭제할 때 제거해야 할 범위는 다음과 같다.

1. **URL 라우팅 설정**: `urlpatterns`에서 경로 제거, 또는 ViewSet router에서 등록 해제
2. **View / ViewSet 클래스 또는 함수**: 핸들러 구현 자체
3. **ViewSet의 특정 액션만 삭제하는 경우**: ViewSet 클래스는 남기고 해당 액션(메서드)만 제거. 이 경우 router가 생성하는 URL 패턴에서 해당 경로가 더 이상 노출되지 않는지 확인한다.
4. **해당 핸들러 전용 의존**: 다른 엔드포인트에서 공유하지 않는 serializer, form class, utility
5. **관련 테스트**: 삭제된 엔드포인트를 호출하는 테스트 케이스

범위를 좁게 잡을수록 실수가 줄어든다. "어디까지 제거해야 하는가"를 팀이 공유된 기준으로 합의해 두면 리뷰 단계에서 놓친 항목을 잡기 쉽다.

## 잔여 스캔으로 "없음"을 증명한다

삭제 후에는 "정말 다 지웠는가"를 검증하는 단계가 필요하다. 이 단계는 없음을 증명하는 것이 목적이다.

### 코드 잔여 스캔

삭제한 함수명, URL 패턴, 클래스명이 저장소 내 어디에도 남아 있지 않은지 확인한다.

```bash
# 삭제한 핸들러 이름 잔여 여부 확인
grep -rn "legacy_resource_view" . --include="*.py"

# 삭제한 URL 패턴 문자열 잔여 여부 확인
grep -rn "legacy-resource" . --include="*.py"
```

결과가 0건이어야 한다. 1건이라도 나오면 어떤 컨텍스트인지 확인한다. 삭제되어야 할 참조가 남은 것인지, 주석이나 테스트 fixture에 의도적으로 남긴 것인지 구분한다.

### 라우트 등록 잔여 스캔

URL conf나 router 설정에서 삭제한 경로가 여전히 등록되어 있지 않은지 확인한다. Django 계열이라면 `show_urls` 커맨드나 router의 URL 리스트를 출력해 삭제한 경로 패턴이 포함되어 있지 않은지 확인할 수 있다.

```bash
# Django 예시
python manage.py show_urls | grep legacy
# 결과가 0줄이어야 한다
```

라우트 출력을 CI에서 스냅샷으로 유지하면 의도치 않은 라우트 추가/삭제를 자동으로 감지할 수도 있다.

### 운영 로그 확인

삭제하기 전 일정 기간(예: 최근 30일~90일)의 접근 로그에서 해당 엔드포인트로의 실제 호출이 있었는지 확인한다. 호출이 없었음이 확인된 엔드포인트는 삭제 근거가 충분하다. 호출 기록이 있다면 마지막 호출 시점과 호출 주체를 파악한 뒤 정리 일정을 재조정한다.

운영 로그를 직접 조회하기 어려운 경우, 모니터링 도구나 APM에서 엔드포인트별 요청 카운트를 확인하는 방식으로 대체할 수 있다.

### 클라이언트 저장소 참조 스캔

API를 호출하는 클라이언트가 별도 저장소에 있다면, 해당 저장소에서 삭제 대상 URL 패턴이나 경로 문자열을 검색한다. 자동화된 스캔이 어렵다면 클라이언트 팀과 직접 확인하는 절차를 밟는다. 클라이언트 측 참조가 남아 있는 채로 서버 API를 삭제하면 클라이언트에서 4xx/5xx가 발생한다.

## 삭제 판단의 트레이드오프

| 항목                      | 즉시 삭제             | 단계적 삭제 (deprecation 기간 운영) |
| ------------------------- | --------------------- | ----------------------------------- |
| 코드베이스 정리 속도      | 빠름                  | 느림                                |
| 외부 클라이언트 영향 위험 | 높음                  | 낮음                                |
| 운영 로그 의존도          | 높음 (부재 증명 필요) | 낮음 (호출 감소 추이 관찰 가능)     |
| 처리 복잡도               | 낮음                  | 높음 (deprecated 상태 관리 필요)    |

위험도 LOW 엔드포인트(내부 전용, 로그 확인 완료)는 즉시 삭제가 합리적이다. 위험도 HIGH(외부 클라이언트 참조 가능성, 로그 확인 불가)는 deprecation 헤더를 추가하거나 모니터링 알림을 붙이고 일정 기간 실제 호출 추이를 관찰한 뒤 삭제하는 것이 안전하다.

"로그에 없었으니 바로 지워도 된다"는 판단은 로그 보존 기간과 로그 수집 완전성을 전제로 한다. 로그가 단기간만 보관되거나 일부 경로의 로그가 수집되지 않을 수 있는 환경이라면, 즉시 삭제 전에 이 전제를 먼저 검토한다.

## 체크리스트

**삭제 전**

- [ ] 삭제 대상 엔드포인트 전체 목록(인벤토리)이 작성되어 있는가
- [ ] 각 항목의 위험도가 분류되어 있는가
- [ ] 운영 로그에서 일정 기간 내 호출이 없음을 확인했는가
- [ ] 클라이언트 저장소 또는 외부 자동화에서의 참조를 스캔했는가

**삭제 시**

- [ ] URL 라우팅 설정(urlconf, router)에서 경로를 제거했는가
- [ ] View / ViewSet / 핸들러 구현을 제거했는가
- [ ] 해당 엔드포인트 전용 serializer, form, utility를 정리했는가
- [ ] 관련 테스트 케이스를 제거했는가

**삭제 후 (잔여 스캔)**

- [ ] 삭제한 함수명/클래스명이 저장소 내 어디에도 남아 있지 않은가
- [ ] 라우트 출력(show_urls 등)에서 삭제한 경로가 포함되어 있지 않은가
- [ ] 삭제한 URL 패턴 문자열이 코드베이스 내 어디에도 없는가
- [ ] CI/CD 파이프라인(linter, 테스트 suite)이 통과하는가

## 배운 점

- **삭제는 "지운 것 같음"이 아니라 "없음의 증명"이다.** 코드를 제거하는 것만으로 완료가 아니다. 라우팅 설정과 구현을 같이 제거하고, 이후 잔여 스캔으로 참조가 남아 있지 않음을 확인해야 실질적인 삭제다.
- **인벤토리 없이 삭제를 시작하면 "다 됐는가"를 판단할 기준이 없다.** 작업 도중 "빠뜨린 항목이 있지 않을까"라는 불안을 없애려면 전체 목록을 먼저 만들고 처리 상태를 추적해야 한다.
- **위험도에 따라 삭제 게이트를 나누면 리스크를 통제할 수 있다.** LOW는 빠르게 정리하고, HIGH는 외부 참조 확인이나 deprecation 기간 운영 같은 추가 절차를 거친다. 일괄 처리보다 안전하고, 단계적으로 효과를 확인하면서 진행할 수 있다.
- **잔여 스캔의 기준은 "결과가 0건"이다.** grep 결과가 1건이라도 나오면 맥락을 확인하는 습관이 필요하다. 주석인지, 삭제되어야 할 참조인지 판단하지 않으면 정리 완료를 단언할 수 없다.
