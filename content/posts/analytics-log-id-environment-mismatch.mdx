## 문제 정의

analytics warehouse(GA4 BigQuery export 등)에서 URL path 패턴을 파싱해 이벤트 ID를 추출하고, 그 ID를 서비스 DB의 기본 키와 직접 조인해서 랭킹 후보를 선출하는 배치가 있다고 하자.

```
/product/<event_id>  →  analytics_log.event_id 추출  →  service_db.events.id 조인
```

로컬 또는 개발 환경에서 배치를 실행했을 때 `ranking_cache`에 저장된 행이 예상보다 훨씬 적게 나오거나 단 한 건만 남는 경우가 있다. 코드는 정상적으로 실행되고 에러도 없다. 이 상황에서 "버그"를 찾으려 코드를 파다 보면 결국 문제가 데이터에 있음을 알게 된다.

핵심 질문은 이것이다: **analytics 로그에 담긴 ID가 현재 연결된 DB 환경에서 유효한 ID인가?**

## 관찰된 증상

- 배치 실행 후 `ranking_cache` 행 수가 1~2개에 그침 (개발 DB에는 수십~수백 개의 이벤트 행이 존재함에도)
- 배치 로그에는 "처리 완료" 메시지가 정상적으로 찍힘
- analytics warehouse 쿼리 자체는 상위 N개 후보를 정상적으로 반환함
- 에러 없이 조인 결과가 0에 가까운 행을 반환함

## 원인 분석

원인은 두 레이어에 걸쳐 있었다.

### 1. 환경 불일치: analytics 로그 ID가 개발 DB 범위 밖에 있음

analytics warehouse는 프로덕션 트래픽을 수집한다. 사용자가 실제로 방문한 URL은 프로덕션 DB의 `event_id` 범위에 속한다. 반면 개발 DB에는 테스트용으로 만든 소수의 레코드만 있고, 해당 ID는 프로덕션 analytics 로그에 등장할 이유가 없다.

```
analytics warehouse에서 추출한 상위 10개 event_id 예시:
  [104521, 98302, 110034, 97811, ...]

개발 DB의 events 테이블 id 범위:
  1 ~ 50  (테스트 시드 데이터)

교집합: 0개
```

analytics 로그 ID와 서비스 DB PK가 같은 정수 타입이라 겉보기에는 조인이 가능해 보이지만, 실제로 같은 엔티티를 가리키지 않는다.

### 2. 존재하더라도 적격성 조건을 통과하지 못하는 레코드

ID 범위가 우연히 겹치는 경우에도, 개발 DB의 해당 레코드가 배치의 적격성 필터를 통과하지 못할 수 있다. 예를 들어 판매 상태가 종료됐거나, 노출 비허용 상태이거나, 특정 이벤트 타입이 아닌 경우다.

두 가지 원인이 겹치면 결과적으로 후보 리스트에서 적격 행이 거의 남지 않아 `ranking_cache`가 텅 빈다.

## 왜 가짜 매핑을 만들면 안 되는가

빠른 해결책처럼 보이는 접근이 있다: "개발 DB에 있는 ID를 analytics 로그 ID와 매핑하는 테이블을 임시로 만들자." 이 방법은 다음 이유로 피해야 한다.

**테스트 결과가 현실을 반영하지 않는다.** 프로덕션에서는 analytics ID → 실제 이벤트 ID가 1:1로 존재하지만, 가짜 매핑은 임의의 연결을 만든다. 배치 로직이 "가짜로 연결된 데이터"를 기준으로 검증되면 실제 환경에서 동작이 달라질 수 있다.

**적격성 필터가 엉뚱한 레코드를 대상으로 실행된다.** 매핑된 개발 DB 레코드가 실제 프로덕션 이벤트의 특성을 반영하지 않으면, 필터 통과/탈락 비율이 왜곡된다. 이 상태로 후보 크기(N)나 필터 조건을 조정하면 잘못된 파라미터가 프로덕션에 배포될 수 있다.

**환경 경계가 흐려진다.** 가짜 매핑은 "프로덕션 analytics 신호 → 개발 DB 레코드"라는 인위적인 크로스-환경 연결을 만든다. 이 연결이 코드베이스에 남으면 이후 개발자가 왜 이 매핑이 존재하는지 이해하기 어려워진다.

## 환경 정렬 검증 워크플로우

analytics ID를 조인 키로 사용하기 전에 아래 순서로 검증한다.

### 1단계: analytics 로그 상위 ID 추출 및 DB 교집합 확인

```sql
-- analytics warehouse: 상위 후보 ID 추출 (실제 테이블/컬럼명은 환경에 맞게 변경)
WITH top_candidates AS (
  SELECT
    REGEXP_EXTRACT(page_location, r'/product/(\d+)') AS event_id,
    COUNT(*) AS view_count
  FROM analytics_events
  WHERE event_name = 'page_view'
    AND _TABLE_SUFFIX BETWEEN '20260615' AND '20260622'
  GROUP BY event_id
  HAVING event_id IS NOT NULL
  ORDER BY view_count DESC
  LIMIT 200
)
SELECT event_id FROM top_candidates;
```

추출한 ID 목록을 대상 환경 DB의 임시 후보 테이블(`candidate_ids`)로 옮긴 뒤, 서비스 DB와 조인해서 네 가지 범주로 분류한다.

```sql
-- 대상 환경 DB: ID별 존재 여부 및 적격성 분류
SELECT
  c.event_id,
  CASE
    WHEN e.id IS NULL              THEN 'missing_in_db'
    WHEN e.type != 'target_type'   THEN 'wrong_type'
    WHEN e.status != 'active'      THEN 'inactive'
    WHEN e.sale_end < NOW()        THEN 'sale_ended'
    ELSE                                'eligible'
  END AS category,
  COUNT(*) AS count
FROM candidate_ids c
LEFT JOIN events e ON e.id = CAST(c.event_id AS BIGINT)
GROUP BY category;
```

결과 예시:

| category      | count |
| ------------- | ----- |
| missing_in_db | 187   |
| inactive      | 5     |
| eligible      | 1     |

`missing_in_db` 비율이 압도적으로 높으면 환경 불일치가 원인이다.

### 2단계: 배치 적격성 필터와 API 적격성 필터 비교

배치가 사용하는 적격성 조건과 API 서비스가 사용하는 조건이 동일한지 확인한다. 조건이 다르면 배치는 통과시키지만 API는 제외하는(또는 반대) 이벤트가 생겨 랭킹 결과가 실제 서비스와 다르게 된다.

```python
# 배치 적격성 필터 (예시)
def is_eligible_for_ranking(event):
    return (
        event.type == "target_type"
        and event.status == "active"
        and event.display_enabled
        and event.sale_end > now()
    )
```

API에서 목록을 필터링하는 조건과 동일한 필드/값인지 코드 레벨에서 비교한다.

### 3단계: 개발 환경 대표 테스트 데이터 준비

가짜 매핑 대신, 개발 DB에 배치가 처리할 수 있는 대표 레코드를 명시적으로 시드한다.

- analytics warehouse 상위 ID 목록에서 일부를 뽑아 개발 DB에 동일 ID로 레코드를 생성한다.
- 또는 개발 DB에 존재하는 ID를 analytics warehouse 쿼리 결과에 포함시키는 픽스처를 만든다 (통합 테스트용).

이렇게 하면 배치의 전체 흐름(후보 추출 → 적격성 검증 → 캐시 저장)을 실제 조인 경로로 테스트할 수 있다.

### 4단계: 배치 실행 후 범주별 카운트 로깅

배치 실행이 끝나면 단순히 "완료"가 아니라 아래 항목을 로깅한다.

```python
logger.info(
    "ranking batch complete",
    candidates_from_analytics=len(candidates),
    missing_in_db=missing_count,
    wrong_type=wrong_type_count,
    inactive=inactive_count,
    eligible=eligible_count,
    cached=cached_count,
)
```

`cached_count`가 예상보다 적을 때 어느 단계에서 탈락이 일어났는지 즉시 파악할 수 있다.

## 트레이드오프

### 환경별 analytics 데이터 소스를 분리할 것인가

analytics warehouse를 환경별로 분리하는 방법(개발용 analytics, 프로덕션용 analytics)이 있다. 이 방법은 환경 불일치를 구조적으로 제거하지만 개발 환경에 트래픽이 없으면 analytics 신호가 생기지 않아 배치 자체를 테스트하기 어렵다.

실용적인 타협점은 **analytics 소스는 프로덕션 것을 읽되, 대상 DB는 환경별로 분리**하는 것이다. 대신 위에서 정리한 검증 워크플로우로 환경 불일치를 감지하고, 개발 DB에는 대표 테스트 데이터를 명시적으로 준비한다.

### 후보 크기(N)를 얼마나 크게 잡아야 하는가

환경 정렬 문제를 해결한 후에도, analytics 상위 N개 중 일부는 적격성 필터에서 탈락한다. N을 크게 잡으면 탈락 후에도 충분한 후보가 남지만 재검증 비용이 늘어난다. N을 결정하는 기준은 실제 탈락률을 측정한 뒤 조정하는 것이 가장 현실적이다.

## 부수 교훈: 조회수는 내부 정렬에만 사용한다

이와 별개로, analytics 집계값(viewCount 등)을 랭킹 캐시에 저장하거나 API 응답에 내려보내지 않도록 주의한다. 조회수는 후보 선출과 순위 계산의 내부 신호로만 소비하고, 캐시에는 **순위 인덱스(rank)** 만 저장한다. 이 설계 원칙은 [BigQuery를 랭킹 신호로만 쓰는 글](/posts/bigquery-ranking-signal-local-source-of-truth)에서 더 자세히 다뤘다.

## 배운 것

**URL path에서 파싱한 정수 ID는 다른 환경 DB의 PK와 자동으로 일치하지 않는다.** 타입이 같다고 같은 엔티티를 가리키는 것이 아니다. analytics 로그 ID를 조인 키로 쓰기 전에 "이 ID가 대상 환경에서 유효한가"를 먼저 확인해야 한다.

**빈 캐시 결과는 코드 버그가 아니라 데이터 환경 불일치일 수 있다.** 에러 없이 행이 0~1개인 결과가 나올 때, 코드를 파기 전에 ID 범주별 카운트부터 찍어본다.

**가짜 크로스-환경 매핑은 검증을 왜곡한다.** 환경 불일치를 임시 매핑으로 메우면 배치 로직이 잘못된 데이터를 기준으로 검증된다. 대신 대표 테스트 데이터를 명시적으로 시드해서 실제 조인 경로로 검증한다.

**배치 로그는 완료 여부가 아니라 단계별 카운트를 남긴다.** "몇 개 후보 중 몇 개가 각 단계에서 탈락했는가"가 기록되어야 이상 징후를 빠르게 감지할 수 있다.
