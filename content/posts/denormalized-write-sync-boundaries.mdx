## 문제 정의

같은 값이 두 테이블에 나뉘어 저장되는 구조에서 한쪽만 업데이트하면 데이터가 어긋난다. 성능이나 조회 편의를 위해 의도적으로 비정규화(denormalization)한 경우라도, 쓰기 경로가 단일하지 않으면 두 저장 위치 사이에 불일치가 생긴다.

구체적인 상황을 예로 들면 이렇다. 주문(order) 수준에서 관리자가 입력한 요청사항 메모가 있고, 그 주문과 연결된 참여자(participant) 수준 창고 요청 메모가 별도로 존재한다. 주문 메모를 배치로 수정할 때 참여자 쪽 메모도 함께 바꾸지 않으면, 창고에서는 오래된 값을 보게 된다.

## 비정규화 쓰기가 까다로운 이유

정규화된 구조라면 원본 한 곳만 바꾸면 된다. 비정규화 구조에서는 다음 세 가지 질문에 미리 답해야 한다.

- **어느 레코드까지 동기화 대상인가?** 비활성 상태이거나 취소된 레코드까지 건드리면 부작용이 생긴다.
- **동기화 범위 안에서 대표 레코드를 어떻게 고르는가?** 참여자 한 명에 여러 레코드가 연결되어 있을 때 어느 것을 업데이트할지 기준이 없으면 일관성이 깨진다.
- **읽고 쓰는 DB 커넥션이 같은가?** 읽기 전용 레플리카에서 읽고 프라이머리에 쓰면 레플리케이션 지연 때문에 의도와 다른 값이 덮어 써질 수 있다.

## 동기화 경계 결정하기

배치 업데이트는 처리 범위를 명시적으로 좁혀야 한다.

첫 번째 기준은 **외부 시스템의 성공 목록**이다. 외부 이행 시스템(OMS)이 수락한 주문만 업데이트하고, 거부된 주문은 건너뛴다. 성공 목록 없이 전체 주문을 업데이트하면 이행 실패 건도 바뀌어 운영 오류가 된다.

두 번째 기준은 **레코드 활성 상태**다. 비활성(soft-deleted) 참여자나 참여자 정보는 창고로 전달되지 않으므로, 이들을 동기화 대상에서 제외한다. 상태 필터를 빠뜨리면 의미 없는 행도 업데이트되어 `updated_at`이 불필요하게 갱신된다.

```python
# 동기화 대상 범위 예시 (의사 코드)
target_orders = Order.objects.filter(
    id__in=oms_success_ids,
    status=OrderStatus.ACCEPTED,
)
active_participants = Participant.objects.filter(
    order__in=target_orders,
    is_active=True,
)
```

## 대표 레코드 선택 기준

참여자 한 명이 여러 참여자 정보(participant info) 레코드를 가질 수 있을 때, 어느 레코드를 업데이트할지 명확한 규칙이 필요하다. 암묵적인 순서에 의존하면 DB 엔진이나 쿼리 계획에 따라 결과가 달라진다.

실용적인 기준 두 가지를 조합한다.

1. **티켓 수(ticket_count) 내림차순**: 더 많은 티켓을 보유한 레코드가 실질적으로 대표성이 높다.
2. **생성일(created_at) 내림차순**: 같은 티켓 수라면 최근에 생성된 레코드를 택한다.

```python
representative_info = (
    ParticipantInfo.objects.filter(participant=participant, is_active=True)
    .order_by("-ticket_count", "-created_at")
    .first()
)
```

이 기준을 문서화하지 않으면 다음 개발자가 순서를 바꿔도 테스트가 통과하는 것처럼 보일 수 있다. 동점 처리(tie-break) 케이스를 테스트로 고정해 두는 이유다.

## 트랜잭션·DB 라우팅·체크리스트

**쓰기 DB를 명시적으로 지정한다.** 읽기-수정-쓰기(read-modify-write) 흐름에서 읽기도 프라이머리에서 해야 방금 커밋된 값을 정확히 읽는다.

```python
with transaction.atomic(using="writer"):
    orders = Order.objects.using("writer").filter(...)
    # 수정 후 저장
```

**`bulk_update`는 `auto_now` 필드를 갱신하지 않는다.** Django의 `bulk_update`는 `updated_at = auto_now=True` 필드를 자동으로 건드리지 않는다. 동기화 시각을 추적해야 한다면 `updated_at`을 업데이트 대상 필드 목록에 직접 포함해야 한다. 이때 현재 시각은 프레임워크 전역에서 하나의 시간 제공자(time provider)를 통해 얻는다. 이렇게 하면 배치 안의 모든 레코드가 동일한 서비스 시각을 공유하고, 테스트 환경에서도 시각을 주입하거나 고정하기 쉬워진다.

```python
now = clock.now()  # 프로젝트 공통 시간 제공자 — 배치 전체가 동일 시각 사용
for record in records_to_update:
    record.warehouse_note = new_note
    record.updated_at = now  # bulk_update는 auto_now를 트리거하지 않으므로 직접 지정

Model.objects.using("writer").bulk_update(
    records_to_update, ["warehouse_note", "updated_at"]
)
```

**`None`을 빈 문자열로 정규화한다.** 주문 메모가 `None`일 수 있지만 창고 요청 메모 컬럼이 `NOT NULL`이면 저장 전에 변환이 필요하다. 이 변환을 서비스 레이어에서 명시적으로 하지 않으면 DB 레이어에서 예외가 터진다.

```python
warehouse_note = order.admin_note or ""
```

## 검증 전략

동기화 로직은 경계 케이스가 많으므로 단위 테스트로 각각을 고정한다.

| 케이스                                     | 검증 포인트                          |
| ------------------------------------------ | ------------------------------------ |
| OMS 성공 주문                              | 두 저장 위치 모두 새 값으로 바뀌는가 |
| OMS 실패 주문                              | 어느 쪽도 바뀌지 않는가              |
| 비활성 참여자                              | 업데이트 대상에서 제외되는가         |
| 활성 비당첨·대기 참여자 정보(성공 범위 내) | 두 저장 위치 모두 새 값으로 바뀌는가 |
| `None` → `""` 정규화                       | 빈 문자열로 저장되는가               |
| 동점 tie-break                             | 기준 순서대로 대표가 선택되는가      |

통합 테스트(실제 DB 연결)와 단위 테스트를 구분해서 운영한다. 단위 테스트는 ORM 쿼리를 목(mock)하지 않고 인메모리 픽스처로 로직 분기만 검증하고, 통합 테스트는 실제 DB에서 `bulk_update` 이후 값을 직접 조회해 확인한다. 두 레이어를 분리하면 CI에서 DB 없이도 기본 회귀를 잡을 수 있다.

## 배운 것

비정규화 쓰기는 단순히 "두 번 저장"이 아니다. 대상 범위, 대표 레코드 선택 기준, DB 라우팅, 필드 타입 불일치를 모두 명시적으로 결정해야 한다. 이 결정들을 코드 안에 묻어두지 않고 테스트 케이스로 드러내면, 나중에 정책이 바뀌었을 때 어디를 수정할지 바로 보인다. 동기화 경계를 설계할 때는 "무엇을 업데이트하는가"만큼 "무엇을 건드리지 않는가"를 명확히 하는 것이 똑같이 중요하다.
