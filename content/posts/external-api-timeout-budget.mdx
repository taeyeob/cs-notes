## 문제 정의

외부 API retry를 "최대 3회"처럼 횟수 기준으로만 설계하면 한 가지 구조적 함정이 생긴다. 각 시도마다 소비하는 시간(connect timeout + read timeout)과 시도 사이 backoff를 모두 더한 최악의 총 소요 시간이 상위 gateway나 load balancer의 timeout을 초과할 수 있다는 것이다.

예를 들어 상위 gateway timeout이 60초인 상황에서, read timeout 20초 × 3회 + backoff 합계 15초 = 75초 구성은 gateway가 먼저 연결을 끊는다. 배치 내부에서는 retry를 마치기 전에 gateway가 504나 timeout 응답을 반환하고, 이후 성공하더라도 호출자가 이미 없는 상황이 된다.

이 문제는 timeout 값 하나를 줄이는 것으로는 해결이 안 된다. "전체 deadline"이라는 상위 제약을 먼저 정의하고, 그 안에 connect timeout·read timeout·backoff·시도 횟수가 들어오도록 역산해야 한다.

## Timeout Budget 계산

### 기본 공식

아래 관계가 항상 성립해야 한다.

```
전체 deadline < 상위 gateway timeout

전체 deadline ≥ (connect_timeout + read_timeout) × max_attempts
              + sum(backoff_1, backoff_2, ..., backoff_(max_attempts-1))
```

지수 backoff를 사용할 때 worst-case 합계는 등비수열로 계산한다.

```
backoff(k) = min(base × 2^k, max_backoff)   (k = 0부터 시작)

sum(backoffs) = base × (2^(n-1) - 1) / (2 - 1)   단, max_backoff에 의해 상한 클리핑
```

### 예시 수치 검토

| 항목                    | 값                      |
| ----------------------- | ----------------------- |
| 상위 gateway timeout    | 60 s                    |
| 설정할 전체 deadline    | 45 s                    |
| connect timeout (1회)   | 3 s                     |
| read timeout (1회)      | 10 s                    |
| 시도당 소비 시간        | 13 s                    |
| 최대 시도 횟수          | 3 회                    |
| backoff (1회 후)        | 2 s                     |
| backoff (2회 후)        | 4 s                     |
| worst-case 총 소요 시간 | 13×3 + 2 + 4 = **45 s** |

이 구성에서 deadline 45s는 gateway timeout 60s보다 15s 여유가 있다. 그리고 worst-case 총 소요 시간이 정확히 deadline에 닿으므로, 3회를 꽉 채우면 경계 조건이 된다. 실제 구현에서는 deadline에 약간의 여유를 두거나, 다음 시도를 시작하기 전에 잔여 budget을 확인하는 방식으로 정확히 넘기지 않도록 한다.

## 설계 접근

### connect timeout과 read timeout 분리

단일 timeout 값으로 묶으면 어떤 단계에서 실패했는지 구분할 수 없다. SSL handshake 단계에서 멈춘 것인지, 연결 후 응답을 기다리다 멈춘 것인지는 원인과 대응이 다르다.

```python
import httpx

CONNECT_TIMEOUT = 3.0   # 연결 수립 + SSL handshake
READ_TIMEOUT = 10.0     # 응답 첫 바이트 수신까지
ATTEMPT_TIMEOUT = CONNECT_TIMEOUT + READ_TIMEOUT  # 단일 시도 최대 13s

client = httpx.Client(
    timeout=httpx.Timeout(
        connect=CONNECT_TIMEOUT,
        read=READ_TIMEOUT,
        write=5.0,
        pool=2.0,
    )
)
```

connect timeout이 짧으면 네트워크 레벨 문제를 빠르게 포착한다. read timeout은 외부 API 특성(응답 크기, 처리 지연)에 맞게 별도로 조정한다.

### retryable 예외만 재시도

모든 예외를 retry하면 재시도할 의미가 없는 오류(인증 만료, 스펙 불일치)에도 budget을 소진한다.

```python
RETRYABLE_HTTP_CODES = {429, 500, 502, 503, 504}

def is_retryable(exc: Exception) -> bool:
    if isinstance(exc, (httpx.ConnectError, httpx.TimeoutException)):
        return True
    if isinstance(exc, httpx.HTTPStatusError):
        return exc.response.status_code in RETRYABLE_HTTP_CODES
    return False
```

401, 403, 422처럼 재시도해도 결과가 바뀌지 않는 오류는 즉시 상위로 전파하거나 non-retryable 실패로 기록한다.

### 다음 시도 전 잔여 budget 확인

시도를 시작하기 전에 남은 시간이 한 번의 시도를 완료할 수 있는지 확인한다. 확인 없이 진행하면 deadline을 넘겨 partial 실행 상태가 된다.

```python
import time
import logging

DEADLINE = 45.0       # 전체 deadline (초)
MAX_ATTEMPTS = 3
BASE_BACKOFF = 2.0    # 첫 backoff (초)
MAX_BACKOFF = 8.0     # backoff 상한

logger = logging.getLogger(__name__)

def fetch_with_budget(url: str, params: dict) -> dict | None:
    start = time.monotonic()

    last_exc: Exception | None = None

    for attempt in range(MAX_ATTEMPTS):
        elapsed = time.monotonic() - start
        remaining = DEADLINE - elapsed

        # 현재 남은 시간이 한 번의 시도를 완료하기에 충분한지 확인
        if remaining < ATTEMPT_TIMEOUT:
            logger.warning(
                "budget_exhausted_before_max_attempts",
                extra={"attempt": attempt, "remaining_sec": round(remaining, 2)},
            )
            break

        try:
            return _do_request(client, url, params)
        except Exception as exc:
            if not is_retryable(exc):
                logger.error("non_retryable_error", extra={"error": str(exc)})
                raise
            last_exc = exc
            logger.warning(
                "retryable_error",
                extra={"attempt": attempt + 1, "error": str(exc)},
            )

        if attempt < MAX_ATTEMPTS - 1:
            backoff = min(BASE_BACKOFF * (2 ** attempt), MAX_BACKOFF)
            # backoff 후에도 한 번의 시도가 들어올 수 있는지 확인
            if time.monotonic() - start + backoff + ATTEMPT_TIMEOUT > DEADLINE:
                logger.warning(
                    "next_attempt_would_exceed_deadline",
                    extra={"attempt": attempt + 1, "backoff_sec": backoff},
                )
                break
            time.sleep(backoff)

    # 모든 시도 소진 또는 deadline 초과 → fallback
    logger.warning(
        "all_attempts_failed_returning_fallback",
        extra={
            "last_error": str(last_exc),
            "elapsed_sec": round(time.monotonic() - start, 2),
        },
    )
    return None
```

### 실패 시 안전한 fallback 반환과 기록

외부 API 호출 실패가 배치 전체 중단으로 이어지면 안 되는 경우가 많다. 해당 항목에 대해 `None`이나 미리 정의한 기본값을 반환하고, 실패 사실과 elapsed time을 구조화 로그로 남기는 방식이 현실적이다.

```python
def get_external_rate(currency_pair: str) -> float | None:
    result = fetch_with_budget(RATE_API_URL, {"pair": currency_pair})
    if result is None:
        logger.warning(
            "rate_fetch_failed_using_fallback",
            extra={"pair": currency_pair},
        )
        return None  # 호출자가 None 여부를 판단해서 처리
    return result["rate"]
```

`None`을 반환할 때는 호출자가 이를 명시적으로 처리해야 한다. `None`을 그냥 쓰면 downstream에서 예상치 못한 오류가 생긴다. 타입 힌트로 `float | None`을 선언해두면 호출 지점에서 처리를 강제할 수 있다.

## 트레이드오프

**성공률 vs. 상위 timeout 보호**

retry 횟수를 늘리면 일시적 장애에서 회복할 확률이 높아지지만, deadline도 함께 늘어나서 상위 timeout과의 여유가 줄어든다. 반대로 deadline을 짧게 잡으면 상위 timeout과 충돌할 위험이 없지만, 일시적 장애에서 회복할 시간이 줄어든다.

이 균형은 외부 API의 p99 응답 시간을 측정해서 read timeout을 정하고, 실제 retry 성공률(1회 실패 후 2회에서 성공하는 비율)을 보고 시도 횟수를 결정하는 방식으로 접근한다. 숫자 없이 "넉넉하게"로 설정한 값은 deadline 계산에서 오차가 생긴다.

**단일 전역 deadline vs. 호출별 deadline**

배치 내에서 외부 API를 여러 항목에 대해 순차 호출할 때, 전역 deadline을 사용하면 앞쪽 항목이 budget을 다 쓰면 뒤쪽 항목은 전혀 시도하지 못한다. 항목별로 deadline을 독립적으로 설정하면 각 항목의 retry 기회가 보장되지만, 총 실행 시간이 예측하기 어려워진다. 배치 총 실행 시간에 상위 제약이 있다면 항목별 deadline × 항목 수 ≤ 스케줄러 타임아웃을 별도로 확인해야 한다.

**backoff 중 sleep vs. 비동기 대기**

`time.sleep(backoff)`는 스레드/프로세스를 점유한다. 항목이 많거나 비동기 환경이라면 `asyncio.sleep(backoff)`나 backoff를 포함한 task 재예약 방식이 자원을 더 효율적으로 쓴다. 단, sleep 구현이 달라지면 아래 검증 절의 mock 방법도 함께 바뀐다.

## 검증 방법

### deadline 내에서 조기 중단

max retry 횟수를 채우기 전에 deadline이 소진되면 중단하는 경로를 단위 테스트로 검증한다. `time.monotonic`과 `time.sleep`을 mock으로 교체하면 실제 대기 없이 시간 흐름을 시뮬레이션할 수 있다.

```python
import pytest
from unittest.mock import patch, MagicMock

def test_stops_before_max_attempts_when_deadline_exceeded():
    call_count = 0
    tick = 0.0

    def fake_monotonic():
        nonlocal tick
        # 첫 호출 후 시간을 크게 앞당겨 deadline 소진을 시뮬레이션
        if call_count > 0:
            return tick + DEADLINE  # 잔여 budget = 0
        return tick

    def fake_request(client, url, params):
        nonlocal call_count
        call_count += 1
        raise httpx.ConnectError("simulated")

    with patch("time.monotonic", side_effect=fake_monotonic), \
         patch("time.sleep"), \
         patch("module.under_test._do_request", side_effect=fake_request):
        result = fetch_with_budget(URL, {})

    assert result is None
    assert call_count == 1  # deadline 초과로 1회 후 중단
```

### deadline이 상위 timeout보다 짧음을 상수 수준에서 검증

```python
UPSTREAM_GATEWAY_TIMEOUT = 60.0

def test_deadline_is_less_than_upstream_timeout():
    assert DEADLINE < UPSTREAM_GATEWAY_TIMEOUT, (
        f"DEADLINE({DEADLINE}s)이 upstream gateway timeout({UPSTREAM_GATEWAY_TIMEOUT}s) 이상임. "
        "worst-case retry 총 소요 시간이 gateway를 초과한다."
    )

def test_worst_case_fits_within_deadline():
    # max_attempts번 시도 + 중간 backoff 합계 ≤ DEADLINE
    total = MAX_ATTEMPTS * ATTEMPT_TIMEOUT
    for k in range(MAX_ATTEMPTS - 1):
        total += min(BASE_BACKOFF * (2 ** k), MAX_BACKOFF)
    assert total <= DEADLINE, (
        f"worst-case 총 소요 시간({total}s)이 DEADLINE({DEADLINE}s)를 초과한다."
    )
```

이 테스트는 상수가 바뀔 때마다 deadline 계산이 깨지지 않는지를 CI에서 자동으로 확인한다. 새 환경에 배포하거나 timeout 값을 조정할 때 수동 계산 실수를 잡아준다.

### non-retryable 응답은 재시도하지 않음

```python
def test_non_retryable_status_raises_immediately():
    call_count = 0

    def fake_request(client, url, params):
        nonlocal call_count
        call_count += 1
        response = MagicMock()
        response.status_code = 401
        raise httpx.HTTPStatusError("Unauthorized", request=MagicMock(), response=response)

    with patch("module.under_test._do_request", side_effect=fake_request):
        with pytest.raises(httpx.HTTPStatusError):
            fetch_with_budget(URL, {})

    assert call_count == 1  # 재시도 없이 즉시 실패
```

### fallback None이 반환되는 경로

```python
def test_returns_none_after_all_retries_exhausted():
    with patch("module.under_test._do_request", side_effect=httpx.ConnectError("fail")), \
         patch("time.sleep"):
        result = fetch_with_budget(URL, {})
    assert result is None
```

## 배운 것

retry 횟수를 조정하는 것은 "시도 기회를 늘린다"는 감각이지만, 실제로는 "상위 timeout과 경쟁하는 시간을 늘린다"는 의미이기도 하다. 외부 API가 transient 실패를 일으켰을 때 단순히 `stop_after_attempt(5)`로 올리면 어느 순간 gateway가 먼저 연결을 끊는 상황이 된다.

timeout budget 설계의 순서는 이렇다. 먼저 상위 gateway timeout을 확인하고, 그것보다 짧은 전체 deadline을 정한다. 그 deadline 안에 (connect timeout + read timeout) × max_attempts + backoff 합계가 들어오는지 역산한다. 맞지 않으면 시도 횟수나 backoff를 줄이거나, read timeout을 줄여야 한다.

connect timeout과 read timeout을 분리하는 것은 단순히 코드 스타일이 아니다. connect timeout 초과는 네트워크·DNS 문제이고, read timeout 초과는 외부 제공자 처리 지연이다. 두 경우의 조치와 알림 기준이 다를 수 있다. 묶어두면 원인 파악이 느려진다.

deadline을 기반으로 "다음 시도를 시작할 수 있는가"를 확인하는 코드는 로직이 1~2줄이지만, 이게 없으면 deadline을 맞춰두고도 경계 조건에서 초과한다. 회귀 테스트로 상수 관계를 CI에서 검증해두면 timeout 값 변경이 있을 때 계산 실수가 코드 리뷰가 아니라 빌드 단계에서 드러난다.
