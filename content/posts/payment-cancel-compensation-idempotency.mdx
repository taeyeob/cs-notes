## 문제 정의

결제 취소는 사용자 또는 내부 시스템이 취소 API를 직접 호출하는 command-side 흐름이다. 외부 결제사(이하 PG) 웹훅 수신 이후 상태를 맞추는 흐름과는 다르다. 웹훅 처리 패턴은 [PG 웹훅 이후 주문·결제 상태 동기화가 어긋나는 이유](./payment-webhook-state-sync)를 참고한다.

취소 command 흐름의 핵심 어려움은 세 가지다.

첫째, **동일한 취소 요청이 여러 번 들어올 수 있다.** 네트워크 재시도, UI 더블 클릭, 비동기 큐에서의 중복 실행 등이 원인이다. 각각의 호출이 독립적으로 PG에 취소를 요청하면 중복 취소나 의도하지 않은 부분취소가 발생한다.

둘째, **PG cancel API 응답 실패가 실제 취소 실패를 의미하지 않는다.** 네트워크가 끊겨서 실패 응답을 받았어도 PG 쪽에서는 이미 취소 처리를 완료한 경우가 있다. 이 상황에서 내부 상태를 "취소 실패"로 단정하고 재시도를 멈추면 PG와 내부 상태가 영구적으로 어긋난다.

셋째, **PG 상태 조회로 보정할 때도 오판 가능성이 있다.** 이전 부분취소 이력이 남아 있으면, 이번 취소가 실제로는 아직 처리되지 않았는데 "이미 취소됐다"고 잘못 판단할 수 있다.

## 실패 모드

**1. 중복 취소 요청으로 두 개의 cancel task가 PG에 동시 도달**

취소 요청을 받은 즉시 PG API를 호출하는 구조에서, 재시도나 큐 중복 실행으로 같은 결제 건에 대해 PG cancel API가 두 번 호출된다. PG에 따라 두 번째 호출이 오류를 반환하거나 이미 취소된 금액을 다시 차감하거나 전혀 다른 결과를 낼 수 있다.

**2. PG 응답 실패 → 내부 상태를 취소 실패로 고착**

PG cancel API 호출 중 타임아웃이나 네트워크 오류가 발생하면 실패 응답을 받는다. 이를 곧바로 "취소 실패"로 처리하면, PG가 실제로는 취소를 완료했음에도 내부에서는 취소되지 않은 상태로 남는다. 이후 고객은 환불이 됐다고 보고, 내부 시스템은 취소 실패로 본다.

**3. PG 상태 조회 보정 시 부분취소 이력 오판**

PG cancel API 실패 후 PG 상태 조회(retrieve/status API)로 실제 처리 여부를 확인할 때, 이전 부분취소로 잔액이 이미 줄어든 상태가 조회되면 이번 취소가 반영된 것처럼 보인다. "잔액이 0이다" 또는 "취소 이력이 있다"는 조건만으로 보정 성공을 판정하면 오판이다.

**4. PG별 상태 응답 계약 차이를 무시한 공통 추상화**

PG마다 상태 조회 API의 필드명, 취소 성공/실패 판정 기준, 부분취소 표현 방식이 다르다. 공통 추상화 레이어만 믿고 각 PG별 계약을 검증하지 않으면, 한 PG에서 "성공"으로 파싱한 응답이 다른 PG에서는 부분 처리 상태일 수 있다.

**5. 보정 실패를 성공으로 처리해서 재처리 가능성을 잃음**

상태 조회도 실패했을 때 "어차피 모르니까 성공으로 처리하자"는 판단은 위험하다. 이후에 PG 실제 상태와 내부 상태를 맞출 수단이 없어지고, 잘못된 환불 지급이나 정산 오류로 이어진다.

## 설계 접근

### 1단계: 상태 전환으로 중복 task를 막는다

취소 요청이 들어오면 PG API를 즉시 호출하기 전에 내부 결제 상태를 `CANCEL_REQUESTED`로 먼저 전환한다. 이 전환은 조건부 update와 row lock으로 원자적으로 수행해서, 동시에 들어온 중복 요청이 모두 성공하지 않도록 한다.

```
# 의사코드
def request_cancel(payment_id):
    # 조건부 update: 현재 상태가 PAID일 때만 CANCEL_REQUESTED로 전환
    updated = db.update(
        "UPDATE payment SET status = 'CANCEL_REQUESTED' WHERE id = ? AND status = 'PAID'",
        payment_id
    )
    if updated == 0:
        existing = db.get("SELECT status FROM payment WHERE id = ?", payment_id)
        if existing.status in ('CANCEL_REQUESTED', 'CANCELED'):
            return {"result": "already_in_progress"}  # 멱등 응답
        raise ConflictError("취소 불가 상태")

    # 상태 전환 성공한 경우에만 cancel task 생성
    enqueue_cancel_task(payment_id)
    return {"result": "accepted"}
```

`status = 'PAID'` 조건이 없으면 두 요청이 동시에 들어왔을 때 둘 다 통과한다. `WHERE` 절에 상태 조건을 넣는 것이 핵심이다. 이미 `CANCEL_REQUESTED`나 `CANCELED`인 경우는 동일한 결과를 반환해서 호출자가 재시도해도 안전하다.

### 2단계: cancel task는 단일 실행을 보장한다

cancel task가 큐에서 중복 실행될 수 있으므로, 실행 시작 전에 상태를 재확인한다.

```
# 의사코드
def execute_cancel_task(payment_id):
    payment = db.get_for_update("SELECT * FROM payment WHERE id = ? FOR UPDATE", payment_id)

    if payment.status != 'CANCEL_REQUESTED':
        # 이미 다른 실행이 처리했거나 상태가 바뀌었음
        return

    try:
        pg_response = pg_client.cancel(payment.pg_transaction_id, payment.amount)
        handle_cancel_response(payment_id, pg_response)
    except PGTimeoutError:
        # 응답을 못 받았을 때 → 상태 조회로 보정
        compensate_by_status_inquiry(payment_id, payment)
    except PGError as e:
        # 명확한 실패 응답 → 종류에 따라 분기
        if e.is_already_canceled():
            mark_canceled(payment_id)  # PG 이미 처리됨
        else:
            mark_cancel_failed(payment_id, reason=str(e))
```

타임아웃과 명확한 오류 응답을 구분해서 처리한다. 타임아웃은 "PG가 처리했을 수도 있다"는 불확실 상태이므로 상태 조회 보정 경로로 넘긴다.

### 3단계: PG 상태 조회 보정에 freshness 기준을 추가한다

PG 상태 조회 결과만으로 "이번 취소가 반영됐다"고 판단하면 부분취소 이력에 의해 오판할 수 있다. 핵심은 **"이번 취소 요청 이전 잔액보다 줄었는가"** 를 기준으로 삼는 것이다.

```
# 의사코드
def compensate_by_status_inquiry(payment_id, payment):
    balance_before = payment.remaining_amount  # 취소 요청 시점 스냅샷

    pg_status = pg_client.retrieve(payment.pg_transaction_id)

    cancel_amount = pg_get_cancel_amount_after(pg_status, after=payment.cancel_requested_at)
    # PG별로 판정 로직을 분리 (공통 추상화 외에 결제사별 핸들러)

    if cancel_amount >= payment.requested_cancel_amount:
        # 이번 요청분 이상이 취소됨 → 성공으로 확정
        mark_canceled(payment_id)
    elif cancel_amount > 0 and cancel_amount < payment.requested_cancel_amount:
        # 부분 반영: 오판 방지를 위해 실패로 남기고 운영 판단
        mark_cancel_failed(payment_id, reason="partial_amount_mismatch")
    else:
        # 취소 미반영 → 실패로 남김
        mark_cancel_failed(payment_id, reason="not_reflected")
```

`payment.cancel_requested_at` 이후에 발생한 취소 이력만 집계하는 로직이 필요하다. PG 상태 조회 응답에 타임스탬프가 있는 경우 이를 활용하고, 없는 경우에는 잔액 기준으로 판단한다.

### 4단계: PG별 판정 로직을 분리한다

공통 추상화는 호출 방식을 통일하는 데 쓰고, 성공/실패/부분취소 판정 기준은 결제사별로 분리한다.

```
# 의사코드
class PGAStatusJudge:
    def is_cancel_success(self, response, requested_amount):
        # PG A의 응답 필드와 상태 코드 기준
        return response["status"] == "CANCELLED" and response["refund_amount"] >= requested_amount

class PGBStatusJudge:
    def is_cancel_success(self, response, requested_amount):
        # PG B는 partialCancelList를 순회해서 합산
        canceled = sum(item["amount"] for item in response.get("partialCancelList", []))
        return canceled >= requested_amount

def get_judge(pg_code):
    return {
        "PG_A": PGAStatusJudge(),
        "PG_B": PGBStatusJudge(),
    }[pg_code]
```

PG별 응답 계약이 바뀔 때 공통 추상화를 수정하면 다른 PG에 의도치 않은 영향을 줄 수 있다. 판정 로직을 결제사별로 분리해서 변경 범위를 격리한다.

### 5단계: 보정 실패는 실패로 남긴다

상태 조회 보정도 실패했을 때 무리하게 성공 처리하지 않는다. 내부 상태를 `CANCEL_FAILED`로 남기고 다음 경로를 열어두는 것이 낫다.

- 자동 재시도: 일정 시간 후 cancel task를 다시 실행
- 운영 도구: `CANCEL_FAILED` 목록을 조회하고 PG 상태를 수동으로 확인해 처리
- 알림: 보정 실패가 발생하면 즉시 알림으로 운영자에게 전달

```
# 의사코드
def compensate_by_status_inquiry(payment_id, payment):
    try:
        pg_status = pg_client.retrieve(payment.pg_transaction_id)
        judge = get_judge(payment.pg_code)
        if judge.is_cancel_success(pg_status, payment.requested_cancel_amount):
            mark_canceled(payment_id)
        else:
            mark_cancel_failed(payment_id, reason="pg_not_reflected")
    except Exception as e:
        # 상태 조회 자체 실패 → 성공 처리 금지
        mark_cancel_failed(payment_id, reason=f"status_inquiry_failed: {e}")
        alert_ops(payment_id, "PG 상태 조회 보정 실패 - 수동 확인 필요")
```

## 트레이드오프

**조건부 update vs. select-then-update**

`WHERE status = 'PAID'` 조건을 update 쿼리에 넣으면 원자성이 보장되지만, 실패 원인(상태가 이미 바뀐 것인지, 레코드 자체가 없는 것인지)을 구분하려면 별도 조회가 필요하다. select-then-update는 구현이 명확하지만 두 쿼리 사이 경쟁 조건이 남는다. 대부분의 경우 `affected_rows == 0`이면 현재 상태를 조회해서 원인을 확인하는 패턴이 균형이 맞다.

**PG 상태 조회 보정의 복잡도**

보정 로직을 추가하면 실패 경로의 안전성이 높아지지만 코드 복잡도가 늘어난다. PG마다 상태 조회 API 특성이 다르고, freshness 판단 기준이 PG 응답 스펙에 의존한다. PG가 하나라면 공통 추상화 없이 직접 구현하는 것이 더 단순하다. PG가 여럿이라면 판정 로직 분리 없이 공통 추상화 하나로 처리하려다가 판정 오류가 생기는 경우가 많다.

**보정 실패 시 자동 재시도 vs. 운영 판단**

자동 재시도는 일시적인 PG 장애에 빠르게 대응하지만, 재시도 횟수 상한과 백오프 설계가 필요하다. 운영 판단은 안전하지만 처리가 느리다. 두 가지를 조합해서 N회 자동 재시도 후 `CANCEL_FAILED`로 확정하고 알림을 보내는 방식이 현실적이다.

**상태 조회 타이밍**

PG cancel API 실패 직후 바로 상태를 조회하면 PG 처리가 아직 반영되지 않았을 수 있다. 일정 시간(수 초~수십 초) 대기 후 조회하는 것이 더 정확하지만, 지연 시간 동안 내부 상태가 `CANCEL_REQUESTED`에 머무른다. Cloud Tasks나 Celery 등 지연 큐로 보정 task를 별도로 예약하면 실패 경로에서 동기 대기를 피할 수 있다.

## 검증 방법

- 동일한 payment_id로 취소 요청을 두 번 보냈을 때 두 번째 요청이 멱등하게 응답하는가
- 두 요청이 동시에 들어왔을 때 cancel task가 하나만 실행되는가 (DB 조건부 update의 affected_rows 확인)
- PG cancel API 타임아웃을 시뮬레이션했을 때 상태 조회 보정 경로가 실행되는가
- 보정 시 이전 부분취소 이력만 있는 상태를 성공으로 오판하지 않는가 (freshness 조건 유닛 테스트)
- PG별 판정 로직이 각 결제사 응답 스펙의 edge case(부분취소, 전액취소, 이미 취소된 경우)를 올바르게 처리하는가
- 보정 실패 시 내부 상태가 성공으로 바뀌지 않고 `CANCEL_FAILED`로 남는가
- `CANCEL_FAILED` 건을 운영 도구에서 조회하고 수동 처리하는 경로가 실제로 동작하는가

## 배운 것

취소 API는 단발성 command처럼 보이지만, 외부 PG를 거치는 순간 응답 실패 ≠ 취소 실패라는 비대칭이 생긴다. 이 비대칭을 모르고 설계하면 "실패 응답이 왔으니 취소 안 됐다"는 잘못된 단정이 PG 상태와 내부 상태의 영구적인 불일치로 굳는다.

상태 조회 보정은 이 비대칭을 해소하는 수단이지만, 보정 자체에도 freshness 기준이 없으면 오판이 생긴다. "잔액이 줄었다" 자체가 아니라 "이번 요청 전보다 줄었는가"를 물어야 한다.

설계 원칙을 요약하면 이렇다.

1. 상태를 먼저 전환하고, 전환 성공한 경우에만 PG 호출을 시도한다. 이것이 중복 task를 막는 가장 단순한 방법이다.
2. PG 응답 실패 후 무리하게 결론 내리지 않는다. 타임아웃과 명확한 실패는 다르다.
3. 보정할 때는 freshness 기준을 명시하고, 기준을 충족하지 못하면 실패로 남긴다.
4. PG마다 상태 응답 계약이 다르다. 공통 추상화는 호출 인터페이스에 국한하고, 판정 로직은 결제사별로 분리한다.
5. 보정도 실패할 수 있다. 그 경우 내부 상태를 실패로 남겨 재처리와 운영 판단 가능성을 열어둔다.

가장 위험한 순간은 "어차피 모르니까 성공으로 처리하자"는 선택을 할 때다. 불확실한 상태를 성공으로 덮으면 이후에 바로잡을 수단이 사라진다.
