## 문제 상황

`service-project`에서 돌아가는 배치 서비스가 `data-project`의 BigQuery에 저장된 분석 데이터를 쿼리해야 하는 상황이 있다. 가장 먼저 떠오르는 방법은 `data-project`에서 서비스 계정 키를 발급하고 JSON 파일을 `service-project`의 Secret Manager에 넣는 것이다.

이 방식은 쓰지 않는 게 낫다. 장기 유효 키를 여러 환경에 복사하면 키가 어디에 얼마나 퍼져 있는지 파악하기 어렵고, 키가 탈취되면 피해 범위를 즉시 확인할 수 없다. GCP는 런타임 아이덴티티를 기반으로 키 없이 교차 프로젝트 접근을 구성할 수 있다.

## 권한의 두 가지 층

BigQuery 접근에는 구분해야 할 권한이 두 개다.

- **쿼리 실행(Job) 권한**: 쿼리 잡을 어느 프로젝트에서 만들고 비용을 누가 부담할지에 대한 권한이다. `roles/bigquery.jobUser`를 **실행 주체가 속한 프로젝트**에 부여한다. 배치 서비스가 `service-project`에서 돌아간다면, 서비스의 런타임 서비스 계정(`batch-runtime-sa`)에게 `service-project` 수준으로 이 역할을 준다.
- **데이터 읽기 권한**: 실제 테이블을 읽는 권한이다. `roles/bigquery.dataViewer`를 **`data-project`의 특정 데이터셋**에 부여한다. 프로젝트 전체 수준으로 주면 접근 범위가 너무 넓어진다.

두 권한을 혼동해서 모두 `data-project` 프로젝트 수준에 주거나, 반대로 `service-project`에만 주면 권한 오류나 예기치 않은 접근 범위 문제가 생긴다.

## 데이터셋 범위를 좁혀야 한다

분석 파이프라인은 보통 `analytics_<property>`, `analytics_<env>` 같은 이름으로 여러 데이터셋을 만든다. 배치 서비스가 특정 데이터셋 하나만 읽는데, 모든 `analytics_*` 데이터셋에 `dataViewer`를 주는 것은 과도하다.

쿼리에서 실제로 참조하는 데이터셋이 어느 것인지 확인하고 그것에만 권한을 부여한다. 쿼리 SQL에 fully-qualified 테이블 이름(`data-project.analytics_<property>.events_*`)을 명시하면 어떤 데이터셋이 필요한지 명확해진다. 프로젝트 수준 grant는 나중에 데이터셋이 추가될 때 의도치 않게 접근 범위가 넓어지는 위험이 있다.

## 원본 데이터셋이 너무 넓다면 큐레이션 레이어를 만든다

원본 분석 데이터셋이 여러 팀이 공유하는 민감한 데이터를 담고 있다면, 배치 서비스가 읽어야 하는 컬럼과 파티션만 담은 뷰나 테이블을 `curated_dataset`에 만들고 그 데이터셋에만 `dataViewer`를 주는 것이 낫다.

```sql
-- data-project의 curated_dataset에 생성하는 뷰 예시
-- 배치 서비스가 필요한 컬럼과 파티션 범위만 노출한다
CREATE OR REPLACE VIEW curated_dataset.batch_input AS
SELECT
  event_date,
  event_name,
  user_pseudo_id
  -- 필요한 컬럼만 명시적으로 선택
FROM analytics_dataset.events_*
WHERE _TABLE_SUFFIX BETWEEN '20240101' AND '20241231'
```

이렇게 하면 원본 데이터셋의 스키마나 파티션 구조가 바뀌어도 배치 서비스 쪽 SQL을 건드리지 않아도 된다.

## UDF와 파생 데이터셋을 빠뜨리지 않는다

실제로 권한을 적용하다 보면 자주 놓치는 부분이 있다. 쿼리가 persistent UDF를 사용한다면, UDF가 정의된 데이터셋이 analytics 데이터셋과 다를 수 있다. 이 경우 `udf_dataset`에 대한 읽기 권한도 별도로 부여해야 한다.

확인 절차:

- 쿼리 SQL에서 `FROM`, `JOIN`, 함수 호출 부분을 모두 추출한다.
- 각각이 어느 프로젝트의 어느 데이터셋에 속하는지 파악한다.
- 참조된 데이터셋마다 `dataViewer`가 있는지 확인한다.

BigQuery의 "데이터 없음" 오류와 "권한 없음" 오류 메시지가 혼동될 수 있다. 권한 문제는 보통 `Access Denied: BigQuery BigQuery: Permission denied` 메시지로 나온다.

## 서비스 계정 임퍼소네이션을 써야 하는 경우

데이터 플랫폼 팀이 `data-project`의 쿼리 잡을 직접 소유하고 싶다면(비용 귀속, 감사 로그 분리 등), `service-project`의 `batch-runtime-sa`가 `data-project`의 서비스 계정을 임퍼소네이션하는 방식을 쓸 수 있다.

```
batch-runtime-sa (service-project)
  → roles/iam.serviceAccountTokenCreator
  → data-project의 data-platform-sa

data-platform-sa (data-project)
  → roles/bigquery.jobUser (data-project)
  → roles/bigquery.dataViewer (analytics 데이터셋)
```

이렇게 구성하면 키 발급 없이 임시 토큰으로 위임이 이루어지고, 감사 로그에 임퍼소네이션 체인이 기록된다. 단, 호출 경로가 복잡해지고 토큰 갱신 로직이 필요하다.

## 방식별 트레이드오프

**직접 IAM 부여 (데이터셋)**

- 장점: 단순, 추가 인프라 없음
- 단점: 데이터셋 범위 관리 필요

**큐레이션 뷰/테이블**

- 장점: 접근 범위 명확, 스키마 격리
- 단점: 뷰 관리 부담

**서비스 계정 임퍼소네이션**

- 장점: 비용/감사 분리, 키 없음
- 단점: 설정 복잡, 토큰 로직 추가

**브로커 잡 (데이터 플랫폼)**

- 장점: 완전한 격리, 중앙 관리
- 단점: 플랫폼 팀 의존, 레이턴시

## 검증 순서

권한을 한 번에 모두 적용하고 배치를 실행하면 어디서 막혔는지 찾기 어렵다. 단계를 나눠서 확인한다.

- **dev 환경에 먼저 적용**: 실수했을 때 영향 범위를 최소화한다.
- **최소 쿼리로 연결 확인**: `SELECT 1`이나 단순 `COUNT(*)` 쿼리로 연결과 권한을 먼저 검증한다.
- **실제 배치 쿼리 실행**: 참조하는 테이블, UDF, 파생 데이터셋까지 포함된 실제 쿼리를 돌린다.
- **다운스트림 경로 검증**: 배치가 결과를 캐시나 API에 쓴다면 그 경로까지 end-to-end로 확인한다.
- **stage/prod에 동일하게 적용**: dev에서 확인한 IAM 설정을 Terraform 등으로 코드화해서 환경 간 차이를 없앤다.

## 체크리스트

- [ ] `batch-runtime-sa`에 `roles/bigquery.jobUser`를 `service-project` 수준으로 부여했는가
- [ ] `roles/bigquery.dataViewer`를 프로젝트 전체가 아닌 특정 데이터셋에 부여했는가
- [ ] 쿼리 SQL에 fully-qualified 테이블 이름을 사용하는가
- [ ] 쿼리가 참조하는 UDF 데이터셋에도 권한이 있는가
- [ ] 서비스 계정 JSON 키를 발급·복사하지 않았는가
- [ ] dev → stage → prod 순서로 검증했는가
- [ ] IAM 설정이 Terraform 등으로 코드화되어 있는가

## 정리

서비스 계정 키를 Secret Manager에 넣는 방식의 직관적인 단순함에는 숨겨진 비용이 있다. 키 배포 범위를 추적하기 어렵고, 환경이 늘어날수록 복사본이 쌓인다. GCP의 런타임 아이덴티티와 데이터셋 수준 IAM을 조합하면 키 없이 동일한 접근을 구성할 수 있다. 쿼리 실행 권한과 데이터 읽기 권한을 분리해서 각각 올바른 프로젝트와 데이터셋 범위에 부여하는 것이 핵심이다.
