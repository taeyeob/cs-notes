## 문제 정의

"그룹별로 콘텐츠를 묶어 보여주되, 전체 활동량 기준으로 그룹 순위를 매겨달라"는 요구사항이 있다고 하자.

직관적인 첫 구현은 이렇다. 그룹별로 최신 N개 콘텐츠만 가져오고, 그 N개의 수를 집계해서 랭킹을 정한다. API 응답 크기도 작고, 쿼리도 간단해 보인다.

하지만 이 방식은 랭킹을 왜곡한다.

## 왜 bounded scan이 문제인가

최신 N개만 스캔하면 `COUNT`가 `MIN(실제 수, N)`으로 고정된다. 콘텐츠가 1,000개인 그룹과 N+1개인 그룹이 스캔 창 안에서 동점이 된다. 실제 활동량 차이를 순위에 반영할 수 없다.

유효 필터(예: 삭제 여부, 공개 상태)가 적용되면 상황은 더 나빠진다. 최신 N개 중 필터를 통과하는 수가 그룹마다 다르기 때문에, 창 크기를 키워도 정확한 수를 보장할 수 없다.

```
그룹 A: 유효 콘텐츠 500개 → 최신 N개 스캔 → COUNT = N
그룹 B: 유효 콘텐츠 N+1개 → 최신 N개 스캔 → COUNT = N
→ 랭킹 동점. 실제 차이는 무시됨.
```

## 권장 설계: 집계와 노출을 분리한다

두 가지 연산을 명확하게 분리하면 해결된다.

**1단계 — 전체 유효 후보 집계**

유효 조건(삭제되지 않음, 공개 상태 등)을 적용한 뒤 그룹별로 `COUNT(*)`를 구한다. 스캔 범위에 제한을 두지 않는다. 이 수치가 랭킹 기준이 된다.

```sql
SELECT group_id, COUNT(*) AS valid_count
FROM contents
WHERE is_deleted = false AND status = 'public'
GROUP BY group_id
ORDER BY valid_count DESC
LIMIT :page_size OFFSET :offset
```

**2단계 — 그룹 내 최신 N개 노출**

1단계에서 나온 그룹 목록을 받아, 각 그룹에서 최신 N개의 콘텐츠를 조회한다. 개념적으로는 그룹별 쿼리로 표현하지만, 실제 구현에서는 아래 "구현 방법 선택" 항목에서 설명하는 배치/윈도우/스트리밍 방식으로 N+1 비용을 제어해야 한다.

```sql
-- 개념 설명용 (그룹 하나에 대한 예시)
SELECT *
FROM contents
WHERE group_id = :group_id
  AND is_deleted = false
  AND status = 'public'
ORDER BY created_at DESC
LIMIT :n
```

노출용 쿼리에도 집계와 동일한 유효 필터를 반드시 재적용한다. 집계 단계에서 걸렀던 조건을 노출 단계에서 빠뜨리면 삭제된 콘텐츠나 비공개 항목이 노출될 수 있다.

## 구현 시 주의할 점

**필터 조건을 두 단계 모두에 적용한다**

집계 쿼리와 노출 쿼리에 동일한 유효성 조건을 각각 명시한다. 한쪽에서만 필터를 수정하면 랭킹 수치와 노출 항목이 서로 다른 모집단을 기준으로 계산된다.

**캐시 키에 필터 조건을 포함한다**

랭킹 결과를 캐싱할 때 필터 파라미터가 캐시 키에 포함되지 않으면 서로 다른 조건의 결과가 뒤섞인다.

```
cache_key = f"ranking:v1:status={status}:page={page}"
```

**동점 시 deterministic tie-breaker를 둔다**

`valid_count`가 같은 그룹이 여러 개일 때 정렬 순서가 실행마다 달라지면 페이지네이션이 깨진다. `group_id`처럼 변하지 않는 값을 보조 정렬 기준으로 추가한다.

```sql
ORDER BY valid_count DESC, group_id ASC
```

**ORM 기본 매니저와 묵시적 어노테이션을 주의한다**

Django, SQLAlchemy 등 대부분의 ORM은 기본 매니저(default manager)나 글로벌 쿼리 스코프를 통해 필터·어노테이션·조인을 자동으로 추가한다. 예를 들어 soft-delete 패턴을 기본 매니저에 심어두면 `Model.objects.all()`이 내부적으로 특정 조건을 붙인 채로 실행된다. 이 자체는 편리하지만 랭킹 집계에서는 두 가지 문제를 일으킬 수 있다.

- **의도치 않은 필터 불일치**: 집계 쿼리와 노출 쿼리에서 서로 다른 매니저를 쓰면 한쪽에서만 필터가 적용되거나 중복 적용된다.
- **대규모 스캔 시 숨겨진 비용**: `annotate()`로 집계를 추가하면 불필요한 서브쿼리나 조인이 붙어 전체 후보 집합을 스캔할 때 비용이 예상보다 커진다.

대규모 read-only 랭킹 스캔에서는 다음 중 하나를 선택한다.

1. **명시적 베이스 쿼리셋 사용**: 기본 매니저 대신 필요한 조건만 포함한 쿼리셋을 직접 구성하고, 유효성 필터(삭제 여부, 공개 상태 등)를 명시적으로 재적용한다.
2. **기본 어노테이션 우회 후 필터 재적용**: ORM의 글로벌 스코프나 기본 매니저를 우회해 가장 가벼운 쿼리셋부터 시작하고, 유효성 조건만 명시적으로 덧붙인다.

어느 방식을 택하든, ORM이 실제로 생성하는 SQL을 출력해(`print(queryset.query)` 또는 DB 슬로우 로그) 기대한 조건과 일치하는지 확인한다.

## 트레이드오프

| 항목           | bounded scan          | 전체 집계 + 로컬 제한                            |
| -------------- | --------------------- | ------------------------------------------------ |
| 랭킹 정확도    | 왜곡 가능             | 정확                                             |
| 쿼리 비용      | 낮음                  | 그룹 수 × 노출 쿼리 추가                         |
| 구현 복잡도    | 낮음                  | 두 단계                                          |
| 필터 변경 영향 | 집계/노출 불일치 위험 | 양 단계에 필터를 명시적으로 동기화·재적용해야 함 |

그룹 수가 많고 페이지당 노출 그룹 수도 많으면 2단계 노출 쿼리를 그룹별로 개별 실행하면 N+1 문제가 된다. 아래 구현 방법 중 상황에 맞는 것을 선택한다.

**구현 방법 선택**

**(a) IN 절 배치 조회**: 1단계에서 얻은 그룹 ID 목록 전체를 하나의 `IN` 절로 묶어 한 번에 조회한 뒤 애플리케이션에서 그룹별로 분류한다. 구현이 간단하고 추가 DB 기능이 필요 없다.

**(b) 윈도우 함수**: `ROW_NUMBER() OVER (PARTITION BY group_id ORDER BY created_at DESC)`로 행 번호를 붙이고 `COUNT(*) OVER (PARTITION BY group_id)`로 유효 수를 계산하면, 집계·정렬·노출 제한을 단일 쿼리로 처리할 수 있다.

```sql
-- 1) 그룹별 유효 후보 수 집계
WITH group_counts AS (
  SELECT group_id, COUNT(*) AS valid_count
  FROM contents
  WHERE is_deleted = false AND status = 'public'
  GROUP BY group_id
),
-- 2) 상위 그룹 선택 (그룹 단위 페이지네이션)
top_groups AS (
  SELECT group_id, valid_count
  FROM group_counts
  ORDER BY valid_count DESC, group_id ASC
  LIMIT :page_size OFFSET :offset
),
-- 3) 선택된 그룹 내 행에 순번 부여
ranked_rows AS (
  SELECT c.*,
    ROW_NUMBER() OVER (PARTITION BY c.group_id ORDER BY c.created_at DESC) AS rn,
    tg.valid_count
  FROM contents c
  JOIN top_groups tg ON c.group_id = tg.group_id
  WHERE c.is_deleted = false AND c.status = 'public'
)
-- 4) 그룹 내 최신 N개만 노출
SELECT *
FROM ranked_rows
WHERE rn <= :n
ORDER BY valid_count DESC, group_id ASC, rn ASC
```

이 CTE 구조는 그룹 수 기준으로 페이지네이션(`LIMIT :page_size`)을 먼저 적용한 뒤, 선택된 그룹 내에서만 행 번호를 매기고 `rn <= :n`으로 노출을 제한한다. 단순히 전체 행에 `LIMIT`을 적용하면 그룹 수가 아닌 행 수가 잘려 페이지가 잘못 구성되므로, 그룹 단위 페이지네이션은 반드시 CTE에서 먼저 처리해야 한다. 전체 후보 집합이 클 경우 group_counts 단계의 스캔 비용이 커질 수 있으므로 실행 계획을 확인한다.

**(c) 스트리밍 단일 패스**: 유효 후보 전체를 `created_at DESC` 순으로 스트리밍하면서 그룹별 카운터를 유지하고, 각 그룹에서 최신 N개를 채운 뒤에는 카운트만 진행하고 행을 버린다. DB 정렬 인덱스를 충분히 활용할 수 있을 때 전체 임시 정렬 없이 처리할 수 있다.

## 검증 체크리스트

- [ ] 집계 쿼리와 노출 쿼리에 동일한 유효 필터가 적용되어 있는가
- [ ] 콘텐츠 수가 N보다 많은 그룹과 N인 그룹의 순위가 올바르게 구분되는가
- [ ] `valid_count`가 같은 두 그룹의 정렬 순서가 매 요청마다 동일한가
- [ ] 캐시 키에 필터 파라미터가 포함되어 있는가
- [ ] 콘텐츠가 삭제되거나 비공개로 전환될 때 집계 수치도 즉시 반영되는가
- [ ] ORM이 생성하는 SQL을 실제로 출력해서 의도치 않은 `JOIN`이나 중복이 없는지 확인했는가

회귀 테스트는 픽스처로 고정해두는 것이 유리하다. 그룹 A의 유효 수가 그룹 B보다 많을 때 순위가 A > B로 나오는 케이스, 경계값(N개, N+1개)에서 순위가 갈리는 케이스를 각각 단위 테스트로 확보한다. 필터 조건이 바뀔 때마다 이 테스트가 먼저 실패해서 알려준다.

## 배운 것

랭킹 왜곡은 쿼리 결과가 틀렸기 때문이 아니라, 쿼리 범위가 목적과 어긋났기 때문에 생긴다. 응답에 담길 항목 수와 순위 기준이 되는 수를 같은 쿼리로 동시에 해결하려 하면 어느 쪽도 정확하지 않다. 두 목적을 분리하고, 필터 조건을 양쪽에 일관되게 적용하고, tie-breaker로 정렬을 고정하는 것이 이 유형의 API를 안정적으로 만드는 핵심이다.

ORM 기본 매니저나 글로벌 스코프가 묵시적으로 추가하는 필터·어노테이션도 예상치 못한 랭킹 오차의 원인이 된다. 집계 쿼리를 작성할 때는 ORM이 생성하는 실제 SQL을 출력해 의도한 조건만 포함되어 있는지 반드시 검증한다.
