## 문제 정의

배치가 캐시를 미리 채우고 API가 그걸 읽는 구조는 단순해 보인다. 그런데 막상 세팅하다 보면 "어느 서비스가 이 캐시의 writer이고 어느 서비스가 reader인가"가 암묵적으로 흐릿해지는 순간이 생긴다. 관리 목적의 백엔드가 같은 캐시 레이어에 접근하더라도, read path가 아니라면 writer/reader 관계에 포함시켜선 안 된다. 이 경계가 흐려지면 key 설계나 payload 검증 단계에서 방향을 잃는다.

## 먼저 고정해야 할 계약

배치 워밍 구조에서 구현 전에 확정해야 하는 것은 세 가지다.

**Writer와 Reader 지정.** 배치가 writer, 사용자-facing API가 reader다. 관리 목적의 서비스가 같은 스토리지에 접근하더라도, 그 서비스는 캐시 계약의 일부가 아니다. writer와 reader를 한 문장으로 쓸 수 없으면 설계를 다시 본다.

**Cache key 기준.** Reader가 실제로 조회하는 key 패턴을 먼저 정한다. 예:

```
entity:list:page:{page}:size:{size}
entity:list:sort:{sort_key}:page:{page}:size:{size}
```

Writer는 reader와 동일한 캐시 추상화(같은 클라이언트, 같은 prefix, 같은 serializer)를 통해 warm한다. "배치가 쓴 key"와 "API가 읽는 key"가 달라지는 순간 warm이 무의미해진다.

**Payload shape.** Reader의 serializer가 정상 응답을 만드는 것과 동일한 shape으로 배치가 payload를 저장해야 한다. 이 shape이 곧 public API 응답의 계약이 된다.

## Cache hit path의 함정

API가 캐시에서 응답을 반환할 때, 통상적인 serializer 검증을 다시 통과하지 않는 경우가 많다. 즉, 배치가 저장한 payload가 그대로 API 응답으로 나간다.

이 구조에서 두 가지 위험이 있다.

첫째, 배치가 분석 지표(예: 페이지뷰, 클릭수)를 정렬 기준으로만 쓰려 했는데 payload에 포함시켜버리면, 그 필드가 의도치 않게 공개 API 응답에 노출된다. 새 필드는 명시적인 스펙 변경으로만 추가한다.

둘째, 배치가 warm하는 payload shape이 reader의 정상 경로 응답과 조금이라도 다르면, 클라이언트는 캐시가 hit일 때와 miss일 때 다른 구조를 받게 된다. 이런 불일치는 캐시 히트율이 낮은 초기에는 잘 드러나지 않는다.

## 페이지네이션 범위와 데이터 소스 분리

**첫 페이지만 warm하는 실수.** 목록 API에 페이지네이션이 있을 때, page 0만 warm하면 page 1부터 캐시 미스가 발생해 정렬 결과가 섞이거나 실시간 조회 결과와 혼재된다. 전체 서비스할 페이지 범위를 배치에서 한 번에 채워야 한다.

**지표별 데이터 소스 분리.** 정렬 기준으로 사용하는 지표가 여러 개라면, 각 지표의 데이터 출처를 명확히 분리한다. 예를 들어 "판매량"과 "조회수"는 집계 파이프라인이 다를 수 있다. 하나의 배치 job에서 이 둘을 같은 소스에서 가져오면, 소스가 바뀌었을 때 한꺼번에 영향을 받는다. 지표별로 소스를 분리해 두면 교체나 디버깅이 쉬워진다.

## 검증 방법

### 1. Cache key/payload 계약 검증

로컬이나 개발 환경에서 배치 런타임을 완전히 재현하지 못해도, cache contract는 검증할 수 있다. reader가 실제로 쓰는 key로 set → get을 확인하고, get한 payload가 reader의 정상 응답 shape과 같은지 비교한다.

```python
# 배치가 set
cache.set("entity:list:page:0:size:20", payload)

# reader가 get
result = cache.get("entity:list:page:0:size:20")
assert result["items"][0]["id"] == expected_first_id
assert "analytics_metric" not in result["items"][0]  # 내부 지표 노출 방지
```

### 2. API 응답 검증

실제 API 호출로 cache hit 응답을 확인한다. 체크 포인트:

- 첫 항목이 정렬 기준에 맞는 entity인가
- 메타(total_count, total_pages)가 정확한가
- page 0뿐 아니라 page 1, 마지막 page 등 경계도 hit하는가
- cache miss로 폴백했을 때와 응답 구조가 동일한가

### 3. 배치 실행 결과 로깅

배치 job은 실행 후 processed / skipped / errors / duration 같은 집계를 남긴다. 이 숫자가 예상 범위를 벗어나면 warm이 불완전하게 끝난 것이다. 단순히 job이 완료됐는지가 아니라, 기대한 page 수만큼 실제로 set이 이뤄졌는지를 확인한다.

## 배운 것

배치 캐시 워밍에서 가장 많이 놓치는 것은 "배치가 쓴 것"과 "API가 읽는 것"이 실제로 같은 key와 shape인지 확인하는 단계다. 그 확인이 빠지면 warm은 했지만 hit이 안 되거나, hit은 됐지만 shape이 달라 클라이언트가 오작동하는 상황이 만들어진다.

계약을 먼저 고정하는 순서는 이렇다: writer/reader 지정 → reader 기준 key 패턴 정의 → payload shape 합의 → 페이지 범위 결정 → 검증. 구현 전에 이 다섯 가지가 문서화되어 있으면, 배치와 API 서비스가 독립적으로 개발되어도 연결 지점에서 충돌이 생기지 않는다.
