## 문제 정의

Django에서 `managed = False`로 선언된 모델은 마이그레이션 대상에서 제외된다. 레거시 테이블이나 여러 서비스가 공유하는 테이블을 읽기 전용으로 참조할 때 흔히 쓰는 패턴이다. 문제는 실제 테이블이 변경되어도 Django ORM 모델에는 그 변화가 자동으로 반영되지 않는다는 점이다.

이 간극이 드러나는 방식은 보통 다음과 같다. 특정 API를 구현하는 도중 CI 파이프라인에서 테스트가 실패하기 시작한다. 로컬에서는 재현되지 않는다. 에러 메시지를 보면 DB 쪽에서 `NOT NULL constraint failed` 혹은 `column "weight_index" of relation does not exist` 같은 메시지가 나온다. 소스를 보면 해당 컬럼이 ORM 모델에 없거나, factory가 그 필드를 생성하지 않는다.

이것이 unmanaged 모델 스키마 드리프트다.

## unmanaged 모델이 드리프트하는 이유

`managed = True`인 모델은 `makemigrations` / `migrate`로 DB와 코드를 동기화한다. 하지만 `managed = False` 모델은 그 흐름 밖에 있다. DB 스키마를 바꾸는 주체가 Django가 아닌 다른 서비스이거나 DBA가 직접 DDL을 실행하는 경우, Django 코드베이스에는 그 변경이 전혀 반영되지 않는다.

드리프트가 발생하는 주요 경로는 두 가지다.

- **컬럼 추가**: 다른 팀이나 서비스에서 기존 테이블에 NOT NULL 컬럼을 추가하면, Django 모델에는 그 필드가 없는 상태가 된다. 읽기 쿼리는 문제없이 통과하지만, INSERT 경로(테스트에서 factory로 레코드를 생성하는 경우 포함)에서 DB 제약 조건 위반이 발생한다.
- **컬럼 삭제 또는 변경**: ORM 모델에는 있지만 실제 테이블에는 없는 필드가 생기거나, 타입 불일치가 생긴다.

로컬 개발 환경에서 재현이 안 되는 이유는 대부분 로컬 DB가 프로덕션 스키마와 동기화되어 있지 않기 때문이다. CI 환경에서는 마이그레이션을 새로 적용하거나 픽스처를 통해 최신 스키마를 사용하기 때문에 불일치가 먼저 드러난다.

## CI가 먼저 잡은 이유

CI 파이프라인에서 테스트 DB를 어떻게 구성하느냐에 따라 드리프트 감지 시점이 달라진다. 일반적으로 세 가지 방식이 있다.

1. `migrate`로 Django 마이그레이션을 그대로 적용: managed 모델만 다루므로 unmanaged 테이블은 생성 자체가 안 된다. 별도로 DDL을 실행하거나 픽스처를 써야 한다.
2. 덤프된 스키마를 직접 로드: 프로덕션에 가까운 DDL을 CI에서 그대로 사용하면 최신 컬럼 추가가 반영된다.
3. 테스트별 픽스처로 테이블 생성: 픽스처가 최신 스키마를 따르면 NOT NULL 제약 조건도 포함된다.

CI 환경이 방식 2나 3이고 로컬이 방식 1이라면, 새 컬럼이 추가된 시점부터 CI에서만 실패가 발생한다. 이 구조 자체는 올바른 신호를 보내고 있는 것이다.

## 어디를 고쳐야 하는가: 판단 기준

테스트가 실패했을 때 선택지는 크게 세 가지다.

1. **ORM 모델에 필드를 추가한다**: 실제 테이블 스키마와 모델을 일치시킨다.
2. **factory/fixture에서 해당 컬럼에 기본값을 채운다**: 모델은 그대로 두고 테스트 생성 경로만 수정한다.
3. **테스트 DB 구성을 바꾼다**: 해당 제약 조건을 테스트에서 제거한다.

판단 기준은 다음 질문으로 좁힐 수 있다.

> 이 필드는 실제로 읽거나 쓸 수 있어야 하는가?

예라면 모델에 추가해야 한다. 서비스 코드가 언제든 해당 컬럼을 조회하거나 기록해야 한다면, ORM이 그 필드를 모른다는 것은 기술적 부채다. factory 수정은 ORM이 모르는 필드를 DB에 강제로 밀어 넣는 우회책이 되어버린다.

반면 해당 필드가 완전히 다른 서비스 도메인에 속하고, 이 서비스에서는 읽지도 쓰지도 않는다면, factory에서 기본값을 채우는 방식이 합리적일 수 있다. 다만 이 경우에도 테이블에 NOT NULL 컬럼이 있다는 사실은 어딘가에 문서화해 두는 것이 좋다.

방식 3(테스트 DB 제약 조건 제거)은 가장 피해야 한다. CI 환경을 프로덕션과 멀어지게 만들고, 이후에 진짜 스키마 문제가 생겨도 테스트가 통과해버린다.

## 트레이드오프

**모델에 필드 추가(방식 1)**

- 장점: ORM과 DB가 일치한다. `inspectdb`나 코드 리뷰에서 스키마 전체를 파악할 수 있다. 실수로 누락 필드를 쓰는 버그를 타입 수준에서 예방한다.
- 단점: 공유 테이블이라면 필드가 늘어날 때마다 Django 코드도 업데이트해야 한다. 다른 서비스가 자주 DDL을 바꾸는 환경이라면 유지 비용이 생긴다.

**factory/fixture 기본값(방식 2)**

- 장점: 모델 변경 없이 빠르게 테스트를 통과시킬 수 있다.
- 단점: ORM이 모르는 필드를 우회로 채우는 것이라 코드를 읽는 사람에게 혼란을 준다. 이후에 그 필드를 실제로 써야 할 때 또 다른 수정이 필요하다.

## 검증 체크리스트

unmanaged 모델과 관련된 변경 혹은 테스트 실패가 있을 때 아래를 확인한다.

- 실제 테이블 DDL과 Django 모델 필드 목록을 나란히 비교했는가
- NOT NULL 컬럼 중 ORM 모델에 없는 것이 있는가
- 해당 필드를 서비스 코드에서 실제로 읽거나 쓰는 경로가 있는가
- factory가 그 필드를 생성하는가, 생성하지 않는다면 이유가 명확한가
- CI 테스트 DB 구성이 프로덕션 스키마를 따르고 있는가

## 배운 것

`managed = False` 모델은 마이그레이션에서 보이지 않기 때문에 스키마 드리프트가 조용히 쌓인다. CI가 실패 신호를 보낸다면, 그것은 factory나 테스트를 고치라는 신호가 아니라 모델 표현이 실제 DB와 달라졌다는 신호다.

수정 방향을 정할 때는 "어떻게 하면 테스트를 빠르게 통과시킬 수 있는가"보다 "이 모델이 실제 테이블을 정확하게 표현하고 있는가"를 먼저 물어야 한다. 우회책은 테스트를 통과시키지만, 다음 번 드리프트를 더 늦게 발견하게 만든다.
