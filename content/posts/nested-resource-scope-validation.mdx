## 문제: path parameter는 계약이지, 검증이 아니다

`/parents/{parent_id}/children/{child_id}/` 같은 nested route를 설계할 때, `parent_id`와 `child_id`가 path에 있으면 자연스럽게 "child가 parent 안에 있다는 게 보장되겠지"라고 생각하기 쉽다.

실제로는 그렇지 않다. path parameter는 caller의 의도를 표현하는 계약이고, 그 계약이 DB 조회에서도 지켜지는지는 ORM 조건을 어떻게 작성하느냐에 달려 있다.

더 까다로운 부분은 child 자체만 확인하는 것도 충분하지 않다는 점이다. child가 참조하는 related_group 같은 FK 연결 객체도 같은 parent에 속하는지 확인해야 한다.

## 위험한 구현 패턴

아래 코드는 얼핏 보면 문제없어 보인다.

```python
child = Child.objects.select_related("related_group").get(
    id=child_id,
    parent_id=parent_id,
)
```

`child.parent_id == parent_id` 조건은 맞다. 그런데 `child.related_group.parent_id`는 확인하지 않는다. `select_related`는 JOIN을 미리 실행해서 N+1을 막아주는 성능 최적화이지, 보안이나 데이터 정합성 조건이 아니다.

legacy 데이터, 수동 보정 작업, 혹은 과거 버그로 인해 `child.parent_id`와 `child.related_group.parent_id`가 서로 다른 parent를 가리키는 상황이 생길 수 있다. 위 코드는 child가 조회되면 related_group까지 그냥 노출한다.

## 조회 조건 보강

`related_group__parent_id=parent_id` 조건을 함께 걸면 child와 related_group이 같은 parent에 속하지 않으면 404가 난다.

```python
try:
    child = Child.objects.select_related("related_group").get(
        id=child_id,
        parent_id=parent_id,
        related_group__parent_id=parent_id,
    )
except Child.DoesNotExist:
    raise Http404
```

조건이 하나 늘어났지만 의미는 명확하다. "이 parent 스코프 안에 있는 child이면서, child가 참조하는 related_group도 같은 parent 스코프 안에 있어야 한다."

`select_related`는 그대로 두어도 된다. 성능 최적화 역할은 여전히 하고, 정합성 조건은 `get()` 인자로 별도로 명시한다.

## 응답 필드의 출처를 하나로 고정하기

serializer를 작성할 때 같은 의미의 필드가 여러 경로에서 올 수 있으면 혼선이 생긴다. 예를 들어 parent 이름을 `child.parent.name`에서 가져올 수도 있고, `child.related_group.parent.name`에서 가져올 수도 있다.

두 값이 일치한다는 보장이 없다면, 특정 source 하나를 정책으로 고정하는 게 낫다.

```python
class ChildDetailSerializer(serializers.ModelSerializer):
    # parent 이름은 child.parent에서만 가져온다
    parent_name = serializers.CharField(source="parent.name")
    group_name = serializers.CharField(source="related_group.name")

    class Meta:
        model = Child
        fields = ["id", "parent_name", "group_name"]
```

source를 명시하면 테스트도 단순해진다. "parent.name이 바뀌면 응답의 parent_name이 바뀐다"는 것만 검증하면 된다. fallback 로직이나 값 합성이 없으면 예외 케이스도 줄어든다.

## 테스트 전략

세 가지 케이스를 커버해야 한다.

```python
def test_정상_child_조회(self):
    # child.parent_id == parent_id, related_group.parent_id == parent_id
    response = self.client.get(f"/parents/{self.parent.id}/children/{self.child.id}/")
    assert response.status_code == 200

def test_다른_parent의_child는_404(self):
    # child.parent_id != parent_id
    other_child = ChildFactory(parent=self.other_parent)
    response = self.client.get(f"/parents/{self.parent.id}/children/{other_child.id}/")
    assert response.status_code == 404

def test_related_group이_다른_parent에_속한_비정상_데이터도_404(self):
    # child.parent_id == parent_id지만 child.related_group.parent_id != parent_id
    mismatched_group = RelatedGroupFactory(parent=self.other_parent)
    broken_child = ChildFactory(parent=self.parent, related_group=mismatched_group)
    response = self.client.get(f"/parents/{self.parent.id}/children/{broken_child.id}/")
    assert response.status_code == 404
```

세 번째 케이스가 핵심이다. 이 케이스가 없으면 조회 조건에 `related_group__parent_id` 누락된 코드도 테스트를 통과한다.

## 트레이드오프

`related_group__parent_id` 조건을 추가하면 child.parent_id는 맞지만 related_group.parent_id가 어긋난 데이터는 이 API를 통해 접근할 수 없게 된다. legacy 데이터나 수동 보정 과정에서 생긴 불일치 행이 숨겨지는 효과다.

이를 너무 엄격한 처리라고 볼 수도 있다. 그러나 nested route는 caller에게 "당신은 이 parent 스코프 안에 있는 데이터만 본다"는 계약을 제공한다. related_group이 다른 parent에 속한다면, 그 데이터는 이 스코프 밖의 정보를 포함한다.

fail closed, 즉 모호하면 404를 내는 것이 맞다. 불일치 데이터를 노출하는 것보다 숨기는 게 낫고, 불일치 자체는 별도의 데이터 정합성 점검이나 마이그레이션으로 처리해야 할 문제다.

## 배운 것

nested resource를 설계할 때는 응답 필드가 건너가는 모든 FK 관계를 path scope로 묶어야 한다. child 자체의 parent_id만 확인하고 끝내면, child가 참조하는 객체들이 조용히 스코프 밖 데이터를 끌어들일 수 있다.

조회 조건을 작성할 때 "이 필드를 serializer가 노출한다면, 그 필드의 출처도 같은 parent에 속하는지 조건으로 걸었는가"를 체크리스트로 가져가면 이 종류의 버그를 사전에 잡을 수 있다.
