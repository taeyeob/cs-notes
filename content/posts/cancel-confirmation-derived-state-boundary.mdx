## 문제 정의

외부 취소 서비스를 경유하는 주문 취소 흐름에는 내부 처리만으로 끝나는 흐름과 다른 비대칭이 있다.

취소 요청이 들어왔을 때 시스템이 할 수 있는 일은 두 가지뿐이다. 요청을 수락했다는 사실을 기록하거나, 외부 서비스에 취소를 요청한 뒤 그 결과를 기다리는 것이다. 외부 서비스가 성공 응답을 돌려주기 전까지 취소가 "실제로 완료됐다"고 단정할 수 없다.

그런데 이 두 단계 사이에 내부 파생 상태를 갱신하는 로직이 끼어드는 경우가 있다. 파생 상태란 주문에 연결된 혜택 자격, 참여자 행(row), 카운터, JSON 스냅샷, 활성 플래그처럼 주문 자체가 아니라 주문으로부터 유도된 상태를 말한다. 검토 과정에서 자주 보이는 패턴은 이렇다.

```python
# 문제가 있는 흐름 (의사코드)
def cancel_order(order_id, forced=False):
    order = Order.objects.get(id=order_id)
    order.status = "CANCEL_REQUESTED"
    order.save()

    # 아직 외부 취소 확정 전인데 파생 상태를 이미 갱신
    sync_benefit_entitlement(order)  # ← 시점 오류

    result = external_cancel_service.cancel(order.external_ref)
    if result.success:
        order.status = "CANCELED"
        order.save()
```

`sync_benefit_entitlement`가 요청 수락 시점에 호출되면, 외부 취소가 나중에 실패하더라도 파생 상태는 이미 회수된 채로 남는다. 반대로 강제 취소 흐름에서 파생 상태 동기화를 빠뜨리면 주문은 취소됐는데 혜택 자격이 그대로 살아 있는 불일치가 생긴다.

## 세 가지 상태 단계

취소 흐름에는 뚜렷하게 구분되는 세 단계가 있다.

| 단계                                                    | 의미                                                         | 이 단계에서 안전한 것                                 |
| ------------------------------------------------------- | ------------------------------------------------------------ | ----------------------------------------------------- |
| **요청 수락(request-accepted)**                         | 취소 요청이 접수됐고 외부 서비스 호출을 준비 중              | 주문 상태를 `CANCEL_REQUESTED`로 전환, 취소 task 생성 |
| **외부 효과 확정(external-effect-confirmed)**           | 외부 취소 서비스가 성공 응답을 반환했거나 콜백으로 확인됨    | 주문 상태를 `CANCELED`로 전환, 파생 상태 동기화 시작  |
| **로컬 프로젝션 동기화(local-projection-synchronized)** | 파생 상태(혜택, 참여자, 카운터 등)가 취소 기준으로 반영 완료 | 이후 조회에서 일관된 상태 노출                        |

각 단계는 서로 다른 불변 조건(invariant)을 가진다. 요청 수락은 "취소를 시도하겠다"는 의도일 뿐이다. 외부 효과 확정은 "외부 시스템이 취소를 실행했다"는 사실이다. 로컬 동기화는 "내부 파생 상태가 그 사실을 반영했다"는 완료다.

단계를 건너뛰거나 순서를 바꾸면 불일치가 생긴다.

## 설계 접근

### 외부 성공 확인 후에만 파생 상태를 동기화한다

파생 상태 갱신 호출은 외부 취소 성공 응답을 받은 이후 경로에만 위치해야 한다. 요청 수락 경로에는 파생 상태를 건드리는 코드가 없어야 한다.

한 작업에서는 강제 취소(forced cancel) 경로와 일반 취소 요청 경로를 분리한 뒤, 파생 상태 동기화를 강제 취소 성공 확인 이후 블록에만 배치하는 방식으로 수정했다. 일반화하면 이렇다.

```python
# 수정된 흐름 (의사코드)
def execute_cancel(order_id, forced=False):
    # 외부 API 호출 전: 락 없이 상태만 확인
    order = Order.objects.get(id=order_id)

    if order.status != "CANCEL_REQUESTED":
        return  # 중복 실행 방어

    # 외부 서비스에 취소 요청 — 트랜잭션/락 바깥에서 수행
    result = external_cancel_service.cancel(order.external_ref)

    if not result.success:
        order.status = "CANCEL_FAILED"
        order.save(update_fields=["status"])
        return

    # 외부 성공 확인 후에만 writer 트랜잭션을 시작하고 락을 재취득
    with transaction.atomic(using="writer"):
        order = Order._base_manager.using("writer").select_for_update().get(id=order_id)
        if order.status != "CANCEL_REQUESTED":
            return  # 락 재취득 후 상태 재확인 — 중복 실행 방어
        order.status = "CANCELED"
        order.canceled_at = result.confirmed_at
        order.save(update_fields=["status", "canceled_at"])

        sync_derived_state(order)  # 이 안에서 파생 상태 갱신
```

요청 수락 단계와 외부 효과 확정 단계를 코드 경로로 명확히 나누는 것이 핵심이다.

### 로컬 업데이트를 단일 writer 트랜잭션에 묶는다

주문 필드 업데이트와 파생 상태 동기화는 하나의 트랜잭션 안에서 함께 처리해야 한다. 두 작업을 분리하면 주문은 `CANCELED`로 됐는데 파생 상태 동기화가 실패해 중간 상태로 굳는 경우가 생긴다.

또한 트랜잭션 안에서 갱신 대상 행을 잠가야 한다. 파생 상태가 참여자(participant)나 프로젝션 행을 포함한다면 해당 행도 함께 잠근다.

```python
def sync_derived_state(order):
    # 파생 상태에 해당하는 행을 writer DB에서 잠근다
    participants = list(
        Participant._base_manager.using("writer")
        .select_for_update()
        .filter(order=order, is_active=True)
    )

    for p in participants:
        p.entitlement_count = 0
        p.entitlement_snapshot = {}
        p.is_active = False

    Participant._base_manager.using("writer").bulk_update(
        participants,
        ["entitlement_count", "entitlement_snapshot", "is_active"]
    )
```

한 트랜잭션 안에서 주문 행과 파생 행을 함께 잠그고 갱신하면, 동시 접근이 있더라도 어느 한 쪽만 바뀐 상태가 외부에 노출되지 않는다.

### ORM 기본 매니저의 필터를 의식한다

락을 걸기 위해 행을 재조회할 때(lock re-read) ORM 기본 매니저가 어떤 필터를 적용하는지 확인해야 한다.

일반화하면 이렇다. 비즈니스 목록 조회용 매니저(objects)가 `is_active=True` 또는 특정 상태 필터를 기본으로 포함하고 있으면, `CANCELED` 상태로 막 전환된 행을 재조회할 때 그 행이 필터에 걸려 `DoesNotExist`가 발생한다.

```python
# 위험: 기본 매니저에 상태 필터가 있으면 락 재취득 실패
participant = Participant.objects.select_for_update().get(id=pid)
# objects가 is_active=True만 반환하도록 설정됐다면,
# 방금 is_active=False로 바꾼 행은 여기서 조회되지 않는다.

# 안전: PK 기반 락 경로에는 필터 없는 매니저를 명시적으로 사용한다
# Django 내장 _base_manager 또는 모델에 직접 정의한 all_objects 매니저를 쓴다
participant = Participant._base_manager.select_for_update().get(id=pid)
```

취소 흐름처럼 상태가 전환 중인 행을 잠가야 하는 경우에는 비즈니스 필터를 적용하는 매니저 대신, 기본 QuerySet 매니저(또는 `using()` 기반 직접 쿼리)를 명시적으로 선택해야 한다. 이 선택이 암묵적이면 테스트 환경에서는 통과하다가 실 데이터에서만 실패하는 패턴이 된다.

### 외부 성공 이후 로컬 동기화 실패는 다른 실패 모드다

외부 취소 서비스는 성공했지만 로컬 트랜잭션이 롤백된 경우는 취소 요청 실패와 다른 문제다. 외부에서 이미 취소가 실행된 상태에서 내부 상태만 이전으로 되돌려지므로, 재시도 없이 방치하면 영구 불일치가 된다.

이 실패 모드에는 별도의 처리 방침이 필요하다.

- 로컬 동기화 실패를 `SYNC_FAILED` 같은 별도 상태로 기록해 외부 성공과 분리한다.
- 자동 재시도 경로를 만들어 외부 확정 시각을 기준으로 로컬 동기화를 재시도한다.
- 재시도도 실패하면 운영자 알림과 수동 보정 경로를 열어둔다.

외부 취소 성공 이후에는 "외부 취소를 재시도"하는 것이 아니라 "로컬 동기화를 재시도"해야 한다는 점이 이 단계의 핵심 불변 조건이다.

## 파생 상태의 구성 요소

파생 상태는 단일 필드가 아니라 여러 형태로 분산돼 있는 경우가 많다.

- **카운터**: 주문 단위 또는 참여자 단위의 수량 합계
- **JSON 스냅샷**: 취소 시점 자격 정보를 직렬화해 저장한 필드
- **참여자/프로젝션 행**: 주문과 연결된 개별 행의 활성 플래그, 상태 값
- **레거시 키 변형**: 구형 데이터에서 외래키가 `None`이거나 다른 컬럼에 저장된 케이스

이 모두를 한 트랜잭션에서 함께 갱신할 때 레거시 `None` 키 케이스를 빠뜨리면, 구형 데이터에서만 파생 상태가 남는 불일치가 생긴다. 동기화 로직을 작성할 때는 외래키가 비어 있거나 다른 경로로 연결된 행까지 명시적으로 처리해야 한다.

행 수가 많다면 per-row N+1 update 대신 `bulk_update`나 조건부 `UPDATE ... WHERE` 쿼리로 묶는다.

## 테스트 커버리지

취소 흐름의 테스트는 외부 API 목(mock) 응답 경우의 수만큼 분기해야 한다.

| 테스트 케이스                     | 검증 포인트                                                     |
| --------------------------------- | --------------------------------------------------------------- |
| 요청 수락 단독 경로(외부 호출 전) | 파생 상태가 갱신되지 않는가                                     |
| 강제 취소 외부 성공               | 주문 상태 + 파생 상태 모두 갱신되는가                           |
| 강제 취소 외부 실패               | 주문 상태가 `CANCEL_FAILED`로 남고, 파생 상태가 갱신되지 않는가 |
| 로컬 동기화 중 예외 발생          | 주문 필드와 파생 상태가 함께 롤백되는가 (반쪽 커밋 없음)        |
| 부분 취소 경로                    | 카운터와 스냅샷이 부분 취소 기준으로 갱신되는가                 |
| 전량 취소 경로                    | 활성 플래그가 비활성으로 전환되는가                             |
| 레거시 `None` 키 케이스           | 구형 데이터에서도 동기화 로직이 오류 없이 실행되는가            |

"요청 수락 단독 경로에서 파생 상태가 갱신되지 않는가" 테스트는 빠지기 쉽다. 이 케이스가 없으면 시점 오류를 코드 리뷰 없이 감지할 수 없다.

## 검증 체크리스트

취소 흐름을 수정하거나 리뷰할 때 아래 항목을 순서대로 확인한다.

1. **호출 지점 감사**: 파생 상태 갱신 함수가 호출되는 위치를 모두 찾는다. 외부 성공 경로 이외의 위치에 있는 호출이 있는가?
2. **상태 전환 행렬**: 요청 수락 → 외부 효과 확정 → 로컬 동기화 각 단계에서 허용되는 상태 전환을 표로 정리하고, 허용되지 않는 조합이 코드에서 막히는지 확인한다.
3. **트랜잭션 경계 확인**: 주문 필드 갱신과 파생 상태 동기화가 같은 `transaction.atomic` 블록 안에 있는가?
4. **락·DB 라우팅 확인**: 재조회 락 경로에서 쓰는 매니저가 무엇인가? 비즈니스 필터 매니저가 취소 중인 행을 걸러내지 않는가? writer DB를 명시적으로 지정했는가?
5. **롤백 테스트**: 로컬 동기화 중 예외를 강제 발생시켰을 때 주문과 파생 상태가 함께 롤백되는가?
6. **요청 수락 경로 비동기화 테스트**: 외부 서비스 호출 없이 요청만 수락했을 때 파생 상태가 변하지 않는가?
7. **외부 성공 후 로컬 실패 처리**: 이 실패 모드를 기록하고 재시도·보정하는 경로가 있는가?

## 트레이드오프

**파생 상태를 단일 트랜잭션에 묶는 비용**

취소 관련 행이 많을수록 트랜잭션이 길어지고 락 경합이 늘어난다. 파생 상태 동기화가 느린 경우라면 트랜잭션을 짧게 유지하기 위해 주문 상태 전환만 먼저 커밋하고, 파생 동기화를 별도 재시도 가능한 task로 분리하는 방법도 있다. 이 경우 주문 상태와 파생 상태가 짧은 시간 동안 불일치 상태로 노출될 수 있다는 점을 명시적으로 결정해야 한다.

**ORM 매니저 분기 복잡도**

비즈니스 필터 매니저와 락용 기본 매니저를 구분하면 실수 가능성이 생긴다. 락 경로에서 잘못된 매니저를 쓴 경우 테스트에서 재현하기 어렵다. 락 전용 헬퍼 메서드를 별도로 두거나, 명명 규칙으로 두 매니저의 의미를 명확히 구분하는 것이 유지보수에 유리하다.

**레거시 키 처리 비용**

구형 데이터의 `None` 키나 다른 외래키 경로를 처리하는 코드를 추가하면 동기화 로직이 분기된다. 이 분기가 많아지면 가독성이 떨어진다. 일반화하면, 레거시 데이터 처리 분기는 독립된 헬퍼로 분리하고 각 분기에 대해 명시적인 테스트 케이스를 유지하는 것이 낫다.

## 배운 것

취소의 정확성은 "취소 API가 OK를 반환했는가"가 아니라 "이 단계에서 어떤 도메인 효과를 발행해도 안전한가"로 판단해야 한다.

외부 취소 서비스를 거치는 흐름에서 도메인 효과를 발행해도 안전한 시점은 외부 효과가 확정된 이후다. 요청 수락은 의도의 기록이지 효과의 시작이 아니다.

설계 원칙을 요약하면 이렇다.

1. 파생 상태 갱신은 외부 성공 확인 이후 경로에만 위치시킨다.
2. 주문 필드와 파생 상태를 같은 writer 트랜잭션에서 함께 잠그고 함께 갱신한다.
3. 락 재취득 경로에서 ORM 매니저가 취소 중인 행을 필터로 걸러내지 않는지 명시적으로 확인한다.
4. 외부 성공 이후 로컬 실패는 별개의 실패 모드다. 취소를 재시도하지 말고 동기화를 재시도한다.
5. 요청 수락 단독 경로가 파생 상태를 변경하지 않는다는 것을 테스트로 고정한다.

가장 발견하기 어려운 버그는 "취소됐는데 혜택이 남아 있다"처럼 두 상태가 겉으로는 독립적으로 정상처럼 보일 때 생긴다. 트랜잭션 경계가 이 버그를 막는 가장 단순한 수단이고, 요청 수락 경로의 비동기화 테스트가 이 버그를 조기에 감지하는 가장 직접적인 방법이다.
