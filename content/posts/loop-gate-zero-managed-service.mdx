## 문제 정의

레거시 이미지 썸네일 서비스 마이그레이션 작업은 대개 "이것을 최신 스택으로 다시 짜자"는 지시로 시작한다. 그런데 실제 목표를 물어보면 대부분 "운영 복잡도를 줄이고 싶다"는 이야기가 나온다. 두 목표는 같지 않다.

한 작업에서는 Django 기반 레거시 썸네일 서비스를 최신 Python LTS + FastAPI로 재작성하는 방향으로 시작했다. 레거시 동작을 분석하고 API 계약을 정리하고 로컬 프로토타입까지 만들었는데, 검토 결과 관리형 이미지 서비스/CDN 방식이 운영 측면에서 더 합리적이라는 판단에 이르렀다. 재작성은 배포되지 않았지만 이 과정을 통해 결정을 내리는 데 필요한 불확실성이 줄어들었다.

이 글은 그 결정 루프에서 재사용 가능한 원칙을 정리한다.

## 게이트 0: 구현을 시작하기 전에 결정한다

마이그레이션 작업에서 시간을 가장 많이 낭비하는 패턴은 구현부터 시작하는 것이다. 코드를 짜면서 "이게 맞는 방향인가"를 확인하게 되면, 이미 만든 것을 버리기가 어려워진다.

게이트 0은 구현 전 단계에서 세 가지 선택지를 명시적으로 비교하는 체크포인트다.

| 선택지        | 요약                 | 결정 조건                                               |
| ------------- | -------------------- | ------------------------------------------------------- |
| 직접 재작성   | 스택 교체, 내부 소유 | 도메인 제어가 필요하고 관리형 대안이 없거나 부적합할 때 |
| 관리형 서비스 | 외부 제공자에게 위임 | 운영 부담이 핵심 병목이고 제공자 제약이 수용 가능할 때  |
| 삭제·유지     | 아무것도 하지 않음   | 실제 소비자가 없거나 비용 대비 효용이 없을 때           |

이 비교를 구현 전에 한 번이라도 명시적으로 문서화하지 않으면, 팀은 기본값으로 "재작성"을 선택하고 나중에 후회하거나 도중에 방향을 바꾸느라 비용을 치른다.

```
게이트 0 질문 목록
──────────────────
1. 이 서비스를 소유하고 운영할 팀이 있는가?
2. 관리형 대안이 기능·비용·보안 요구사항을 충족하는가?
3. 실제 소비자가 누구인지 확인했는가?
4. 삭제하면 어떤 영향이 있는가?
```

## 호환성 기준선과 신규 운영 스펙을 분리한다

레거시 서비스를 분석하면서 스펙이 두 종류로 나뉜다는 것을 알게 됐다.

**레거시 호환성 기준선**은 기존 동작을 그대로 유지해야 하는 항목들이다. 예를 들어 기존 서비스에서 특정 썸네일 폭이 하드코딩되어 있거나, JPEG 출력만 지원하거나, 특정 크롭 동작이 고정된 경우다. 이것을 바꾸면 기존 소비자가 영향을 받는다.

**신규 운영 스펙**은 재작성이나 마이그레이션 기회에 함께 도입하고 싶은 항목들이다. 예를 들어 WebP·AVIF 지원, 해상도 프리셋 체계, 품질 파라미터, 사용 가이드 등이다.

이 두 가지를 같은 문서나 같은 스코프 안에 섞으면 작업 범위가 걷잡을 수 없이 커진다. 호환성 기준선은 롤아웃 리스크를 결정하고, 신규 운영 스펙은 미래의 제품·운영 결정이다.

```
분리 원칙
──────────
호환성 기준선: 기존 소비자가 기대하는 동작. 이것을 바꾸려면 소비자 협의가 필요하다.
신규 운영 스펙: 이번 마이그레이션 스코프에 포함할지 별도로 결정한다.
```

관리형 서비스로 전환할 때도 이 분리가 중요하다. 기존 URL 구조나 이미지 출력 형식이 호환성 기준선이라면, 관리형 서비스가 그 기준선을 충족할 수 있는지 먼저 확인한다. 신규 스펙은 그 다음 단계에서 결정한다.

## 실제 소비자를 먼저 확인한다

API를 설계하기 전에 실제로 이 서비스를 호출하는 쪽이 무엇을 기대하는지 확인해야 한다.

한 작업에서는 이미지 처리 작업을 큐에 넣고 결과를 기다리지 않는 fire-and-forget 호출 구조가 있었다. 즉, 호출자는 응답 바디를 소비하지 않았다. 실제 제품 가치는 처리된 이미지 파일 자체에 있지, API 응답 구조에 있지 않았다.

이것을 미리 확인하지 않으면 API 응답 포맷을 정교하게 설계하는 데 시간을 쓰고, 실제로는 아무도 그 응답을 쓰지 않는다는 것을 나중에 알게 된다.

소비자 확인 체크리스트:

- [ ] 이 API를 호출하는 클라이언트 목록을 만든다 (caller map)
- [ ] 각 호출자가 응답 바디를 실제로 사용하는지 확인한다
- [ ] 호출 방식이 동기/비동기인지, 재시도 정책이 있는지 확인한다
- [ ] 이미지·파일 출력이 있다면 실제 출력물이 최종 제품 가치인지 확인한다

## 로컬 프로토타입은 배포되지 않아도 가치가 있다

재작성 방향으로 작업하면서 만든 로컬 프로토타입과 테스트는 최종적으로 배포되지 않았다. 그러나 이 작업은 낭비가 아니었다.

로컬 수준의 검증에서는 레거시 동작이 어떻게 구현되어 있는지, API 계약이 어떤 형태인지, 이미지 처리 파이프라인에서 어떤 부분이 단순하고 어떤 부분이 복잡한지를 구체적으로 파악할 수 있었다. 이 정보가 "직접 재작성 vs 관리형 서비스" 비교를 실질적으로 가능하게 만들었다.

"코드가 배포되지 않으면 실패"라는 프레임은 틀렸다. 불확실성을 줄이는 것이 목표라면, 프로토타입은 그 목표를 달성할 수 있다.

## 트레이드오프

| 방향               | 장점                                         | 단점                                         |
| ------------------ | -------------------------------------------- | -------------------------------------------- |
| 직접 재작성        | 도메인 동작 완전 제어, 내부 인프라 통합 자유 | 소유·운영 부담 내재화, 온콜 범위 증가        |
| 관리형 서비스      | 운영 부담 외부화, 인프라 유지보수 감소       | 제공자 제약·가격 구조에 종속, 설정 방식 변화 |
| 레거시 호환성 유지 | 롤아웃 리스크 최소화, 소비자 영향 없음       | 기존 기술 부채를 그대로 이전할 수 있음       |
| 삭제·no-op         | 운영 비용 즉시 0                             | 실제 소비자가 있으면 서비스 중단             |

관리형 이미지 서비스(예: CDN 기반 이미지 변환 서비스)를 선택할 때 자주 놓치는 제약은 URL 구조 변경과 캐시 정책이다. 기존 소비자가 특정 URL 패턴에 의존하고 있다면, 관리형 서비스의 URL 생성 방식이 호환성 기준선을 충족하는지 미리 확인해야 한다.

## 다음 마이그레이션을 위한 게이트 체크리스트

이 결정 루프를 재사용 가능한 형태로 정리하면 다음과 같다.

### 게이트 0: 방향 결정 전

- [ ] **소비자 맵**: 이 서비스의 실제 호출자 목록이 있는가
- [ ] **API 계약**: 호출자가 기대하는 요청/응답 형식이 문서화되어 있는가
- [ ] **출력 계약**: 이미지·파일 출력이 있다면 포맷·크기·형식 기준이 있는가
- [ ] **호환성 기준선 vs 신규 스펙**: 두 종류의 요구사항이 분리되어 있는가
- [ ] **관리형 대안 검토**: 비용·기능·보안·제약을 직접 재작성과 비교했는가
- [ ] **삭제 가능성 검토**: 소비자가 없거나 기능이 중복된 경우 삭제 옵션을 고려했는가

### 구현 중 또는 프로토타입 단계

- [ ] **로컬 스모크 테스트**: 핵심 경로가 로컬에서 동작하는가
- [ ] **비용·운영 비교**: 재작성 유지 비용 vs 관리형 서비스 비용을 수치로 비교했는가
- [ ] **롤백 계획**: 새 서비스에 문제가 생겼을 때 레거시로 돌아올 수 있는가
- [ ] **소유권**: 새 서비스를 운영할 팀과 온콜 범위가 결정되었는가

### 결정 시점

- [ ] **결정 기록**: 왜 이 방향을 선택했는지 문서화한다
- [ ] **제외한 선택지**: 검토했지만 선택하지 않은 이유도 기록한다

## 배운 것

"레거시 서비스를 재작성하라"는 지시를 받았을 때, 실제 목표가 "코드를 최신 스택으로 교체하는 것"인지 "운영 복잡도를 줄이는 것"인지 먼저 확인해야 한다. 두 목표가 같은 결론으로 이어지지 않을 수 있다.

게이트 0은 구현 시작 전에 세 가지 선택지(재작성·관리형·삭제)를 명시적으로 비교하는 단계다. 이 단계를 건너뛰면 구현 도중 방향을 바꾸는 비용이 발생하고, 이미 만든 것을 버리기 어려운 심리적 부담도 생긴다.

로컬 프로토타입과 테스트는 배포 여부와 관계없이 불확실성을 줄이는 역할을 한다. 프로토타입을 통해 레거시 동작을 구체적으로 파악했기 때문에 관리형 서비스와의 기능 비교가 가능했다. 코드가 배포되지 않았다고 해서 그 과정이 낭비인 것은 아니다.

결정 기록은 결과만 적지 않는다. 검토했지만 선택하지 않은 이유까지 적어야 나중에 같은 고민을 반복하지 않는다.
