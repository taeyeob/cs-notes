## 문제 정의

서비스를 새 시스템으로 이관하거나 오래된 백엔드를 점진적으로 정리할 때, "이 API가 실제로 아직 쓰이고 있는가"를 판단하기 어렵다. 코드에 라우팅이 남아 있고 테스트가 통과한다고 해서 실제 호출자가 있다는 의미는 아니다. 반대로 외부 로그에 트래픽이 없어도 특정 배치나 관리자 도구가 드물게 호출하는 경우도 있다.

직관에 의존해 API를 삭제하면 두 가지 위험이 생긴다. 첫째, 실제로 쓰이던 엔드포인트를 제거해서 예상치 못한 장애가 발생한다. 둘째, 불확실성 때문에 아무것도 지우지 못하고 레거시가 계속 축적된다. 두 위험을 동시에 줄이려면 "증거 기반으로 후보를 분류하고, 작은 단위로 제거하고, 각 단계마다 검증한다"는 절차가 필요하다.

## 인벤토리의 역할

삭제 작업을 시작하기 전에 인벤토리를 먼저 만든다. 인벤토리의 목적은 전체 API 목록을 한 곳에서 볼 수 있게 하는 것이지, 처음부터 삭제 여부를 결정하는 것이 아니다.

인벤토리에 담아야 할 항목은 다음과 같다.

- **엔드포인트 식별자**: HTTP 메서드, 경로 패턴, ViewSet/Router 이름
- **코드 위치**: 라우팅 설정 파일, ViewSet 클래스, 전용 Serializer 여부
- **연관 테스트**: 이 엔드포인트만을 직접 테스트하는 파일이 있는가
- **마지막 트래픽 날짜**: 로그나 APM에서 확인 가능한 최근 호출 시점
- **호출 주체 추정**: 프론트엔드, 관리자 도구, 외부 파트너, 내부 배치 중 어느 쪽인지

이 정보가 한 표에 모이면, 항목마다 "삭제 가능한가"를 독립적으로 평가할 수 있게 된다. 인벤토리가 없으면 삭제 판단이 항상 코드를 다시 따라가는 것에서 시작된다.

### 번호 순차성과 스키마 일관성 검증

레거시 서비스에서 API 목록을 만들 때, 인벤토리 자체의 완결성도 검증해야 한다. 경로나 ID에 번호 체계가 있다면 순차성이 깨진 항목이 없는지 확인한다. 오래된 기능 설명 문자열이나 이미 삭제된 리소스를 가리키는 참조가 남아 있으면 제거한다. 인벤토리 작성 단계에서 이 정리를 함께 하면, 이후 삭제 후보를 평가할 때 노이즈가 줄어든다.

## 삭제 후보를 증거 등급으로 나누기

인벤토리가 완성되면 각 엔드포인트를 증거 등급으로 분류한다. 등급은 "얼마나 확실하게 미사용임을 증명할 수 있는가"를 기준으로 나눈다.

| 등급                 | 기준                                                                                                        | 처리 방향          |
| -------------------- | ----------------------------------------------------------------------------------------------------------- | ------------------ |
| **삭제 가능**        | 새 서비스로 1:1 이관되어 동일 기능이 존재하고, 기존 호출자가 새 엔드포인트를 쓰고 있음을 코드나 로그로 확인 | 이번 배치에서 제거 |
| **보류 — 확인 필요** | 트래픽 로그가 없지만 드물게 호출될 가능성을 배제하기 어려움. 간접 호출 경로(배치, 관리자 스크립트)가 있음   | 별도 조사 후 판단  |
| **유지**             | 현재도 호출 중이거나, 이관이 아직 완료되지 않았거나, 삭제 시 즉각적인 장애 위험이 있음                      | 건드리지 않음      |

"보류" 항목을 "삭제 가능"으로 격상하려면 추가 증거가 필요하다. 예를 들면, 프론트엔드 코드베이스에서 해당 경로를 호출하는 코드가 없다는 것, 새 시스템에서 동일 기능이 이미 활성화됐다는 것, 로그 보존 기간 안에 트래픽이 전혀 없다는 것 중 하나 이상을 확인해야 한다.

초기 인벤토리에서 후보가 수십~수백 건이라도, keep 기준을 적용하면 첫 삭제 배치는 그보다 훨씬 적어진다. 이는 문제가 아니라 의도된 결과다. 확실한 것부터 지우고 불확실한 것은 근거를 쌓아 다음 배치에서 처리한다.

## 작게 삭제하고 검증하기

### 삭제 단위를 "라우팅을 끊는 데 필요한 최소 범위"로 설정한다

API를 제거할 때 가장 흔한 실수는 너무 넓게 지우거나, 관련 코드를 함께 제거하지 않아 죽은 코드가 남는 것이다.

**제거 대상 (라우팅 경로를 끊는 데 직접 필요한 것)**

- 라우터 등록 항목 (urlpatterns, router.register)
- ViewSet 클래스 또는 해당 action 메서드
- 이 엔드포인트만을 직접 테스트하는 전용 테스트

**별도 확인 후 처리 (간접 참조 가능성이 있는 것)**

- Controller / Service 레이어: 다른 엔드포인트나 배치에서 공유할 수 있음
- Serializer: 여러 뷰에서 재사용되는 경우가 많음
- Template 문자열 / 상수: 로그나 알림에서 참조할 가능성이 있음

이 구분을 지키면 "API가 사라졌지만 내부 비즈니스 로직은 남아 있다"는 상태가 된다. 이후 공유 여부를 확인한 뒤 남은 코드를 별도 PR에서 정리한다. 한 번에 다 지우려다 공유 코드까지 제거해서 다른 기능이 깨지는 상황을 막는 것이 목적이다.

### 프론트엔드 조율은 증거로 판단한다

프론트엔드가 이미 새 base URL이나 새 HTTP 클라이언트로 전환된 경우, "기존 API를 더 이상 호출하지 않는다"는 증거를 코드베이스에서 확인한다.

확인 방법:

```bash
# 삭제 대상 경로 패턴이 프론트엔드 코드에 남아 있는지 검색
rg "old-backend-host" frontend/src/
rg "/legacy-admin/(resource-a|resource-b)" frontend/src/
```

검색 결과가 없어도 "새 프론트엔드가 기존 API를 다시 쓰지 않도록 주의사항을 남긴다"는 점이 중요하다. 새 프론트엔드가 배포된 이후 특정 화면이나 플로우에서 구 API로의 호출이 부활하는 경우를 방지하기 위해, 삭제한 엔드포인트 목록과 이관된 새 경로를 PR 설명에 명시한다.

### 첫 삭제 배치 예시

한 레거시 서비스에서 새 서비스로 1:1 이관된 관리자 API 묶음을 처음 제거할 때의 순서다.

```python
# 제거 전: 라우터에 ViewSet이 등록된 상태
router = DefaultRouter()
router.register(r"admin/resource-a", AdminResourceAViewSet, basename="admin-resource-a")
router.register(r"admin/resource-b", AdminResourceBViewSet, basename="admin-resource-b")
# ... (수십 개)

# 제거 후: 이관 완료된 항목만 라우터에서 제거
router = DefaultRouter()
# admin/resource-a, admin/resource-b 삭제
# 이관 미완료 항목은 그대로 유지
```

ViewSet 클래스도 함께 삭제하고, 해당 ViewSet만 직접 테스트하는 파일을 삭제한다. Serializer나 Controller는 다른 엔드포인트에서 사용 여부를 확인한 뒤 별도로 처리한다.

## 트레이드오프

| 접근 방식                          | 장점                                              | 단점                                       |
| ---------------------------------- | ------------------------------------------------- | ------------------------------------------ |
| 인벤토리 없이 직관으로 삭제        | 빠름                                              | 호출자 파악 누락, 장애 위험                |
| 인벤토리 작성 후 전체 한 번에 삭제 | 한 번의 PR로 정리 완료                            | 삭제 범위가 넓어 리뷰 어려움, 롤백 비용 큼 |
| 인벤토리 작성 후 등급별 순차 삭제  | 확실한 것부터 지워 위험 최소화, 각 배치 검증 가능 | 여러 번의 PR과 긴 기간 필요                |
| 삭제 없이 deprecated 표시만        | 즉각적인 위험 없음                                | 코드가 계속 쌓임, 유지보수 비용 유지       |

"인벤토리 작성 후 등급별 순차 삭제"가 가장 안전하지만, 완료까지 시간이 오래 걸린다. 대신 각 배치마다 "이 시점에서 안전하게 제거된 API 목록"이 PR과 로그에 남는다. 나중에 특정 엔드포인트가 언제, 왜 제거됐는지 추적할 수 있다.

Controller/Serializer 같은 공유 가능성이 있는 코드를 첫 배치에 포함하면 당장 삭제량이 늘어나 보이지만, 예상치 못한 공유 경로가 있을 때 위험 범위가 넓어진다. "라우팅 끊기"와 "내부 구현 정리"를 분리하면 각각 독립적으로 검증할 수 있다.

## 검증 체크리스트

각 삭제 배치를 합치기 전에 확인하는 순서다.

- [ ] **diff에 공백 변화만 있는 줄이 없는지 확인한다.** 삭제 diff에서 들여쓰기 변경이나 빈 줄 추가가 섞이면 의도하지 않은 변경이 포함된 것일 수 있다.
- [ ] **삭제한 엔드포인트만 직접 테스트하는 파일을 함께 삭제했는지 확인한다.** 라우팅은 제거됐는데 테스트가 남아 있으면 CI 통과 여부와 관계없이 죽은 테스트가 생긴다.
- [ ] **공유 Serializer/Controller가 남은 다른 엔드포인트에서 참조되는지 확인한다.** `rg "ClassName" .` 으로 제거 대상 이외의 참조가 있는지 검색한다.
- [ ] **프론트엔드 코드베이스에서 삭제 대상 경로를 호출하는 코드가 없는지 확인한다.** 패턴 검색 결과가 없어야 삭제 가능 상태다.
- [ ] **pre-commit hook과 CI가 통과하는지 확인한다.** 삭제 후 import 오류나 참조 오류가 없어야 한다.
- [ ] **삭제한 API 목록과 이관된 새 경로를 PR 설명에 명시한다.** 리뷰어가 "왜 이 항목이 안전하게 삭제 가능한가"를 코드만 보고 판단할 수 있어야 한다.
- [ ] **이관 미완료 항목이 실수로 포함됐는지 다시 확인한다.** 인벤토리의 "유지" 또는 "보류" 항목이 이번 삭제 diff에 없어야 한다.

## 배운 것

API 정리 작업에서 가장 비효율적인 접근은 "이번 기회에 전부 지우자"다. 범위가 넓어질수록 각 항목에 대한 증거를 꼼꼼히 확인하기 어려워지고, 리뷰와 롤백 비용이 함께 올라간다.

반대로 인벤토리를 먼저 만들고 등급을 분류하면 "지금 확실하게 지울 수 있는 것"과 "조사가 더 필요한 것"이 명확히 나뉜다. 첫 삭제 배치가 예상보다 적더라도 괜찮다. 각 배치가 독립적으로 검증되고 PR에 기록되면, 시간이 지나면서 레거시 규모는 줄어들고 각 삭제 결정에 대한 근거는 이력에 남는다.

Controller와 Serializer처럼 공유 가능성이 있는 코드를 첫 단계에서 보존하는 것도 같은 원칙이다. "라우팅을 끊는 데 필요한 최소 범위만 제거한다"는 규칙을 지키면, 예상치 못한 공유 경로로 인한 장애를 피하면서도 API 삭제를 안전하게 시작할 수 있다.
