## 문제 정의

외부 API를 주기적으로 호출하는 배치는 실패 원인이 두 종류로 나뉜다.

- **Transient failure**: SSL EOF, TCP reset, 일시적 DNS 오류, 외부 제공자 측 일시 과부하. 대부분 재시도하면 해결된다.
- **Persistent failure**: 외부 제공자 인증 키 만료, 스펙 변경으로 인한 파싱 오류, 내부 코드 버그. 재시도해도 반복 실패한다.

두 종류를 구분하지 않으면 두 가지 문제가 생긴다. 첫째, transient failure에 즉시 알림이 울려 운영자가 조치할 수 없는 상황에 호출된다. 둘째, persistent failure가 알림 없이 transient로 분류되어 오래 방치된다.

## 실패 모드별 분류

실행 결과를 세 가지로 나누면 처리 방향이 명확해진다.

| 분류         | 예시                        | 대응                                          |
| ------------ | --------------------------- | --------------------------------------------- |
| `transient`  | SSL EOF, timeout, 503 일시  | retry 후 성공하면 무시, 반복 실패 시에만 알림 |
| `persistent` | 401 인증 만료, 파싱 오류    | 즉시 알림, 재시도 무의미                      |
| `degraded`   | 결과 일부 누락, 데이터 이상 | 알림 + 부분 성공 상태로 기록                  |

HTTP 상태 코드만으로는 분류가 불완전하다. 503은 transient일 수도 있고 persistent일 수도 있다. 응답 body의 에러 코드나 에러 메시지를 함께 보고 분류한다.

## Timeout과 Retry 설계

### Timeout 계층 분리

연결 timeout과 읽기 timeout을 분리해서 설정한다.

```python
import httpx

client = httpx.Client(
    timeout=httpx.Timeout(
        connect=5.0,   # 연결 수립
        read=30.0,     # 응답 수신 (외부 API 특성에 맞게 조정)
        write=10.0,
        pool=5.0,
    )
)
```

연결 timeout이 짧으면 네트워크 지연을 일찍 포착하고, 읽기 timeout이 없으면 외부 서버가 응답을 끊지 않을 때 배치가 영구 대기한다. 두 값을 묶어서 설정하면 원인 파악이 어려워진다.

### Retry와 Backoff

Transient 오류 코드에만 retry를 적용한다. 401, 403, 422 같이 재시도해도 의미 없는 오류에는 즉시 실패 처리한다.

```python
from tenacity import retry, stop_after_attempt, wait_exponential, retry_if_exception

RETRYABLE_STATUS = {429, 500, 502, 503, 504}

def is_retryable(exc):
    if isinstance(exc, httpx.TimeoutException):
        return True
    if isinstance(exc, httpx.HTTPStatusError):
        return exc.response.status_code in RETRYABLE_STATUS
    return False

@retry(
    retry=retry_if_exception(is_retryable),
    stop=stop_after_attempt(3),
    wait=wait_exponential(multiplier=1, min=2, max=30),
    reraise=True,
)
def fetch_from_external(client, url, params):
    response = client.get(url, params=params)
    response.raise_for_status()
    return response.json()
```

Backoff 상한(max)을 배치 전체 실행 시간 한도 안에 들어오도록 설정한다. 재시도가 너무 길면 다음 스케줄 실행과 겹칠 수 있다.

## 알림 정책 경계

알림의 목적은 "운영자가 즉시 조치할 수 있는 상황"을 전달하는 것이다. Transient failure는 즉시 조치 대상이 아니다.

**알림을 억제하는 기준**

- 3회 retry 중 1~2회 실패 후 최종 성공한 경우
- 외부 제공자가 공지한 점검 시간대의 오류
- 허용된 retry 횟수 안에서 해결된 timeout

**알림을 보내는 기준**

- 최대 retry 횟수를 소진한 실패가 연속/비율 임계치에 도달
- Persistent 오류 코드(401, 403, 422)로 즉시 실패
- 연속 N회 실행 실패 (스케줄러 레벨에서 감지)
- 응답 파싱 오류 (외부 스펙이 바뀌었을 가능성)

```python
def run_batch():
    result = {"status": "ok", "retries": 0, "error": None}
    try:
        data = fetch_from_external(client, EXTERNAL_URL, params)
        process(data)
    except httpx.TimeoutException as e:
        result["status"] = "transient_fail"
        result["error"] = str(e)
        logger.warning("외부 API timeout (retry 소진)", error=str(e))
        if should_notify_transient_failure():
            notify_ops("외부 API timeout이 연속 임계치를 넘었습니다")
    except httpx.HTTPStatusError as e:
        if e.response.status_code in {401, 403}:
            result["status"] = "persistent_fail"
            notify_ops(f"외부 API 인증 실패: {e.response.status_code}")
        else:
            result["status"] = "transient_fail"
            logger.error("외부 API 오류", status=e.response.status_code)
            if should_notify_transient_failure():
                notify_ops("외부 API 일시 오류가 연속 임계치를 넘었습니다")
    return result
```

상태는 항상 로그나 실행 이력에 남긴다. 알림 억제가 "기록 억제"를 의미하지 않는다. 단발성 transient 실패는 조용히 기록하고, 연속 실패나 비율 임계치 초과처럼 운영자가 판단할 신호가 생겼을 때만 알림으로 올린다.

## 관측 설계

### 실행 이력 기록

배치 완료 후 실행 결과를 구조화해서 저장한다. 스케줄러 대시보드의 성공/실패만으로는 원인 분류가 안 된다.

```python
execution_log = {
    "run_at": run_at,
    "status": result["status"],       # ok / transient_fail / persistent_fail
    "retries": result["retries"],
    "duration_ms": elapsed,
    "error": result["error"],
    "records_processed": count,
}
```

### 메트릭

- 실행당 retry 횟수 평균: 외부 제공자 안정성 추이 파악
- Transient fail 비율: 임계치 초과 시 알림 (예: 최근 24시간 중 30% 이상 transient fail)
- 응답 시간 p95: timeout 설정이 적절한지 판단 기준

에러 트래킹 도구를 쓸 때는 transient 오류에 `level=warning`, persistent 오류에 `level=error`를 구분해서 집계 노이즈를 줄인다.

## 수동 재실행과 검증

스케줄러 수동 실행은 멱등성을 전제해야 한다. 동일 파라미터로 두 번 실행해도 결과가 같아야 하고, 중복 저장이나 상태 누적이 없어야 한다.

수동 재실행 전 확인 체크리스트:

- [ ] 스케줄러 직전 실행 이력에서 실패 분류 확인 (`transient` vs `persistent`)
- [ ] Transient면 외부 제공자 상태 페이지나 응답 코드 이력 확인
- [ ] Persistent면 인증 키 유효 기간, 엔드포인트 변경 여부 확인
- [ ] 수동 실행 시 전체 실행 시간 한도 안에서만 timeout/retry 상한 조정
- [ ] 결과 레코드 수가 기대 범위 안인지 확인

수동 실행 후 "실행 완료"만 확인하고 끝내지 않는다. 처리된 레코드 수와 부분 실패 여부를 실행 이력에서 확인한다.

## 배운 것

외부 API 배치에서 알림 설계의 핵심은 "조치 가능한 실패"와 "조치 불가능한 실패"를 구분하는 것이다. Transient 오류에 즉시 알림이 울리면 노이즈가 많아져 실제 장애 알림을 놓친다. 반대로 transient로 분류하다가 persistent를 방치하면 데이터 공백이 생긴다.

설계 순서는 이렇다: 실패 분류 정의 → timeout 계층 분리 → retryable 오류 범위 결정 → 알림 기준 명시 → 로그/메트릭 구조화. 이 다섯 가지가 코드 작성 전에 정해져 있으면, 알림 억제가 "무시"가 아니라 "의도적 선택"임이 코드와 운영 이력에서 드러난다.
