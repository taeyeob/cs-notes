## 문제 정의

PG(결제대행사) 웹훅이나 콜백을 받는 구조에서 자주 마주치는 문제가 있다. PG 쪽 처리는 완료됐는데 내부 주문 또는 결제 상태는 중간 단계에 멈춰 있는 경우다.

취소 요청을 예로 들면, PG는 환불을 완료해 `REFUND_COMPLETE` 이벤트를 보냈지만 내부 order 상태는 `CANCEL_REQUESTED`에 그대로 남아 있다. 고객은 환불이 됐다고 보고, 어드민은 아직 취소 중으로 본다. 이 불일치는 금전 정산과 재고 원복 모두에 영향을 준다.

표면적으로는 "웹훅 처리가 안 됐다"처럼 보이지만, 실제로는 이벤트는 수신됐고 로그도 남아 있다. 문제는 이벤트 수신과 상태 반영 사이 어딘가다.

## 실패 모드

**1. 상태 가드가 올바른 이벤트를 막는다**

핸들러 안에 현재 상태를 먼저 확인하는 guard가 있는 경우, 중간 상태가 아니면 업데이트를 건너뛰도록 짜여 있을 수 있다.

```python
def handle_refund_complete(order_id):
    order = Order.objects.get(id=order_id)
    if order.status != "REFUND_PROCESSING":  # guard
        return  # 이미 다른 경로로 상태가 바뀌어 있으면 여기서 종료
    order.status = "CANCELED"
    order.save()
```

문제는 `payment` 테이블과 `order` 테이블의 상태가 완전히 동기화되지 않은 상태에서 guard 조건을 따로 평가할 때 생긴다. payment는 `REFUND_COMPLETE`인데 order는 `CANCEL_REQUESTED`여서, payment 핸들러 guard는 통과했지만 order 핸들러 guard는 막는 식이다.

**2. 이벤트가 두 테이블 중 하나만 업데이트한다**

하나의 PG 이벤트가 order와 payment를 둘 다 업데이트해야 할 때, 트랜잭션 없이 순차 처리하면 첫 번째 업데이트 직후 예외가 나도 두 번째는 실행되지 않는다. 이후 재시도가 없다면 반영 누락이 그대로 굳는다.

**3. 실패 이벤트 원본을 추적할 수 없다**

웹훅 수신 로그가 없거나, 처리 결과가 별도로 기록되지 않으면 어떤 이벤트가 들어왔고 어디서 멈췄는지 파악하기 어렵다. 재처리 수단도 없어서 상태를 수동으로 직접 수정하는 수밖에 없게 된다.

**4. 비동기 흐름에서 타이밍 충돌**

취소 요청 직후 PG 콜백이 거의 동시에 들어오면, 두 경로가 같은 레코드를 읽고 각자 저장하면서 나중에 저장된 쪽이 앞선 쪽을 덮어쓴다. 결과적으로 한 경로의 상태 전환이 유실된다.

## 설계 접근

**이벤트 원본을 저장한다**

웹훅 수신 즉시 원본 페이로드와 타임스탬프를 별도 테이블에 기록한다. 처리 결과(성공/실패/건너뜀)도 함께 남긴다. 이벤트가 수신됐는지, 처리됐는지를 독립적으로 추적할 수 있어야 재처리 경로를 만들 수 있다.

**guard 조건을 명시적으로 문서화한다**

상태 전환을 허용하는 조건이 여러 테이블에 걸쳐 있다면, 어떤 상태 조합에서 어떤 이벤트가 어디를 업데이트하는지 표로 정리한다. guard가 암묵적으로 흩어져 있으면 어떤 조합이 막히는지 리뷰 때 보이지 않는다.

```
PG 이벤트            | order 허용 상태              | payment 허용 상태
---------------------|------------------------------|--------------------
REFUND_COMPLETE      | CANCEL_REQUESTED, REFUNDING  | REFUND_PROCESSING
CANCEL_FAILED        | CANCEL_REQUESTED             | CANCEL_PROCESSING
DEPOSIT_COMPLETE     | WAITING_FOR_PAYMENT          | PENDING
```

**트랜잭션으로 묶거나 보상 경로를 만든다**

order와 payment를 같이 업데이트해야 한다면 하나의 트랜잭션으로 묶는다. 트랜잭션이 어렵다면(예: 별도 서비스 호출이 포함된 경우) 첫 번째 업데이트 성공 여부를 확인하고 실패 시 보상 처리를 트리거하도록 설계한다.

**멱등 재처리를 전제로 설계한다**

같은 이벤트를 두 번 처리해도 결과가 같아야 한다. 이미 `CANCELED`인 order에 `REFUND_COMPLETE` 이벤트를 다시 보내면 상태를 바꾸지 않고 그냥 통과한다. 이 조건이 보장돼야 실패한 이벤트를 부담 없이 재처리할 수 있다.

## 트레이드오프

**guard를 엄격하게 vs. 느슨하게**

guard 조건을 엄격하게 유지하면 이중 처리를 막을 수 있지만, 예상치 못한 상태 조합이 들어왔을 때 조용히 건너뛴다. 느슨하게 열어두면 재처리 안정성은 높아지지만 상태가 엉뚱하게 덮어써질 위험도 커진다. 어느 쪽이든 guard가 이벤트를 막았을 때 로그를 남겨야 나중에 파악할 수 있다.

**즉시 처리 vs. 큐 기반 처리**

웹훅을 수신하자마자 동기적으로 처리하면 구조가 단순하지만, 처리에 실패하면 PG 재전송을 기다리거나 수동 재처리를 해야 한다. 큐로 분리하면 재처리가 쉽고 타이밍 충돌도 줄지만 운영 복잡도가 늘어난다. 실패 빈도가 낮다면 이벤트 원본 기록 + 재처리 API 조합으로 충분한 경우가 많다.

## 검증 방법

- PG 이벤트 수신 로그와 내부 상태 변경 로그를 나란히 놓고 비교할 수 있는가
- 특정 order_id 또는 payment_id로 관련 이벤트 전체를 조회할 수 있는가
- guard가 이벤트를 건너뛴 경우 어느 조건에서 막혔는지 로그로 확인할 수 있는가
- 동일 이벤트를 두 번 처리했을 때 상태가 바뀌지 않는지 테스트로 검증했는가
- 처리 실패 이벤트를 재처리하는 경로가 있고, 그 경로가 실제로 동작하는지 확인했는가

## 배운 것

PG 웹훅 처리 문제는 이벤트 수신 실패보다 "수신은 됐지만 반영이 안 됐다"는 형태로 더 자주 나타난다. 그리고 이 상황에서 원인을 파악하기 가장 어려운 이유는 이벤트 원본과 처리 결과를 같이 볼 수 없기 때문이다.

상태 guard는 이중 처리를 막기 위해 필요하지만, guard가 예상 밖 조합을 조용히 막는 순간 디버깅이 막힌다. 막히면 로그를 남기고, 로그가 있어야 재처리 경로가 생기고, 재처리 경로가 있어야 수동 수정 없이 복구할 수 있다.

결국 웹훅 안정성은 수신 안정성이 아니라 처리 가시성과 재처리 가능성에 달려 있다.
