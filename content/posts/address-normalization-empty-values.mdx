## 빈 값은 다 같은 빈 값이 아니다

주소 필드를 다루다 보면 비어있는 것처럼 보이지만 실제로는 서로 다른 세 가지 상태를 만난다.

- `null`: 명시적으로 "없다"고 선언한 값
- `""` (빈 문자열): 입력은 있었지만 내용이 없는 값
- 필드 자체 누락: 아직 전달되지 않은 값

이 세 가지를 동일하게 처리하면 버그가 생긴다. 저장 전에 빈 문자열을 `null`로 변환하는지 아닌지에 따라 조회 결과가 달라지고, 프론트엔드가 기대하는 응답 스펙도 바뀐다.

## API 경계에서 한 번만 정규화한다

입력이 들어오는 지점이 API라면, 그 지점에서 빈 값을 정해진 형태로 바꾸는 것이 가장 깔끔하다.

```python
def normalize_address_field(value):
    if value is None or value.strip() == "":
        return None
    return value.strip()
```

이렇게 하면 서비스 레이어와 DB 레이어는 `None`/`null`만 신경 쓰면 된다. 빈 문자열이 DB에 그대로 저장되는 경로를 막고, 조회 시 `IS NULL` 조건을 일관되게 쓸 수 있다.

## FE-BE 스펙 정렬

빈 값 처리 방식은 프론트엔드와 합의가 필요하다.

- 응답에서 `null`과 `""`를 구분해 내려보내야 하는가
- 프론트엔드는 `null`과 `""`를 같은 방식으로 렌더링하는가
- 선택 필드는 요청에서 생략할 수 있는가, 아니면 항상 포함해야 하는가

합의 없이 각자 판단하면 혼선이 생긴다. BE가 `null`로 저장한 값을 FE가 빈 문자열로 PUT하면, 원래 `null`인지 의도적으로 비운 것인지 구분할 수 없게 된다.

## 변환 API를 추가할 때 주의점

기존 포맷과 새 포맷을 모두 지원해야 할 때, 변환 레이어는 양쪽 빈 값 규칙을 알아야 한다.

- 기존 포맷의 `""`를 새 포맷의 `null`로 바꿀지 결정
- 변환 실패 시 원래 값을 흘릴 것인지, 에러를 낼 것인지 명시
- 변환 레이어가 정규화까지 담당하면 로직이 두 곳에 생기므로 책임 범위를 좁힌다

## 리뷰 체크리스트

PR에서 주소 필드 관련 변경이 있으면 아래를 확인한다.

- 빈 문자열이 DB에 그대로 저장되는 경로가 있는가
- `null` 체크와 빈 문자열 체크가 모두 필요한 곳에 둘 다 있는가
- 응답 스펙이 FE와 맞춰져 있는가 (특히 optional 필드)
- 변환 API가 있다면 양쪽 포맷의 빈 값 규칙이 문서화되어 있는가

## 배운 것

빈 값 버그는 단독으로 드러나지 않는다. 저장은 성공하지만 조회 시 의도와 다른 결과가 나오거나, FE와 BE가 서로 다른 상태를 같은 값으로 주고받으면서 데이터가 조용히 덮어 써진다. 정규화 지점을 한 곳으로 모으고, FE-BE 빈 값 계약을 명시적으로 합의해두면 이런 종류의 버그를 예방할 수 있다.
