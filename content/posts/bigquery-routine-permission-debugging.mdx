## 문제 정의

analytics ingest 계열 API를 실행했더니 HTTP 500이 반환됐다. 앱 로그에는 내부 작업 실패 외에 별다른 단서가 없었다. 이런 경우 원인 후보가 여럿 겹친다. Secret/환경 변수가 반영이 안 됐을 수도 있고, BigQuery IAM 설정이 덜 됐을 수도 있고, 코드 자체 문제일 수도 있다.

먼저 API 응답 body를 열어봤다. 해당 API는 작업 실패 시에도 HTTP 500을 반환하면서, 구체적인 원인을 `results[].errors`에 담는 구조였다.

```json
{
  "results": [
    {
      "status": "error",
      "errors": [
        "403 Access Denied: Routine analytics_project.analytics_dataset.udf_name; User does not have permission to invoke routine analytics_project.analytics_dataset.udf_name"
      ]
    }
  ]
}
```

HTTP 상태 코드만 보고 멈췄다면 가설 공간이 너무 넓었을 것이다. errors 필드를 먼저 확인하는 것이 출발점이다.

## 가설 분리

에러 메시지를 얻은 뒤에는 가능한 원인을 독립적으로 나눠서 확인했다.

**1. Secret/환경 변수 누락 여부**

앱이 BigQuery 클라이언트를 초기화할 때 쓰는 자격증명이 런타임 환경에 제대로 주입됐는지 확인한다. 이 경우 에러 메시지가 403이 아니라 인증 실패(401) 또는 클라이언트 초기화 오류로 나타난다. 403이면 인증은 됐지만 권한이 없다는 뜻이므로, Secret 문제는 배제할 수 있다.

**2. 서비스 계정 IAM 설정**

403 Access Denied가 확인됐으므로 실제로 런타임 서비스 계정(`runtime-service-account@project.iam.gserviceaccount.com`)에 어떤 권한이 있는지 확인한다.

```bash
gcloud projects get-iam-policy PROJECT_ID \
  --flatten="bindings[].members" \
  --format="table(bindings.role, bindings.members)" \
  --filter="bindings.members:runtime-service-account"
```

BigQuery 관련 역할이 없거나, 있더라도 routine 호출에 필요한 권한이 누락됐을 수 있다.

## BigQuery 권한 모델에서 놓치기 쉬운 부분

BigQuery의 권한은 세 층으로 분리되어 있다.

- **Job 생성 권한**: `bigquery.jobs.create` — BigQuery 쿼리 자체를 실행할 수 있는 권한. 보통 `roles/bigquery.jobUser`로 부여한다.
- **테이블 조회 권한**: dataset이나 테이블 수준의 `bigquery.tables.getData` — `SELECT` 쿼리가 실제 데이터를 읽을 수 있는 권한.
- **Routine 호출 권한**: `bigquery.routines.get` + routine이 속한 dataset의 접근 권한 — UDF나 프로시저를 쿼리 안에서 호출하기 위해 별도로 필요하다.

이 세 가지는 독립적이다. 테이블 직접 쿼리(`SELECT * FROM table`)가 잘 통과하더라도 동일 dataset의 UDF를 호출하는 쿼리(`SELECT udf_name(col) FROM table`)에서는 막힐 수 있다. wildcard 테이블 쿼리가 성공한 것으로 routine 권한까지 있다고 가정하면 안 된다.

## 권한 수정 및 검증

dataset 수준에서 서비스 계정에 `READER` 역할을 부여하는 것이 routine 호출까지 커버하는 가장 간단한 방법이다.

BigQuery console에서 dataset → 공유 → 주 구성원 추가 → `roles/bigquery.dataViewer` 또는 커스텀 역할(`bigquery.routines.get` 포함) 부여.

bq CLI 또는 Terraform(IaC) 중 하나를 선택해 관리한다. 두 방법을 혼용하면 Terraform plan이 drift를 감지해 수동 변경을 되돌릴 수 있으므로, 팀 내에서 방법을 통일하는 것이 좋다.

**bq CLI**

```bash
bq add-iam-policy-binding \
  --member="serviceAccount:runtime-service-account@project.iam.gserviceaccount.com" \
  --role="roles/bigquery.dataViewer" \
  analytics_project:analytics_dataset
```

**Terraform**

```hcl
resource "google_bigquery_dataset_access" "routine_invoker" {
  dataset_id    = "analytics_dataset"
  project       = "analytics_project"
  role          = "READER"
  user_by_email = "runtime-service-account@project.iam.gserviceaccount.com"
}
```

권한 부여 후 동일 API를 재실행해서 `results[].errors`가 비어있는지 확인한다.

## 운영 체크리스트

BigQuery 관련 API 500을 처음 받았을 때 확인 순서다.

- [ ] 응답 body의 `errors` 또는 작업 결과 내 에러 메시지를 먼저 읽는다
- [ ] 403이면 인증 문제가 아니라 권한 문제이므로 IAM으로 범위를 좁힌다
- [ ] 런타임 서비스 계정에 `bigquery.jobUser` 역할이 있는가
- [ ] 쿼리 대상 dataset에 대한 `dataViewer` 또는 상응하는 권한이 있는가
- [ ] 쿼리 안에서 호출하는 routine이 속한 dataset 권한도 별도로 있는가
- [ ] 리소스 location이 일치하는가 (US vs EU 등 region 불일치도 접근 오류로 나타날 수 있다)

## 배운 것

BigQuery 권한 오류는 HTTP 500 뒤에 숨어있는 경우가 많다. API가 내부 작업 실패를 모두 500으로 뭉개서 반환하는 구조라면, 응답 body 안의 상세 에러를 먼저 꺼내보는 습관이 디버깅 시간을 크게 줄인다.

BigQuery 권한 모델에서 "job 실행 가능"과 "테이블 읽기 가능"과 "routine 호출 가능"은 별개다. 테이블 쿼리가 되더라도 UDF 호출에서 막히는 이유가 여기 있다. 서비스 계정에 권한을 부여할 때는 routine이 포함된 dataset의 접근 권한을 명시적으로 확인해야 한다.
