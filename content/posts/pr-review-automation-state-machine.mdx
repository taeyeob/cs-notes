## 문제 정의

cron으로 돌아가는 PR 리뷰 봇을 만들다 보면 "지금 이 PR을 리뷰해야 하나?"라는 판단을 반복해서 마주친다. 조건을 if/else로 나열하기 시작하면 순서에 따라 결과가 달라지거나, 조건 간 충돌로 예상치 못한 중복 리뷰나 누락이 생긴다.

세 가지 상황이 특히 까다롭다. 첫째, cron이 자주 실행되면 같은 PR에 리뷰를 반복 트리거한다. 둘째, PR의 head가 바뀐 뒤에도 이전 리뷰를 유효한 것으로 취급하면 변경 사항을 놓친다. 셋째, 이미 승인된 PR을 다시 리뷰하면 불필요한 소음이 된다.

## 상태 머신으로 모델링하기

각 PR에 명시적인 상태를 부여하면 판단 로직이 단순해진다.

- `NEEDS_REVIEW`: 공식 리뷰가 0건인 PR
- `NEEDS_REREVIEW`: 마지막 리뷰 이후 head commit이 바뀐 PR
- `APPROVED`: 현재 head가 이미 승인 상태인 PR
- `SKIP`: 그 외 — 이미 리뷰됨, 조건 불충족

상태 전환 순서가 중요하다. `APPROVED` 확인을 `NEEDS_REREVIEW`보다 먼저 평가해야 "head가 바뀌었지만 이미 승인된 PR"을 불필요하게 재리뷰하지 않는다. 조건을 if로 흩어두면 이 순서가 코드 안에서 암묵적으로 숨어들어 나중에 추적하기 어려워진다.

## 정책과 트레이드오프

리뷰 봇은 blocking 판단도 해야 한다. 구조적 이슈나 레거시 코드 스타일 지적은 blocking으로 처리하지 않는 것이 낫다. 모든 지적을 merge 전에 반드시 수정하도록 강제하면 자동화 리뷰의 신뢰도가 오히려 낮아진다.

blocking과 non-blocking을 분리해서 정의하면 신호 대 잡음비를 유지할 수 있다. 자동화 리뷰가 진짜 중요한 문제를 놓치지 않으면서도, 리뷰어를 필요 이상으로 묶어두지 않는 균형점이다.

상태 설계 관점에서 보면, blocking 여부도 상태의 일부로 취급할 수 있다. `NEEDS_REVIEW`로 분류된 PR이라도 이전 리뷰에서 non-blocking 코멘트만 남겼다면, 재리뷰 없이 넘어갈 수 있다.

## 검증 방법

상태 판단 함수를 순수 함수로 만들면 테스트가 쉬워진다. 입력은 PR 메타데이터(리뷰 수, 마지막 리뷰 SHA, 현재 head SHA, 승인 여부), 출력은 상태 값이다.

각 상태 전환 케이스를 단위 테스트로 고정해 두면, cron 스크립트나 검색 조건이 바뀌어도 판단 로직 회귀를 바로 잡을 수 있다. 실제 PR 없이 픽스처만으로 조건 분기를 전부 커버할 수 있다는 것도 이 접근 방식의 장점이다.

## 배운 것

조건이 셋 이상 중첩되면 상태 머신으로 추상화하는 것이 코드 가독성과 디버깅 양쪽에 유리하다. 자동화 스크립트에서도 "이 PR은 지금 어떤 상태인가"를 명시적으로 모델링하면, 조건이 바뀔 때 어디를 수정할지 바로 보인다. if 체인을 늘리는 대신 상태 테이블을 업데이트하는 방식으로 유지보수하는 게 훨씬 낫다.
