## 문제: logging만 하고 삼키면 알림이 죽는다

API 요청 처리 중 외부 연동이 실패했다. 개발자는 이렇게 작성한다.

```python
try:
    result = external_api.call(payload)
except Exception:
    logger.exception("external_api 호출 실패")
    return None  # 또는 빈 응답 반환
```

로컬에서 보면 로그가 남는다. 그러나 프로덕션에서 이 패턴이 반복되면 두 가지 문제가 생긴다. 공통 예외 계층(미들웨어, 글로벌 핸들러)은 예외가 실제로 전파되어야 작동하는데 `except` 블록에서 삼키면 이 경로가 실행되지 않는다. Slack·Sentry 등 알림 파이프라인도 이 경로에 연결되어 있어 함께 우회된다. 로그 파일만 쌓이고 온콜 팀은 아무것도 모른다.

## 원칙: 비즈니스 실패는 공통 예외 경계까지 올린다

공통 예외 계층은 보통 다음 역할을 한다.

- HTTP 상태 코드 매핑 (예: 도메인 예외 → 4xx/5xx)
- 외부 알림 발송 (Slack, Sentry 등)
- 구조화된 에러 응답 포맷 통일
- 예외 맥락(request id, user id, payload)을 함께 기록

이 경로를 우회하는 `try-except-log-return`은 개발 편의를 위한 단기 선택처럼 보이지만, 운영 단계에서는 장애를 보이지 않게 만드는 패턴이다.

## 실패 유형별로 다르게 다루기

모든 예외를 무조건 올리는 것도 문제다. 예외 유형에 따라 처리 방향이 달라야 한다.

**1. 사용자 입력 검증 오류**

입력이 잘못된 경우는 클라이언트 오류다. 이 예외는 공통 예외 계층까지 올리되, 알림을 발송하지 않도록 예외 클래스를 구분한다.

```python
class ValidationError(AppException):
    # 공통 핸들러가 4xx로 매핑하고, 알림은 발송하지 않음
    notify = False
```

**2. 외부 연동 실패 (3rd-party API, downstream 서비스)**

이 실패는 운영팀이 알아야 한다. 예외를 삼키지 않고 공통 예외 계층으로 올린다.

```python
class ExternalServiceError(AppException):
    # 공통 핸들러가 5xx로 매핑하고, 알림을 발송함
    notify = True
```

```python
try:
    result = external_api.call(payload)
except SomeExternalError as e:
    raise ExternalServiceError("external_api 호출 실패") from e
    # logger.exception은 쓰지 않는다 — 공통 핸들러가 기록한다
```

**3. 선택적 부수효과 실패 (알림 발송, 이벤트 트리거 등)**

주요 트랜잭션과 무관한 부수효과가 실패했을 때는 전파보다 격리가 맞을 수 있다. 단, 격리하더라도 반드시 별도로 기록하거나 알려야 한다.

```python
try:
    send_notification(user_id, message)
except NotificationError:
    # 격리하되, logger만으로 끝내지 말고 dead-letter 큐나 별도 알림 사용
    alert_ops_channel("notification 발송 실패", context={"user_id": user_id})
```

## 안전 패턴

**공통 예외 클래스 계층 설계**

```python
class AppException(Exception):
    notify: bool = True  # 기본값: 알림 발송
    status_code: int = 500

class ValidationError(AppException):
    notify = False
    status_code = 400

class ExternalServiceError(AppException):
    notify = True
    status_code = 502
```

공통 미들웨어 또는 글로벌 핸들러가 `AppException`을 잡아 `notify` 플래그에 따라 알림을 분기한다. 개별 뷰/핸들러에서 알림 코드를 직접 쓰지 않아도 된다.

**Background job / async task에서의 예외 처리**

비동기 태스크나 백그라운드 워커는 HTTP 요청 수명 밖에서 동작하기 때문에 공통 미들웨어가 자동으로 잡지 못한다. 이 경우 태스크 러너 수준에서 별도 핸들러를 등록한다.

```python
@celery_app.task
def process_job(job_id):
    try:
        _run(job_id)
    except AppException as e:
        if e.notify:
            notify_ops(e)
        raise  # 태스크를 실패로 마킹하고 재시도 또는 dead-letter로 보냄
```

**catch-and-continue가 허용되는 조건**

격리해도 되는 케이스는 좁게 정의한다.

- 부수효과이고, 실패가 주요 트랜잭션 결과에 영향을 주지 않는다.
- 격리하더라도 실패를 다른 경로(dead-letter, 별도 알림, 재시도 큐)로 확인할 수 있다.
- `except` 블록이 `logger.exception`으로만 끝나지 않는다.

## 트레이드오프

**너무 많이 올리면**: 사소한 외부 오류가 전체 요청을 5xx로 만들 수 있다. 알림이 과도하게 발송되면 알림 피로도(alert fatigue)가 생겨 실제 장애를 놓친다.

**너무 많이 삼키면**: 운영팀이 장애를 모른다. 실패가 누적되어 데이터 불일치나 처리 누락이 생겨도 대응이 늦어진다.

균형점은 예외 유형에 따라 `notify` 여부를 명시적으로 선언하고, 공통 핸들러가 그 선언을 따르도록 구조화하는 것이다. 각 `try-except` 블록마다 알림 코드를 쓰는 것보다, 예외 클래스가 알림 정책을 갖게 하는 것이 관리하기 쉽다.

## 검증 방법

**grep으로 삼키는 패턴 찾기**

```bash
# logger만 남기고 raise나 AppException 없이 except를 닫는 패턴 탐색
grep -n "logger\.exception\|logger\.error" src/ -r \
  | grep -v "raise\|AppException"
```

**알림 경로 통합 테스트**

```python
def test_external_failure_triggers_notification():
    with patch("external_api.call", side_effect=ExternalServiceError("mock fail")):
        with patch("notify_ops") as mock_notify:
            client.post("/api/endpoint/", data={...})
    mock_notify.assert_called_once()
```

알림 함수가 실제로 호출되는지를 테스트한다. 단순히 5xx 응답 코드를 확인하는 것으로는 알림 파이프라인이 작동하는지 알 수 없다.

**단위 테스트: 예외 클래스 속성 확인**

```python
def test_validation_error_does_not_notify():
    assert ValidationError.notify is False

def test_external_service_error_notifies():
    assert ExternalServiceError.notify is True
```

공통 예외 계층이 의도대로 선언되어 있는지를 회귀 방지 차원에서 확인한다.

## 배운 것

`logger.exception`은 디버깅 도구다. 알림 파이프라인 대체재가 아니다. 예외를 삼키면 그 실패는 로그 파일 안에만 존재하고, 운영 관측성 시스템에는 흔적이 남지 않는다.

예외 클래스에 알림 정책을 선언해두면 새 핸들러를 추가할 때마다 알림 코드를 신경 쓰지 않아도 된다. 예외만 적절히 올리면 나머지는 공통 경로가 처리한다. `try-except` 블록을 쓸 때마다 "삼키는가, 공통 경계로 올리는가"를 체크하면 이 종류의 관측성 누락을 사전에 잡을 수 있다.
