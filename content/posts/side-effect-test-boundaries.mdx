## 문제 정의

취소, 환불, 상태 강제 전환처럼 되돌리기 어려운 흐름을 통합 테스트로 검증할 때 두 가지 문제가 반복해서 나타난다.

첫 번째는 **테스트 범위가 의도보다 크게 번지는 문제**다. "이 취소 흐름이 올바르게 동작하는지 확인한다"는 목표를 가지고 시작했지만, 실행 과정에서 사전에 의도하지 않은 주문들이 추가로 영향을 받는 경우가 생긴다. 예를 들어 "각 케이스별 취소 테스트"와 "부하 상황에서 취소 테스트"는 실행 규모가 완전히 다르다. 요청 명세의 명사 하나가 테스트 대상 건수와 부작용 범위를 바꾼다.

두 번째는 **중간 결과를 최종 성공의 증거로 오해하는 문제**다. 외부 결제사 취소 API가 성공 응답을 돌려줬다, HTTP 200을 받았다, 또는 DB의 특정 필드 하나가 기대한 값으로 바뀌었다 — 이것들은 흐름의 특정 단계가 동작했다는 증거이지, 비즈니스 최종 상태 전체가 올바르게 닫혔다는 증거가 아니다.

두 문제는 연결되어 있다. 범위가 불명확하면 어디까지 검증해야 하는지도 불명확해진다.

이 글은 취소 API 자체의 멱등성이나 외부 콜백 처리 방식을 다루기보다, 그런 흐름을 **어떻게 안전하게 검증할 것인가**에 초점을 둔다.

## 위험한 테스트 확대

### 명사 하나가 규모를 바꾼다

부작용 있는 테스트를 요청할 때 흔히 쓰는 표현이 있다.

- "stage 환경 테스트 주문들로 취소 흐름을 검증해주세요"
- "stage 환경 테스트 주문들로 부하 상황에서 취소 흐름을 검증해주세요"

첫 번째 요청은 대상을 특정 케이스로 좁히는 의도를 담고 있고, 두 번째 요청은 동시 다발로 처리하는 규모를 시험하는 의도를 담고 있다. 구현 관점에서 두 요청은 아주 다르다. 그러나 요청을 받는 사람이 미리 질문하지 않으면, 테스트 스크립트를 작성하는 시점에 어느 쪽 해석을 따를지 임의로 결정된다.

부작용 있는 테스트에서 이 모호함이 해결되지 않은 채 실행에 들어가면, 범위를 넓게 해석한 쪽이 훨씬 위험하다. 취소된 주문은 원복 과정이 복잡하고, 외부 결제사에 이미 전송된 취소 요청은 되돌리기 어렵다.

### 범위 계약 없이 실행하는 패턴

문제가 되는 전형적인 패턴이 있다.

```python
# 의사코드 — 범위 계약이 없는 위험한 형태
def run_cancel_test(env="stage"):
    orders = fetch_orders(env=env, status="PAYMENT_COMPLETED")
    # 몇 건인지 확인 없이 전부 취소 시도
    for order in orders:
        cancel_order(order.id)
```

이 스크립트는 stage 환경에 완료 상태 주문이 몇 건이든 전부 취소한다. 테스트 의도가 "각 케이스별 취소 시나리오를 1건씩 확인"이었더라도, 스크립트 자체에는 그 제한이 없다.

범위가 락인(lock-in)되지 않은 부작용 테스트는 실행 환경 상태에 따라 규모가 달라진다. stage 환경의 주문 수가 오늘과 다음 주에 다를 수 있다.

## 안전한 검증 계약

### 테스트 전에 범위를 잠근다

부작용 있는 테스트를 실행하기 전에 다음 세 가지를 명시한다.

1. **어떤 객체가 대상인가**: ID 목록 또는 명확한 필터 조건으로 특정한다.
2. **최대 몇 건까지 허용되는가**: 실행 전에 대상 건수를 세고 예상 범위를 초과하면 중단한다.
3. **전제 조건이 충족되어야 실행된다**: 대상 객체의 상태가 기대와 다르면 실행하지 않는다.

```python
# 의사코드 — 범위 계약을 포함한 형태
def run_cancel_test(target_order_ids: list[str], env="stage"):
    # 1. 명시적 대상 목록
    if not target_order_ids:
        raise ValueError("취소할 주문 ID를 명시해야 합니다")

    # 2. 건수 상한
    MAX_ALLOWED = 5
    if len(target_order_ids) > MAX_ALLOWED:
        raise ValueError(f"한 번에 최대 {MAX_ALLOWED}건까지만 허용합니다")

    # 3. 전제 조건 확인 — 실행 전
    orders = fetch_orders_by_ids(target_order_ids, env=env)
    for order in orders:
        if order.status != "PAYMENT_COMPLETED":
            raise PreconditionError(
                f"주문 {order.id}의 상태가 PAYMENT_COMPLETED가 아닙니다: {order.status}"
            )

    # 조건을 모두 통과한 경우에만 실행
    for order in orders:
        cancel_order(order.id)
```

이 구조에서 대상 건수를 명시하지 않으면 함수 자체가 실행을 거부한다. 요청 시점에 모호하게 남겨뒀던 범위 문제가 코드 경계에서 강제로 드러난다.

### 테스트 전후 상태를 스냅샷으로 고정한다

취소 테스트를 실행하기 전에 대상 주문들의 현재 상태를 스냅샷으로 기록해 두면, 테스트 후 "이 주문은 원래 어떤 상태였는가"를 확인할 수 있다.

```python
# 의사코드
def snapshot_before(order_ids):
    return {
        order.id: {
            "order_status": order.status,
            "cancel_reason": order.cancel_reason,
            "items": [{"id": i.id, "status": i.status} for i in order.items],
        }
        for order in fetch_orders_by_ids(order_ids)
    }

before = snapshot_before(target_order_ids)
# ... 취소 실행 ...
after = snapshot_after(target_order_ids)

for order_id in target_order_ids:
    assert_transition(before[order_id], after[order_id])
```

스냅샷은 검증 단계에서 "어디서 무엇이 바뀌었는가"를 추적하는 기준점이 된다.

## 최종 상태 검증

### 중간 결과는 최종 상태를 증명하지 않는다

취소 흐름에서 흔히 마주치는 착각이 있다.

- 외부 결제사 취소 API가 `200 OK`를 반환했다 → 취소가 완료됐다
- 내부 DB의 `cancel_status` 필드가 `CANCELED`로 바뀌었다 → 취소가 완료됐다
- 취소 이벤트가 큐에 발행됐다 → 취소가 완료됐다

이 중 어느 것도 단독으로는 비즈니스 최종 상태를 증명하지 못한다. 외부 결제사 API 성공은 외부 시스템 쪽 취소를 의미하지만, 내부 주문 상태가 닫혔는지는 별도로 확인해야 한다. 내부 DB의 특정 필드 하나가 바뀐 것은 부분 상태 전환이지, 전체 취소 흐름이 모두 실행됐다는 증거가 아니다.

### 수동 보정 후 검증의 함정

부작용 테스트에서 특히 주의해야 하는 패턴이 있다. 테스트 환경에서 "이 주문의 상태만 먼저 원하는 값으로 맞춰두고 취소 콜백을 검증하자"는 접근이다.

```python
# 의사코드 — 문제 있는 패턴
def test_cancel_callback():
    order = create_test_order()
    # 특정 필드만 직접 조작
    db.execute("UPDATE orders SET order_status = 'CANCEL_PENDING' WHERE id = ?", order.id)

    # 취소 콜백 발송
    send_cancel_callback(order.id)

    # 외부 결제 상태만 확인
    payment = fetch_payment(order.id)
    assert payment.status == "CANCELED"
```

이 테스트는 외부 결제 상태가 `CANCELED`로 바뀌었다는 것은 확인하지만, 실제로 검증하고자 했던 취소 흐름 전체가 동작했다고 말할 수 없다. `order_status`를 직접 조작했기 때문에 실제 취소 요청 처리 경로가 실행된 것이 아니다. 취소 흐름이 의존하는 다른 상태 전환 — 예를 들어 주문 아이템별 상태 변경, 보상 처리, 알림 발송 등 — 은 검증 대상에서 빠져있다.

수동으로 보정한 것은 테스트 환경을 특정 상태로 세팅한 것이지, 취소 흐름 자체를 실행한 것이 아니다.

### 비즈니스 최종 상태 기준으로 검증한다

취소 흐름이 끝난 뒤 확인해야 하는 것은 "외부 결제사가 성공이라고 했는가"가 아니라 "비즈니스 관점에서 이 취소가 닫혔는가"다.

```python
# 의사코드 — 최종 상태 기준 검증
def assert_cancel_complete(order_id):
    order = fetch_order(order_id)
    payment = fetch_payment(order_id)

    # 1. 주문 전체 상태
    assert order.status == "CANCELED", f"주문 상태: {order.status}"

    # 2. 주문 아이템 상태
    for item in order.items:
        assert item.status in ("CANCELED", "REFUNDED"), f"아이템 {item.id} 상태: {item.status}"

    # 3. 외부 결제사 취소 여부
    assert payment.cancel_status == "CANCELED", f"결제 취소 상태: {payment.cancel_status}"

    # 4. 취소 의도 데이터가 기록됐는가
    assert order.cancel_reason is not None, "취소 사유가 기록되지 않음"
    assert order.canceled_at is not None, "취소 시각이 기록되지 않음"
```

검증 항목을 나열할 때 "이 취소 흐름이 실제 운영에서 완료됐다고 판단하는 기준이 무엇인가"를 먼저 정의하고, 그 기준에서 역으로 검증 항목을 도출한다. HTTP 응답 코드나 단일 필드 값은 그 기준을 달성했다는 증거 중 하나일 뿐, 기준 자체가 아니다.

### 취소 의도 데이터를 함께 확인한다

최종 상태를 검증할 때 결과 상태값만 보면 "어떤 의도로 취소됐는가"가 기록됐는지 놓치기 쉽다. 취소 사유, 요청 시각, 취소 요청을 보낸 주체 정보는 나중에 운영 문제를 추적할 때 유일한 단서가 된다.

```python
# 의사코드 — 취소 의도 데이터 검증
cancel_audit = fetch_cancel_audit(order_id)

assert cancel_audit.requested_by is not None   # 취소 요청 주체
assert cancel_audit.cancel_reason is not None  # 취소 사유
assert cancel_audit.request_payload is not None  # 취소 요청 데이터
assert cancel_audit.external_cancel_id is not None  # 외부 결제사 취소 식별자
```

취소 이후 정산이나 운영 확인 과정에서 "이 취소가 왜 발생했는가"를 코드 없이 추적하려면 이 데이터가 반드시 있어야 한다.

## 트레이드오프

### 범위를 좁힐수록 놓치는 케이스가 생긴다

대상 건수를 제한하고 전제 조건을 강하게 잡으면 테스트가 더 안전해지지만, 특정 상태 조합이나 엣지 케이스를 커버하지 못할 수 있다. "모든 케이스를 한 번에 확인하고 싶다"는 욕구와 "한 번 실행으로 부작용이 너무 넓게 퍼지는 것을 막고 싶다"는 요구는 트레이드오프 관계다.

현실적인 타협은 케이스별로 독립적인 테스트를 작성하는 것이다. 정상 취소 케이스, 부분취소 케이스, 이미 취소된 건에 대한 재요청 케이스를 각각 분리하면 각 테스트의 대상 건수는 1건으로 좁아지고, 전체 커버리지는 케이스 수만큼 늘어난다.

### 최종 상태 검증은 셋업 비용이 높다

HTTP 응답 코드 하나를 확인하는 것보다 비즈니스 최종 상태 전체를 확인하는 것이 셋업이 더 복잡하다. 관련된 테이블을 모두 조회해야 하고, 기대값을 미리 정의해야 하고, 관련 시스템이 모두 stage 환경에서 동작하고 있어야 한다.

그러나 이 비용은 대부분 테스트를 처음 작성할 때 한 번 든다. 이후 회귀 테스트에서는 같은 검증 코드가 재사용된다. 반면, 중간 결과만 검증하는 얕은 테스트는 실제 비즈니스 흐름이 깨져도 통과하기 때문에 거짓 안도감을 준다.

### 수동 보정과 실제 흐름 사이의 선택

테스트 환경을 원하는 상태로 빠르게 세팅하기 위해 DB를 직접 조작하는 방법은 편리하지만, 실제 취소 흐름이 아닌 상태에서 검증을 수행하게 된다. 실제 흐름을 처음부터 실행하는 방법은 셋업이 더 복잡하지만, 취소 흐름 전체를 실제로 통과시킨다는 점에서 증거력이 높다.

"어떤 부분을 검증하는 테스트인가"를 명확히 정의하면 이 선택이 쉬워진다. 취소 콜백 처리 로직만 단독으로 검증하고 싶다면 DB 직접 조작도 합리적이다. 그러나 취소 흐름 전체의 정합성을 검증하고 싶다면 처음부터 취소를 실행해야 한다.

### 실패 후 정리 비용도 테스트 설계에 포함한다

부작용 있는 테스트는 실패했을 때도 흔적을 남긴다. 외부 취소는 성공했지만 내부 주문 상태 갱신이 실패할 수도 있고, 일부 주문만 중간 상태에 남을 수도 있다. 따라서 실행 전에 "부분 성공이 발생하면 어떻게 관측하고 정리할 것인가"를 정해 둬야 한다. 전후 스냅샷, 실패 주문 목록, 재처리 가능 여부, 수동 정리 담당 경로가 없으면 테스트 실패가 곧 운영 데이터 오염으로 이어진다.

## 검증 체크리스트

부작용 있는 통합 테스트를 설계하거나 리뷰할 때 확인하는 항목들이다.

**범위 계약**

- [ ] 대상 객체가 ID 또는 명확한 필터로 특정되어 있는가
- [ ] 실행 전에 대상 건수를 세고 상한을 초과하면 중단하는 안전장치가 있는가
- [ ] 전제 조건(대상 상태, 환경)이 충족되지 않으면 실행을 거부하는가
- [ ] 테스트 요청의 의도(케이스 검증인지, 규모 시험인지)가 실행 코드와 일치하는가

**최종 상태 검증**

- [ ] 검증 항목이 HTTP 응답 코드나 단일 필드를 넘어서 비즈니스 최종 상태를 포함하는가
- [ ] 외부 시스템(결제사) 상태와 내부 시스템 상태를 모두 확인하는가
- [ ] 취소 의도 데이터(취소 사유, 요청 시각, 요청 주체)가 기록됐는가
- [ ] 연관된 하위 엔티티(주문 아이템, 보상 내역 등) 상태도 확인하는가
- [ ] 수동 보정이 들어간 테스트라면 "어떤 범위를 검증하는 테스트인지"가 명시되어 있는가

**부작용 관리**

- [ ] 테스트 실행 전후 상태를 스냅샷으로 기록하는가
- [ ] 테스트 실패 시 부분 실행된 부작용을 어떻게 처리할지 정의되어 있는가
- [ ] 테스트 목적이 다른 사람도 읽고 이해할 수 있도록 명시되어 있는가

## 배운 것

부작용 있는 통합 테스트에서 가장 먼저 물어야 할 질문은 "이 테스트로 무엇이 영향을 받는가"와 "어디까지 확인해야 이 흐름이 올바르다고 말할 수 있는가"다.

첫 번째 질문에 답하지 않으면 테스트 요청의 표현 차이 하나가 실행 규모를 예측 불가능하게 바꾼다. 범위 계약은 이 불확실성을 실행 코드 안으로 끌어들여서 명시적으로 다루는 방법이다.

두 번째 질문에 답하지 않으면 중간 결과를 최종 성공으로 오해하는 검증이 누적된다. HTTP 200을 받은 것, 외부 결제사가 취소 성공을 반환한 것, 특정 필드 하나가 바뀐 것은 각각 흐름의 일부가 동작했다는 신호이지, 비즈니스 최종 상태 전체가 닫혔다는 증거가 아니다.

수동으로 DB 필드 하나를 보정한 뒤 콜백을 검증하는 패턴은 특히 위험하다. 실제 취소 흐름을 실행한 것처럼 느껴지지만, 보정한 시점에서 이미 "실제 취소 요청이 들어왔을 때 동작하는 경로"를 우회했다. 테스트가 통과해도 실제 취소 흐름의 정합성은 여전히 미검증 상태로 남는다.

설계 원칙을 두 가지로 요약하면 이렇다.

1. 파괴적 테스트는 범위 계약을 먼저 잠근다. 실행 전에 대상을 특정하고, 건수를 세고, 전제 조건을 확인한다.
2. 검증 기준은 비즈니스 최종 상태에서 역방향으로 정의한다. "이 취소가 완료됐다고 판단하는 기준"을 먼저 쓰고, 그 기준을 달성했는지 확인하는 순서로 작성한다.

중간 결과만 확인하는 테스트가 통과하는 것은 흐름이 올바르다는 증거가 아니다. 거짓 안도감으로 더 오래 숨겨진 버그가 생긴다.
