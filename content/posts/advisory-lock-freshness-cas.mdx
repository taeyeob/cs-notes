## 문제 정의

배치가 분석 데이터를 읽어 캐시를 갱신하는 흐름에서 "동시 실행 방지"는 필요조건이지만 충분조건이 아니다.

advisory lock을 도입하면 같은 키에 대한 배치가 동시에 여럿 뜨는 상황은 막을 수 있다. 그런데 다음 시나리오를 보자.

1. T=0 에 배치 A가 시작된다. 분석 데이터를 읽기 시작한다.
2. T=5 에 배치 B가 시작된다. 더 빠른 경로로 데이터를 읽어 T=8 에 캐시에 저장한다.
3. T=12 에 배치 A가 끝난다. T=0 시점에 읽은 데이터로 캐시를 덮어쓴다.

lock을 직렬화해서 A가 끝난 뒤 B가 시작된다면 문제가 없다. 그러나 A가 락을 잡고 있는 동안 B가 건너뛰거나(skip), A의 재시도가 뒤늦게 도착하거나, 락 없는 재시도 경로가 별도로 존재하는 경우 이 덮어쓰기가 발생한다. 결과적으로 T=8 에 올라간 최신 데이터가 T=0 기준의 낡은 데이터로 교체된다.

## 락이 막아주는 것과 막아주지 못하는 것

| 상황                                         | Advisory Lock | CAS (freshness token) |
| -------------------------------------------- | ------------- | --------------------- |
| 같은 키에 배치가 동시에 여럿 실행            | 막음 (직렬화) | —                     |
| 락 대기 중 skip한 배치가 나중에 재시도       | 막지 못함     | 막음                  |
| 느린 이전 배치가 빠른 최신 배치 이후에 완료  | 막지 못함     | 막음                  |
| 네트워크 재시도로 같은 페이로드가 두 번 저장 | 막지 못함     | 막음 (멱등)           |

advisory lock은 "지금 이 순간 실행 중인 복사본이 하나"를 보장한다. 그러나 시간상으로 앞선 작업의 결과가 뒤에 저장되는 순서 역전은 막지 못한다.

## Freshness Token: 작업 시작 시각을 페이로드에 고정

핵심 아이디어는 간단하다. 배치가 **작업을 시작한 시각**(또는 단조 증가하는 세대 번호)을 `generatedAt`으로 페이로드에 박아 두고, 저장 시점에 그 값이 현재 캐시보다 최신일 때만 쓰는 것이다.

```python
def run_batch(key: str) -> None:
    generated_at = utcnow()          # 작업 시작 시각을 캡처
    data = fetch_analytics_data()    # 분석 데이터 읽기 (느릴 수 있음)

    payload = {
        "items": data,
        "generatedAt": generated_at.isoformat(),
    }
    cache_write_if_fresher(key, payload, generated_at)


def cache_write_if_fresher(key: str, payload: dict, generated_at: datetime) -> bool:
    existing = cache.get(key)
    if existing is not None:
        existing_ts = parse_datetime(existing["generatedAt"])
        if existing_ts >= generated_at:
            # 현재 캐시가 더 최신 → 덮어쓰지 않음
            return False
    cache.set(key, payload)
    return True
```

`generated_at`은 데이터를 읽은 직후가 아니라 **작업을 시작하는 순간** 캡처해야 한다. 그래야 느린 배치의 `generatedAt`이 빠른 배치보다 이전 시각을 갖게 되어 CAS가 올바르게 작동한다.

## 저장 시점 경쟁 조건

단순한 get-then-set은 그 사이에 다른 프로세스가 끼어들 수 있다.

```
프로세스 A: get → 비어 있음 확인
프로세스 B: get → 비어 있음 확인
프로세스 A: set (T=3 페이로드)
프로세스 B: set (T=1 페이로드) ← 덮어씀
```

이 경쟁 조건을 닫는 방법은 세 가지다.

**방법 1: 분산 락 + 단순 CAS**

저장 직전 짧은 시간만 락을 잡고 get → compare → set을 원자적으로 처리한다. 락 보유 시간이 짧아 병목이 적다.

**방법 2: Lua 스크립트 또는 트랜잭션 CAS**

Redis라면 Lua 스크립트로 get-compare-set을 서버 측에서 원자적으로 실행한다.

```lua
-- Redis Lua: 더 최신인 경우에만 set
local existing = redis.call('GET', KEYS[1])
if existing then
  local existing_ts = cjson.decode(existing)['generatedAt']
  if existing_ts >= ARGV[2] then
    return 0  -- 더 오래된 데이터, 기록하지 않음
  end
end
redis.call('SET', KEYS[1], ARGV[1])
return 1
```

**방법 3: 외부 버전 레지스트리**

캐시 외부(DB 또는 별도 키)에 현재 최신 `generatedAt`을 저장하고, 배치는 먼저 그 값을 확인한 뒤 더 최신일 때만 캐시에 쓴다. 캐시가 TTL로 만료되어도 버전 정보가 남아 있어 안전하다.

## 빈 결과와 실패의 트레이드오프

CAS를 적용할 때 두 가지 정책 결정이 필요하다.

**빈 결과(empty result)를 저장할 것인가?**

분석 데이터가 아직 없어 `items: []`가 나왔을 때, 이를 `generatedAt`과 함께 저장하면 이후 배치가 실제 데이터를 가져와도 CAS가 통과하지 않는다는 문제가 없다(더 최신이므로). 그러나 빈 결과를 저장하면 캐시가 채워지기 전에 클라이언트가 빈 응답을 보게 된다. 서비스 특성에 따라 "빈 결과는 스킵, 캐시 미스로 폴백"을 선택할 수도 있다.

**실패한 배치의 generatedAt을 어떻게 처리하나?**

중간에 실패한 배치는 `generatedAt`을 소모했지만 캐시를 갱신하지 못했다. 재시도 시 새 `generatedAt`을 찍으면 시간이 흐른 만큼 최신 세대가 되어 정상 저장된다. 원래 `generatedAt`을 재사용하면 다른 배치가 그 사이에 더 최신 결과를 저장했어도 덮어쓸 수 있으므로 위험하다. 재시도는 항상 새 `generatedAt`으로 시작하는 것이 안전하다.

## 락과 CAS의 역할 분담

두 메커니즘을 함께 쓸 때 역할을 명확히 나누면 설계가 단순해진다.

```
advisory lock: 같은 키의 배치가 동시에 여럿 뜨지 않도록 직렬화
CAS: 직렬화가 깨지거나 재시도가 생겼을 때 오래된 결과가 저장되지 않도록 최후 방어
```

락은 불필요한 작업을 줄이는 최적화이고, CAS는 정합성을 보장하는 안전망이다. 락이 있어도 CAS가 없으면 정합성이 깨질 수 있다. CAS만 있고 락이 없으면 작업 낭비와 분석 저장소 부하가 늘어난다.

## 검증 체크리스트

이 패턴을 적용하거나 리뷰할 때 확인하는 항목들이다.

- `generatedAt`을 데이터 읽기 완료 후가 아닌 **작업 시작 시점**에 캡처하는가
- 저장 시 기존 캐시의 `generatedAt`과 비교하는 CAS 조건이 있는가
- get-compare-set 사이의 경쟁 조건을 락이나 원자적 연산으로 닫았는가
- 재시도 배치는 원래 `generatedAt`을 재사용하지 않고 새 시각을 쓰는가
- 빈 결과와 실패 케이스의 저장 정책이 명시적으로 결정되어 있는가
- 테스트가 다음 두 케이스를 커버하는가:
  - 최신 `generatedAt`을 가진 배치가 더 오래된 캐시를 덮어쓰는 정상 경로
  - 오래된 `generatedAt`을 가진 배치가 최신 캐시를 덮어쓰지 않는 방어 경로

## 배운 것

배치 캐시 갱신에서 "락만 있으면 안전하다"는 직관은 절반만 맞다. 락은 동시성 문제를 해결하지만, 시간 역전(오래 걸린 이전 배치가 빠른 최신 배치 이후에 완료)은 별개의 문제다. 이 두 문제를 하나의 메커니즘으로 해결하려 하면 과도하게 긴 락 보유나 복잡한 취소 로직이 필요해진다.

`generatedAt` 기반 CAS는 이 문제를 분리한다. 락은 불필요한 경쟁 작업을 줄이고, CAS는 어떤 이유로든 오래된 결과가 캐시에 도달했을 때 저장을 거부한다. 두 메커니즘이 독립적으로 작동하기 때문에 한쪽이 의도대로 동작하지 않아도 다른 쪽이 정합성을 지킨다.

테스트를 작성할 때도 "정상 저장 케이스"와 "덮어쓰기 거부 케이스"를 분리해서 각각 명시적으로 검증해야 한다. 두 케이스를 하나의 통합 테스트로 묶으면 어느 쪽이 깨진 건지 구분하기 어렵다.
