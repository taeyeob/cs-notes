## 문제 상황

정산성 엑셀 리포트를 만들다 보면 "하나의 결제 요청 안에 여러 주문이 묶여 있는" 상황을 자주 만난다. 단순하게 조인하면 주문 수만큼 row가 늘어난다. 각 row마다 결제 총액을 그대로 쓰면 금액이 중복 계산된다. 반대로 금액을 SUM으로 묶으면 배송비나 할인 같은 항목이 끼어들어 의도치 않게 부풀거나 줄어든다.

실제로 마주친 케이스는 이렇다.

- 하나의 결제 요청 식별자(이하 `payment_request_id`)에 주문번호가 여러 개 연결되어 있다.
- 엑셀에는 주문번호를 전부 표시해야 하지만 row는 결제 요청 단위로 하나여야 한다.
- 금액은 결제 총액이 아니라 주문별 상품 금액(`item_price`)의 합이어야 한다.
- 한 결제 요청에서 지출 로그가 여러 건 생성되는 케이스(직접 결제 등)도 있어, 단순 조인을 쓰면 row가 두 배로 불어난다.

## 왜 단순 합산·단순 조인이 위험한가

### 단순 조인의 함정

결제 요청 테이블과 주문 테이블을 1:N으로 조인하면, 결과 row 수는 주문 수에 비례한다. 여기에 지출 로그 테이블까지 조인하면 주문 수 × 로그 수만큼 row가 나온다. 이 상태에서 금액 컬럼을 그대로 읽으면 같은 금액이 여러 번 집계된다.

```
-- 위험한 패턴
SELECT pr.id, o.order_no, pr.total_amount
FROM payment_requests pr
JOIN orders o ON o.payment_request_id = pr.id
JOIN spend_logs sl ON sl.payment_request_id = pr.id
-- row 수 = 주문 수 × 로그 수, total_amount는 중복
```

### 단순 SUM의 함정

row를 하나로 줄이려고 GROUP BY 후 SUM을 쓰면, 어떤 컬럼을 SUM하느냐에 따라 결과가 달라진다. 결제 총액에는 배송비, 할인 쿠폰, 포인트 차감이 섞여 있다. 단순히 SUM(total_amount)를 쓰면 "상품 금액만"이라는 조건을 충족하지 못한다.

## 설계 원칙

두 가지 원칙으로 접근한다.

**집계 단위를 명확히 분리한다.** 주문번호를 한 셀에 모아야 한다면, 주문을 먼저 서브쿼리나 CTE로 집계(GROUP_CONCAT 또는 array_agg)한 뒤 결제 요청에 조인한다. 조인 이전에 주문을 이미 하나의 행으로 만들어 두면 이후 조인이 row를 늘리지 않는다.

**금액 기준을 코드 한 곳에 고정한다.** "상품 금액만"이라는 규칙은 결제 총액 컬럼을 재사용하지 말고, 리포트 생성 경로에서 명시적으로 선택한다. API 응답 형식을 바꾸면 다른 클라이언트에 사이드 이펙트가 생기므로, 다운로드 경로(엑셀 생성 함수 또는 배치 잡)에서만 집계 기준을 조정한다.

## 구현 접근

### 주문번호 집계를 먼저 수행

```
-- 의사코드
WITH aggregated_orders AS (
  SELECT
    payment_request_id,
    string_agg(order_no, ', ') AS order_nos,
    SUM(item_price)            AS total_item_price
  FROM orders
  GROUP BY payment_request_id
)
SELECT
  pr.id,
  ao.order_nos,
  ao.total_item_price
FROM payment_requests pr
JOIN aggregated_orders ao ON ao.payment_request_id = pr.id
-- 지출 로그는 별도 서브쿼리로 처리하거나 EXISTS로 필터
```

이 방식은 결제 요청 1건당 row가 항상 1개임을 보장한다.

### 지출 로그가 여러 건인 케이스

지출 로그가 1:N으로 붙어 있으면 위 쿼리에 단순 JOIN을 추가하는 순간 row가 다시 늘어난다. 이 경우는 두 가지 방법 중 하나를 쓴다.

- 지출 로그도 결제 요청 ID 기준으로 미리 집계해서 LEFT JOIN한다.
- 지출 로그는 쿼리 밖에서 애플리케이션 레이어에 Map으로 캐싱해두고, row를 순회하며 룩업한다.

```python
# 의사코드 — 애플리케이션 레이어 룩업 패턴
spend_map = {log.payment_request_id: log for log in spend_logs}

for row in report_rows:
    log = spend_map.get(row.payment_request_id)
    row.spend_amount = log.amount if log else 0
```

이 패턴은 쿼리 복잡도를 낮추고, 집계 단위 혼동을 방지한다.

### 변경 범위를 엑셀 경로로 한정

API 응답 구조를 바꾸지 않고 리포트 전용 경로에서만 집계 로직을 수정한다. 구체적으로는 엑셀 다운로드 함수와 배치 기반 다운로드 잡 두 군데만 수정 대상으로 삼는다. 이렇게 하면 기존 API를 사용하는 다른 뷰나 기능에 영향이 없다.

## 검증 방법

리포트 로직의 버그는 단위 테스트보다 통합 테스트에서 잡기 쉽다. 핵심 케이스는 다음 두 가지다.

**1:N 주문 케이스.** 하나의 결제 요청에 주문이 두 개 이상 붙어 있을 때, 결과 row가 1개이고, 주문번호가 모두 포함되고, 금액이 상품 금액의 합과 일치하는지 확인한다.

**지출 로그 중복 케이스.** 하나의 결제 요청에 지출 로그가 여러 건일 때, row가 1개이고 금액이 중복 합산되지 않는지 확인한다.

CI에서 관련 테스트만 통과 여부를 확인할 때, 전체 테스트 잡에 기존 실패가 섞여 있으면 혼동할 수 있다. 이 경우 변경한 파일 목록과 실패한 테스트 파일을 비교해 인과관계가 없음을 확인하는 것이 안전하다.

## 배운 점

- **row 수를 먼저 고정하라.** 집계 전에 조인을 쌓으면 row 수 예측이 어렵다. N:M 관계가 하나라도 끼면 기하급수적으로 늘어날 수 있다.
- **금액 기준은 코드 한 곳에 명시한다.** "결제 총액이냐, 상품 금액이냐"는 암묵적으로 두면 나중에 누군가 혼동한다. 상수나 함수 이름에 의도를 드러내는 것이 낫다.
- **변경 범위를 의식적으로 좁힌다.** 다운로드 경로만 고쳐야 할 때 API 응답까지 건드리면 영향 범위를 예측하기 어렵다. 범위를 명시하면 리뷰도 쉽고 롤백도 쉽다.
- **테스트 실패 원인을 구분하는 습관이 중요하다.** 전체 잡 실패를 무조건 이번 변경 탓으로 돌리면 기존 실패를 방치하게 된다. 변경 파일과 실패 파일을 대조하는 것을 루틴으로 삼는다.
